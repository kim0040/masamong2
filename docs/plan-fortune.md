# 매일 운세 개선 계획 (2026-11-02)

이 문서는 아침 운세 브리핑(`fortune.subscribe`)과 운세 조회(`/운세`) 기능의 개선 계획입니다. 현재 미구현 상태이며, 7장의 결정 사항이 확정되면 6장의 순서대로 작업을 진행합니다.

## 1. 지금 동작

- 등록 시 생년월일(필수)과 태어난 시각·출생지·성별(선택)에 대한 동의를 받은 뒤 저장합니다([`fortune.go`](../internal/application/fortune.go)).
- 아침 브리핑은 사용자별 설정 시각보다 10분 일찍(`lead_min`) 1회의 모델 호출로 생성합니다.
  - 모델은 `response` 역할, 생각 끄기(`effort none`), 최대 900토큰, temperature 0.8입니다.
  - 근거 자료는 오늘 날짜, 타고난 사주(시주는 시각을 알 때만), 오늘의 간지, 별자리, 오늘 행성 위치입니다.
  - 모델이 `KEY: 값` 형태로 한 줄씩 출력하면, Go에서 점수 막대가 포함된 카드로 가공합니다([`reading.go`](../internal/features/fortune/reading.go), [`fortune_card.go`](../internal/application/fortune_card.go)).
  - 시간대와 방해 금지 시간을 준수하며, 재시도하더라도 중복 발송하지 않습니다.
- 개인 조회는 하루 3번까지입니다. 공개 채널에는 세 줄 요약만 나갑니다.

**운영 기록(읽기 전용 집계, 최근 30일):**

- 등록 3명, 구독 2명. 브리핑 호출은 하루 약 2번, 출력 약 250토큰, 하루 약 $0.0005입니다.
- 2026-10-15 수정 이후 출력 한도에 걸려 잘린 적이 없습니다. 두 구독자 모두 마지막 발송 상태가 `sent`입니다.
- 비용과 안정성은 문제없는 수준이며, 개선할 핵심 영역은 **재미, 반복, 연결**입니다.

## 2. 확인한 문제

코드 분석을 통해 확인한 내용입니다.

| # | 문제 | 근거 |
|---|---|---|
| F-1 | 매일 브리핑이 전날 내용을 모른 채 매번 새로 생성됩니다. 행운 색·물건이 며칠 연속 중복될 수 있고, "어제는 바빴죠"와 같이 이전 내용과 이어지는 맥락이 없습니다. | `morningFor`가 프롬프트에 그날 자료만 넣습니다 |
| F-2 | 반말 프리셋을 고른 방에서도 운세는 언어 기본 어조(해요체)입니다. | [KNOWN_ISSUES 12](KNOWN_ISSUES.md) |
| F-3 | 브리핑이 끝내 실패하면 사용자는 아무 말도 받지 못합니다. | `job.State = "failed"`만 저장합니다([plan-discord-experience 5.10](plan-discord-experience.md)) |
| F-4 | 브리핑 내용이 수신자의 실제 하루(날씨 등)와 이어지지 않습니다. 날씨 지역 정보는 `preferences.set`의 `weather_region`에 이미 설정되어 있습니다. | [`preferences.go`](../internal/application/preferences.go) |
| F-5 | 수신자가 운세를 어떻게 평가했는지 피드백을 알 수 없습니다. 제공되는 버튼은 [구독 해제] 하나뿐입니다. | `fortune:unsub`만 있습니다 |
| F-6 | 등록 전에는 체험할 수단이 별자리 운세뿐이고, 개인 운세 등록으로 유도하는 동선이 없습니다. 최근 30일간 등록자는 3명에 불과합니다. | 운영 집계 |

아직 검증하지 못한 가설도 있습니다. 모델 점수가 75~85점에 몰린다는 지적이나, 지난 브리핑 본문을 보관하지 않아 검증할 데이터가 없습니다. 7일 기록(P1)을 도입하면 함께 확인할 수 있습니다.

## 3. 제안 (우선순위 순)

제안된 아이디어 중 일부는 Gemini Argon 브레인스토밍에서 도출되었으며, 실제 코드와 대조하여 선별 및 정리했습니다.

### P1. 최근 7일 기록으로 반복을 막고 이어지게 (작음)

- 사용자별로 최근 7일간의 점수, 한 줄 요약, 행운 색·물건·숫자를 간소하게 저장합니다. 원문은 저장하지 않고 파싱한 값만 저장합니다.
- 프롬프트에 "최근 쓴 행운 항목(피할 것)"과 "어제 한 줄"을 약 60토큰으로 넣습니다.
- 어제 브리핑을 수신한 경우에만 어제를 언급하며, 날짜가 연속되지 않으면 프롬프트에 넣지 않습니다.
- 모델이 여전히 동일한 행운 항목을 출력하면 Go가 언어팩의 계절 목록 값으로 대체합니다.
- 비용은 브리핑당 $0.00005 정도 늘어납니다. 7일이 지난 기록과 동의 철회 시의 기록은 지웁니다(`deleteFortune`).

### P2. 실패해도 조용히 넘어가지 않기 (작음)

- 생성을 최종 실패하면 예정된 시각에 짧은 대체 문구 카드를 보냅니다(예: "오늘은 별자리 차트를 엎질렀어요"). 카드에는 [지금 뽑기] 버튼을 추가합니다.
- 버튼을 여러 번 눌러도 사용자마다 한 번만 생성하도록 잠금을 겁니다.
- DM이 닫혀 있어(`ErrDMClosed`) 실패한 경우는 대체 카드도 보낼 수 없습니다. 이때는 연속 N회 실패하면 구독을 일시정지하고 콘솔에 표시합니다.

### P3. 반응 버튼 (작음)

- 카드에 [맞았어], [반전이었어], [할 일 했어] 세 버튼을 답니다. 모델 호출은 없습니다.
- 운영자는 콘솔에서 반응 수와 열람 비율만 확인하며, 누가 눌렀는지는 표시하지 않습니다.
- 버튼 상태는 DB에 저장해, 배포 뒤에도 예전 카드의 버튼이 동작하게 합니다.

### P4. 말투 맞추기 (작음, 결정 필요)

- 사람마다 DM 말투(존댓말/반말)를 고르게 하고, 첫 카드에 바꾸기 버튼을 둡니다.
- 서술자 분위기 프리셋(다정한 친구, 장난스러운 점술가, 담백한 현실주의자)을 언어팩의 두 줄짜리 문구로 둡니다.
- 프롬프트 문구는 언어팩에만 둡니다(코드에 넣지 않음). 반말이 없는 언어(영어 등)에서는 프리셋이 말투 대신 분위기만 바꿉니다.

### P5. 날씨 한 줄 덧붙이기 (중간, 결정 필요)

- 운세 본문과 분리된 "마사몽의 덧말" 한 줄을 추가합니다. 사용자가 직접 설정한 `weather_region`의 오늘 날씨(비, 한파, 미세먼지 등 대략적인 정보)를 반영합니다.
- 출생지는 지금 사는 곳이 아닐 때가 많아 쓰지 않습니다.
- 예약 알림 제목, 기억 메모, 대화 내용은 넣지 않습니다(5장).
- 기상 특보가 있으면 야외 활동을 권하는 "할 일"을 제외하도록 프롬프트에 지시합니다.

### P6. 특별한 날을 Go가 미리 계산 (중간)

- 천을귀인일, 일진 충·합처럼 간지로 정해지는 날을 Go가 계산해 근거 자료에 넣습니다. 그런 날에는 카드 색 강조도 붙입니다.
- 점수 변화가 모델의 자의적인 판단이 아니라 사주 달력에 근거하게 됩니다.
- 기운이 낮은 날에는 "쉬어 가는 날"과 가벼운 액땜 한 가지로 씁니다. 불안을 키우는 경고 대신입니다.
- 시주를 모르는 사람은 판단 근거가 줄어든다는 점을 문구에 반영합니다.

### P7. 오늘 카드에 이어서 묻기 (중간)

- 아침 카드에 [물어보기] 버튼을 답니다. 누르거나 카드에 답장하면, 그날 근거 자료와 카드 내용을 넣은 짧은 대화(2~3턴)를 엽니다.
- 다시 뽑기가 아닙니다. 건강·돈·이별 같은 중요한 결정은 친구처럼 방향을 돌리는 안내 문구를 둡니다.
- 하루 몇 턴까지 허용할지는 정해야 합니다(7장).

### P8. 일요일 주간 요약 (중간)

- 해당 주의 점수 흐름, 실천한 일, 모은 행운 색을 카드 한 장으로 발송합니다. 추가 모델 호출 없이 Go가 P1 기록을 바탕으로 생성합니다.
- 놓친 날은 지적하지 않고 좋았던 날만 보여 줍니다.
- [공유용 만들기] 버튼은 사주 정보를 뺀 버전을 공개 채널에 올릴 수 있게 합니다.

### P9. 등록 전 맛보기 (작음, 결정 필요)

- 공개 채널의 세 줄 요약과 별자리 카드에 [포춘쿠키] 버튼을 답니다. 등록 없이 그날 별자리 기준 한 줄을 본인에게만 보여 줍니다. 별자리 캐시를 쓰므로 모델 호출이 늘지 않습니다.
- 몇 번 쓴 뒤 "생일을 등록하면 나만의 아침 운세" 버튼을 보여 줍니다.

### 미룬 것

- **친구끼리 오행 궁합(`/케미`):** 서로 동의해야 하고 좋은 면만 보여 준다고 해도, 작은 서버에서는 반복되다가 일진이 추정될 수 있습니다. 사용자가 원할 때 따로 설계합니다.

## 4. 배치 API

아침 브리핑은 하루 약 2회 발송되고 정해진 시각에 나가야 하므로, 배치 API(최대 24시간, 약 절반 가격)로 얻을 수 있는 이득이 없습니다. 배치는 기억 블록 준비처럼 호출이 수천~수만 번 발생하는 대량 작업에만 적용합니다(당일 작업 대상).

## 5. 하지 않을 것

- 기억 메모, 대화 내용, 예약 알림 제목은 운세에 반영하지 않습니다. 사용자에게 "나를 감시하고 있다"는 인상을 줄 수 있고, 저장된 문장이 프롬프트 인젝션 통로가 될 수 있기 때문입니다.
- 개인 점수를 공개 순위로 만들거나 "오늘 제일 운 나쁜 사람"을 부르지 않습니다.
- 연속 출석 벌칙이나 다시 뽑기를 넣지 않습니다.
- 건강, 투자, 연애 결정을 단정하는 예언을 하지 않습니다.
- 추론량이 많은 모델이나 다단계 에이전트 방식으로 전환하지 않습니다. 비용과 지연 시간이 10배 넘게 증가하며, 다양성 문제는 P1·P6을 통해 더 적은 비용으로 해결할 수 있습니다.

## 6. 작업 순서

1. P2(실패 안내)와 P1(7일 기록) — 신뢰성과 반복 문제를 먼저 해결합니다.
2. P3(반응 버튼) — 이후 변경의 효과를 잴 수 있게 합니다.
3. P4·P9 — 7장 결정 뒤.
4. P6, P5, P7, P8.

모든 단계에서 지키는 것:

- 문구는 `locales/`(5개 언어)와 언어팩에, 조정값은 `tools.fortune.*.defaults`에 둡니다.
- 콘솔에서 켜고 끌 수 있어야 합니다(새 기능은 Action과 GUI까지).
- 테스트는 `internal/application/fortune*_test.go`와 `internal/features/fortune`에 둡니다.
