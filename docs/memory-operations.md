# 제품 기억(RAG)·대화 운영

2026-09-23 사용자 결정으로 테스트 샌드박스에서 검증한 검색 방식을 **Go 제품에 옮겨 기능으로** 켰다. parity는 알고리즘 테스트 근거이며 샌드박스가 만든 처리 산출물의 제품 재사용 허가가 아니다. 이 문서는 운영자가 기억 블록을 만들고, 준비하고, 채널에 연결하고, 확인하는 방법이다. 설계·평가 근거는 [rag/README.md](rag/README.md)와 [원문 처리 기준](RAW_DATA_POLICY.md).

## 1. 무엇이 들어갔나

| 층 | 코드 | 하는 일 |
|---|---|---|
| 원문 | `internal/memory/corpus` | raw corpus(`masamong-raw-observation/v1`) 읽기, 카카오톡 CSV, Discord 실시간 메시지. 사람 글(`human_text`)·시각 있는 글만 기억에 들어간다 |
| 조각(leaf) | `internal/memory/leaves` | 방 안에서 8개 또는 30분 공백마다 자른다. 본문 형식은 샌드박스와 바이트 단위로 같다 |
| 어휘 검색 | `internal/memory/lexical` | 한글 bigram + SQLite FTS5(bm25). 샌드박스와 점수·순서까지 같다 |
| 검색 | `internal/memory/search` | 범위 → 후보원(leaf·요약 어휘/벡터, 화자, 별칭, multi-query) → weighted RRF → auto(R0 / R2 재순위 / 복구 1회) → 점수 하한 → 인접 병합 → 원문 확장 |
| 저장 | `internal/memory/store` | 원문·조각·float16 벡터·요약·임베딩 캐시·대화 턴·비용 장부 (SQLite) |
| 엔진 | `internal/memory/engine` | 색인 적재·교체, 질의 임베딩(캐시·헤지), 배경 색인(예산 한도), 가져오기, 실시간 수집 |
| 대화 | `internal/chat` | 플래너 → 도구 → 채널 기억 → 친구 말투 답변. 프롬프트는 언어팩(`internal/lang`), 도구 메뉴는 도구 목록(`internal/tools`)에서 온다 |
| 연결 | `internal/application/memory.go`, `internal/connectors/discord` | Action(`memory.search`·`imports.start`·`memory.reindex`·`chat.respond`), Discord 응답·수집, 데몬 배경 작업 |

**현재 기본 검색에서 쓰지 않는 것:** 주장(claim), R1 규칙 가산, soft event, 한국어 키워드 의도 추정. 플래너가 없으면 중립 의도를 쓴다. 기억 검토·정정·제외와 사람 병합은 GUI/Action으로 구현되어 있다. 품질 승인은 사람 검수 gold와 별도 운영 검증으로 판단한다.

## 2. 파이썬 샌드박스와의 검색 구현 parity 증거

아래 parity 테스트는 저장소 밖의 개발용 sandbox index와 비교 dump를 읽어 검색 구현의 결과를 대조한다(API 호출 없음, 실행 조건은 각 테스트 파일 머리말). 이 테스트 전용 참조는 제품 입력이나 임베딩·요약 재사용 절차를 허가하지 않는다.

| 비교 | 결과 |
|---|---|
| 어휘 검색 (`lexical/parity_test.go`) | 질의 208개, 순위 항목 133,440개 — 문서·순서·점수 **완전 일치** |
| leaf 분할 (`leaves/parity_test.go`) | 인덱스 4개(고정 8·30분 공백) leaf 26,632개 **바이트 일치** |
| 검색 전체 (`search/parity_test.go`) | holdout 199문항 × R0·auto·R2(가짜 재순위) = 597회. 최종 근거·excerpt·포장 상태·auto 판정 **전부 일치**. 후보 순서는 1문항에서 22번째 이후 4개가 부동소수 동점으로 바뀜(결과 영향 없음) |
| 카카오 관찰 ID (`corpus/corpus_test.go`) | 원문 코퍼스 5,000건 ID 재현 일치 → CSV를 다시 넣어도 중복 없음 |
| 근거 날짜 (`search/parity_test.go`, 2026-09-30) | 인덱스 3개(Discord gap30·카카오 A·카카오 B)에서 leaf 원문 질의 80개씩 × 3모드, 근거 3,590개 **날짜 전부 일치**. 덤프는 leaf 원문 앞부분을 질의로, 그 leaf 벡터를 질의 벡터로 써서 만든다(API 호출 없음). 같은 문장이 반복된 연속 leaf 4개의 동점 순서가 한 문항에서 두 구현 간에 다름(기존 차이, 날짜와 무관) |

**동점 순서 정리 (2026-10-13)**: Discord gap30의 80문항 × 3모드에서 Windows의 fusion 순서 차이 9건은 NumPy 기본 quicksort의 완전 동점 순열 6건과 float32 BLAS 내적의 근접 순열 3건이었다. 샌드박스 dense 정렬을 안정 정렬로 맞췄으며 Go 제품의 동점 규칙·검색 동작·한국어 골든은 그대로다. 남은 역전 쌍의 코사인 차이는 Go에서 1.32×10⁻⁹, NumPy에서 2.38×10⁻⁷이다. 덤프는 원점수·RRF 트리·최종 순위 점수와 OS·아키텍처·Python/NumPy·BLAS 이름/버전을 저장한다(빌드 경로·사용자명 제외). 테스트는 **양쪽 원점수의 상대 ε=10⁻⁶ 안인 역전 쌍만** 허용한 뒤(dense 코사인에만 절대 하한 2×10⁻⁶을 더한다: float32 내적 오차는 점수 크기와 무관해 낮은 코사인·다른 BLAS에서 거짓 실패를 막는다. Windows에서 같은 항목의 양쪽 차이 최댓값은 5.5×10⁻⁷이었다) 중첩 RRF를 다시 계산해 Go 점수·순서·출처를 정확히 대조한다. RRF 자체에 ε를 적용하지 않는다. 최종 후보·풀·근거의 집합 변경, 누락·중복, ε 밖 역전, RRF 계산 오류, 포장·날짜·auto 판정 변경은 계속 실패한다. 근거 순열은 Python이 같은 근거 집합을 해당 순서로 독립 재포장한 덤프와 정확히 비교한다(앞 근거에서 이미 보인 원문 제외·예산 배분만 재계산). 새 덤프의 판정은 **fusion_diff=0, hits_diff=0**이며 차이 개수로 허용하는 상한은 없다. float64·역순 float32·32개 블록 합산 시뮬레이션도 같은 판정을 통과했다. 마지막 비트를 행마다 ±1 ULP 움직이면 hits 순서 차이 2건이 재현되며 ε 판정 뒤에는 hits_diff=0이다. Mac의 과거 차이와 같은 원인이라는 판단은 이 민감도 실험에 근거하며 Mac 실측은 하지 않았다. 점수·트리·순서별 포장 oracle가 없는 옛 덤프는 다시 만든다. 숫자만 보는 진단은 `experimental/rag-leaf-parent/parity_summary.py`를 사용한다.

**근거 날짜 규칙 (2026-09-30)**: 모델에 들어가는 `[i] 날짜=…`는 그 근거가 찾은 leaf의 마지막 원문 날짜다. 원문의 시간대 기준으로 적으며, 시간대가 없는 카카오 시각은 그대로 쓴다(샌드박스가 컴퓨터 시간대로 바꿔 새벽 대화를 하루 앞당기던 것을 Go에 맞춰 고침). 앞 근거와 겹친 원문을 빼다 보니 **자기 원문이 전부 앞 근거에 나와서 앞뒤 문맥만 남은 근거**는, 실제로 보이는 원문의 날짜(`2026-08-11` 또는 `2026-08-11~2026-09-06`)를 적는다. 표본 질의에서 근거의 약 6–8%가 여기에 해당했다. Go `search.contextOnlyDate` ↔ `engine._context_only_date`.

**시간 범위 다시 찾기 (2026-10-11)**: 플래너가 붙인 시간 범위(`recent`·`today`·날짜 등, `any`가 아닌 것) 안에서 아무것도 못 찾으면(`empty_in_allowed_scope`) 범위 없이 **한 번 더** 찾는다. 재정렬 하한이 비운 결과(`abstained`)는 다시 찾지 않는다. 두 번째 검색은 첫 재정렬 비용을 뺀 예산으로 돌고, 비용은 둘 다 센다. 턴 기록 `retrieve.time_relaxed`(재정렬 비용은 두 번의 합). 이때 답변 프롬프트에는 `recent` 표시를 넣지 않고, 근거에는 날짜가 붙어 있어 답변 모델이 "그때"를 구분한다. 두 번째 검색이 실패하면 첫 결과(빈 결과)를 그대로 쓰고 경고 로그를 남긴다. 플래너가 연도 없는 날짜를 올해로 읽거나, 몇 달 전 이야기를 "요즘"으로 묻는 경우가 실제 질문에서 흔했다(제품 실측에서 범위가 걸린 답 있는 문항 11개 중 7개가 근거를 놓침). Go `chat.Answer` ↔ 샌드박스 `_prepare_bot_turn`.

**제품 실측 (2026-10-11)**: 실제 기록(Discord 15개 방 5.6만 건, 카카오 A 7.5만 건, 카카오 B 10만 건)을 제품 경로로 적재하고 합성 문항(세트당 답 있는 40 + 기록에 없는 10, 검수 없음)으로 쟀다. 재정렬(OpenRouter Voyage) 기준 정답 근거 1위/5위 안: Discord 70/77.5%, 카카오 A 57.5/65%, 카카오 B 70/77.5%. 재정렬이 없는 공급자(OpenAI·Gemini·CometAPI)는 평균 42.5/58.3%. 대화 턴 전체로는 맞음·부분 55~70%, 정답 근거가 들어갔을 때 81~90%, 기록에 없는 질문은 30개 중 29개를 "모른다"고 답했다. 09-23 샌드박스 수치(60.7/74.4%)와 같은 수준이다. 가장 약한 곳은 카카오 A의 후보 생성(놓친 14건 중 13건이 후보 풀 밖)이다.

**R0 하한·후보 생성 진단 (2026-10-12, 설정 바꾸지 않음)**: 같은 세트·같은 색인(qwen3-embedding-8b 4096차원, 플래너 없음, top 5)으로 두 가지를 쟀다. 문항이 세트당 40개라 R@5 95% 신뢰구간이 ±13~15%p이므로 1~2문항 차이는 잡음으로 본다.

- **R0 관련성 하한 — 0 유지.** 재정렬 없이 쓸 수 있는 신호 중 범위 안 가장 가까운 leaf의 코사인(top-1)이 기록에 없는 질문을 가장 잘 갈랐다(세트 안 AUC 0.97~1.00; top-1과 10위의 차이·z점수·어휘 점수·어휘 적중 수는 0.46~0.91). 그러나 경계가 세트와 범위 크기에 따라 움직인다. 답 있는 문항의 최저 top-1은 Discord 0.582(채널 범위 53~5,808 leaf), 카카오 A 0.627, 카카오 B 0.644이고, 기록에 없는 문항의 최고는 0.668·0.680·0.653이다. R0로 맞힌 Discord 문항의 정답 leaf 코사인은 0.562까지 내려간다. top-1이 문턱보다 낮을 때만 비우면, 문턱 0.55는 기록 없음 7/30, 0.58은 17/30, 0.60은 21/30을 비우고 답 있는 R0 적중을 각각 0·0·1개 잃는다. 0.58은 Discord 최저값과 0.002 차이라 여유가 없고, 범위가 더 작은 방이나 덜 구체적인 실제 질문에서는 답 있는 질문을 비울 수 있다. 지금의 `hybrid_min_cos`(근거마다 거르는 방식)는 0.58에서 Discord R@5가 25→24, 0.62에서 25→18이 된다. 또 문턱은 임베딩 모델마다 다르고(OpenAI·Gemini 임베딩은 따로 재지 않음), 하한으로 비운 결과(`abstained`)에는 시간 범위 다시 찾기가 돌지 않는다. 답변 모델은 이미 R0에서 기록에 없는 질문 28~29/30에 "모른다"고 답한다. 그래서 하한은 켜지 않는다.
- **카카오 A 후보 생성 — 원인은 leaf 벡터 희석.** 합성 문항은 모두 메시지 **하나**에서 만들어졌다. 카카오 A의 놓친 13건 중 7건은 어휘 상위 200·벡터 상위 150 어디에도 없었고, 4건은 어휘에만 있었으며(어휘 6·34·72·165위), 2건은 벡터 상위 150에는 들었지만 풀 100에 못 들었다. 가중 RRF가 [어휘 1, 벡터 4]라서 어휘에만 걸린 후보는 출처별 보장 5개를 빼면 풀에 들어오지 못한다. 놓친 문항 쪽이 어휘 겹침(생성기 containment 평균 0.11 대 0.18)이 적고 leaf 안 화자 수가 많았다(3.4 대 2.6). ㅋ·ㅎ 같은 자모 비율 차이는 작았다(3.1% 대 2.1%). 설정만 바꿔 본 결과는 모두 잡음 수준이다. 카카오 A R2 R@5는 출처별 보장 10개에서 26→27(다른 세트 변화 없음, 비용 같음), 풀 160에서 26→27(재정렬 비용 +55%, Discord·카카오 B R@1 각 −1)이었다. RRF 가중 [1,1]·[1,2]·[1,3]·[2,3]은 R0 R@5 매크로 56.7~59.2%로 기준 58.3%와 차이가 없었다. 저장된 플래너 의도(semantic_query·key_terms·인물)를 시간 범위 없이 다시 넣으면 풀 회수율이 80.8→84.2%(카카오 A 27→30)였다. 반면 leaf를 **가장 비슷한 메시지 하나**의 코사인으로 매기면(메시지 단위 임베딩) 카카오 A 정답이 벡터 5위 안에 드는 문항이 18→25개, Discord 23→31, 카카오 B 24→25개였다(표본 1,500 leaf로 추정한 순위). 카카오 A 전체 7.5만 메시지를 임베딩해(100만 토큰, $0.011) 이 순위를 기존 후보에 RRF로 더하면 같은 풀 100개에서 회수율이 27→33~34/40(67.5→82.5~85%)으로 올랐다. 카카오 B(10.2만 메시지)에서도 34→36~37/40(85→90~92.5%)이었다. Discord 전체 확인은 하지 않았다. 메시지 단위 후보원은 메시지마다 벡터를 하나씩 저장해야 하므로(카카오 A 기준 leaf의 약 7배, 4096차원 int8이면 메모리 약 300MB) 저장 차원(Matryoshka 축소)과 비용을 정한 뒤 샌드박스와 Go에 함께 넣어야 한다. 합성 문항이 메시지 하나에서 나왔다는 점이 이 효과를 키웠을 수 있어 사람 검수 gold로 다시 확인한다.

## 3. 켜기

역할마다 공급자를 따로 둘 수 있다. 엔진은 임베딩 공급자의 어댑터로 임베딩하고, 재정렬·요약 역할이 다른 공급자면 그 공급자의 어댑터를 쓴다(`internal/application/memory.go` MemoryEngine). 재정렬 역할의 공급자에 `/rerank`가 없으면(OpenAI, Gemini) 재정렬 없이 융합 순위로 답한다(`reranker.Available`). 샌드박스 recipe와 같은 결과를 원하면 임베딩 `qwen/qwen3-embedding-8b`를 `dimensions: 4096`(샌드박스 인덱스와 같은 공간 이름)으로, 재정렬 `voyageai/rerank-2.5-lite`를 OpenRouter로 둔다. 다른 임베딩 모델(예: Gemini `gemini-embedding-2`, 3072차원)로 바꾸면 전체를 다시 색인하며, 품질은 실험실 평가로 다시 확인한다.

**임베딩 폭 (2026-10-13, [측정과 결정](rag/embedding-width-2026-10.md))**: 기본 폭은 **1024**다. 실제 기록 세 세트(메시지 5.6만~10.2만 개, 120문항)에서 재순위가 있는 권장 구성은 4096 대비 R@5가 단일 −2·흐름형 −1(잡음 범위)이었고, Go 힙은 21~27% 줄었다. 검색 속도와 임베딩 요금은 폭과 거의 무관하다(요금은 토큰 단위). 차원이 바꾸는 것은 메모리와 디스크뿐이고, 몇 년 운영에서 그 차이가 쌓인다. 재순위가 **없는** 구성(CometAPI·OpenAI·Gemini만 쓰는 경우)에서는 1024가 대화 흐름 질문을 5문항(약 4%p) 덜 찾았다. 그래서 다음처럼 정했다.

- 앞부분만 잘라 써도 되도록 학습된(Matryoshka, MRL) 모델만 자른다. 목록과 전체 폭은 `internal/providers/openai/hosts.json`의 `embed_widths`에 있다(qwen3-embedding 8b·4b·0.6b, OpenAI text-embedding-3 large·small, gemini-embedding-001·gemini-embedding-2). **목록에 없는 모델은 항상 전체 폭이다.** 학습되지 않은 모델을 자르면 검색 품질이 크게 망가진다.
- 새 설치의 기본은 1024이고, 임베딩 모델을 바꾸면(`models.select`) 목록에 있고 전체 폭이 1024보다 큰 모델은 1024로, 그 밖에는 전체 폭(0)으로 둔다. 모델 문자열이 같고 공급자만 바꾸면 운영자가 정한 폭을 유지한다. 추천 적용(`models.recommend`)도 같다: 같은 모델을 다른 공급자로 옮길 때는 폭을 덮어쓰지 않고 미리보기에도 폭 제안을 붙이지 않는다.
- 추천(`models.recommend`)은 임베딩이 실제로 바뀔 때만 폭을 제안한다(`embed_dimensions`, `embed_dimensions_reason`). 적용 후 문서의 재순위 모델이 있고 그 공급자 어댑터가 키를 갖춰 설정되어 있으며 `/rerank`를 지원해야 재순위가 있는 구성이다(런타임과 같은 판정). 재순위가 없으면 전체 폭(`no_rerank`), 512MB급 기기(hostprofile `small`)면 재순위가 없어도 1024(`small_host`), 그 밖에는 1024(`default`)다. 전체 폭이 1024 이하인 모델은 전체 폭을 쓴다. 전체 폭 제안·저장값은 **0**이며 응답의 `embed_full_width`가 실제 전체 폭을 알려 준다. 임베딩을 유지하는 미리보기·적용(`embed_kept`)에는 폭 제안 필드가 없다. 제안 폭은 운영자가 추천을 적용할 때만 쓰인다. 추천에 재순위 모델이 있고 임베딩이 바뀌면 미리보기는 재순위 선택을 해제했을 때의 제안도 `embed_width_without_rerank_pick`(`dimensions`·`reason`, 전체 폭이면 `full_width`)으로 함께 준다. 추천된 재순위 모델이 있어야 재순위를 쓸 수 있게 되는 경우가 있기 때문이며, 콘솔은 체크 상태에 맞는 쪽을 보인다. 적용은 항상 실제로 보낸 picks로 서버가 다시 계산한다. 두 제안은 미리보기 당시 문서에서만 유효하므로, 콘솔은 추천 창에서 "이 모델로"로 역할을 저장하거나 다른 곳에서 설정이 바뀌면(최초 미리보기를 받는 중에 바뀐 것도 기억했다가 최초 응답 직후) 미리보기를 다시 받고(그동안 적용을 막는다) 체크 상태는 새 미리보기가 여전히 제안하는 역할에서만 유지한다.
- 운영자가 설정에 적은 `dimensions` 값은 자동으로 바꾸지 않는다. 기기 단계마다 기본 폭을 다르게 두지도 않는다(기기를 옮길 때 재임베딩이 생기기 때문).
- 같은 모델에서 폭을 **낮추면**(`models.embed_width`, 또는 설정의 `models.embed.dimensions`) 다음 로드 때 저장된 벡터의 앞부분만 남기고 다시 정규화해 새 공간(`모델:폭:l2`)으로 옮긴다. API 호출과 비용이 없고, 준비된 블록은 ready 그대로이며 채널에 붙인 블록도 그대로 연결된다. 되돌릴 수 없으므로 다시 **넓히려면** 전부 다시 임베딩한다(`models.embed_width`가 `models.embed_reindex_required`와 예상치로 확인을 받는다). 전체 폭보다 큰 비정상 설정에서 0으로 바꿀 때도 새 전체 폭 공간을 다시 임베딩해야 하므로 확인을 받는다. 허용 폭은 0(전체 폭) 또는 전체 폭보다 작은 1024·2048이다. 선택 입력 `direction`(`lower`·`raise`)은 운영자가 승인한 방향이며, 서버가 요청 시점의 실제 방향과 다르면 아무것도 바꾸지 않고 `CONFIG_CONFLICT`(`models.embed_width_direction_changed`)로 거절한다(생략하면 검사하지 않는다). `providers.list.embed_width`는 한 번의 설정 스냅샷에서 만들어지며 `revision`·`provider`·`model`로 어느 커밋 문서의 값인지 밝힌다(콘솔은 이 객체만으로 확인 기준과 `base_revision`을 만든다). `widths`가 현재 모델의 허용값을 0 포함 목록으로 주며, `recommended`는 1024가 허용되면 1024, 아니면 0이다. `rerank_usable`은 현재 설정의 재순위 역할을 런타임·추천과 같은 판정(`engine.RerankUsable`)으로 본 값이라 콘솔이 재순위 없는 구성 안내에 그대로 쓴다. 1024보다 좁히면 메시지 벡터 공간(`모델:min(폭,1024):l2`, §15)도 바뀌어 메시지를 모두 다시 임베딩해야 하므로 Action이 받지 않는다(메시지 벡터 512 측정은 [측정 기록](rag/embedding-width-2026-10.md) §7). 4096으로 적은 설정은 전체 폭(0)과 같은 공간이다.
- 디스크에는 정한 폭으로만 저장한다. 4096 원본을 남겨 두고 메모리에서만 자르는 방식은 쓰지 않는다(보존할 운영 데이터가 없고, 다시 넓힐 때는 원문으로 다시 임베딩하면 방 하나 약 $0.05·10분 안팎이다).
- 샌드박스(`experimental/rag-leaf-parent`)는 leaf 폭 설정이 없는 **4096 기준 실험 환경**이다(`embed_dimension`은 메시지 벡터 폭에만 쓰인다). Go와 샌드박스의 parity는 4096 인덱스로 확인한다.

임베딩 모델을 바꾸면 검색은 새 모델로 임베딩된 leaf만 읽는다(leaf마다 벡터 하나, `embed_space`). 그래서 다시 색인이 끝날 때까지 기억 검색이 비고, 상태 점검은 지금 모델로 임베딩된 leaf만 세어 `pending_index`·`embed_model_changed`로 보이며 홈에 알림이 뜬다. 이미 색인된 기억이 있으면 `models.recommend`와 `models.select`(역할 `embed`)는 확인(`include_embed=true`) 없이 임베딩을 바꾸지 않는다(`models.select`는 `INVALID_INPUT`, 안정적인 메시지 키 `models.embed_reindex_required`, 다시 색인할 양 `reindex`를 돌려준다; 지금 쓰는 모델을 다시 고르는 것은 바꿈이 아니다). 콘솔 연결 화면은 이 키로 거절을 알아보고(영어 문구로 판별하지 않는다) 방·leaf·토큰 추정을 보여 주는 확인창을 띄운 뒤, 확인하면 `include_embed=true`로 다시 보낸다. 콘솔 추천 창은 임베딩을 기본으로 빼 두고, 체크하면 다시 색인할 leaf·토큰·예상 비용을 보여 주며, `reindex=true`면 적용하자마자 블록마다 준비 작업을 시작한다. `masamong models recommend --apply`는 임베딩을 그대로 두고 `embed_kept`로 알린다. 모델을 원래대로 돌리면 이전 벡터가 캐시에 남아 있어 다시 돈이 들지 않는다.

`config.yaml` (setup 기본값):

```yaml
models:                      # 역할별 모델 (provider: openrouter)
  response: {provider: openrouter, model: deepseek/deepseek-v4.1-flash}
  planner:  {provider: openrouter, model: openai/gpt-5.6-luna}
  summary:  {provider: openrouter, model: deepseek/deepseek-v4.1-flash}
  embed:    {provider: openrouter, model: qwen/qwen3-embedding-8b, dimensions: 1024}  # 2026-10-13부터 기본 1024 (§3 임베딩 폭)
  rerank:   {provider: openrouter, model: voyageai/rerank-2.5-lite}
memory:
  capture: true              # 채널 정책 capture가 켜진 방의 실시간 메시지를 저장
  embed: true                # 배경 색인(닫힌 leaf만)
  retrieve: auto             # off | auto | hybrid | rerank
  warm_query: on             # on | off. 호출 메시지를 플래너 판단 전에 임베딩 공급자로 미리 보낸다(기본 on). off면 검색이 요구할 때만 보내고 그 턴의 첫 기억 검색이 더 걸릴 수 있다. 턴마다 읽으며 재요약·재임베딩을 일으키지 않는다
  summaries: true            # leaf 요약(검색 신호). 비용의 대부분
  naive_timezone: Asia/Seoul # 카카오처럼 시간대 없는 시각을 어느 시간대로 읽을지 명시
  index_budget_usd: "1.00"   # 배경 색인 한 번의 유료 호출 한도
  turn_budget_usd: "0.05"    # 한 턴의 재순위 여유 판단
  index_interval_min: 10
  index_workers: 8           # 색인이 한 번에 보내는 임베딩·요약 요청 수(1~256, 비우면 8)
  languages: [ko]            # 기억 언어(토크나이저·조사·대명사·요약 프롬프트). 여러 개면 합친다
  agent_prompt: ""           # 모든 채널 공통 추가 지시 (선택)
instance:
  bot_names: [마사몽, masamong]   # 부르는 이름(멘션 판단·프롬프트·비인물 처리)
tools: {}                    # 도구 켜기/끄기·한도·새 도구 → tools-and-languages.md
limits:
  monthly_budget_usd: "10.00"   # 이번 달 모델 비용이 넘으면 답하지 않는다
discord:
  message_content: true      # 일반 메시지를 읽으려면 필수 (Discord 개발자 포털의 privileged intent도 켠다)
```

키는 설정에 값으로 넣지 않고 `env:`, `file:`, `keychain:` 참조로만 넘긴다. 콘솔에서 새 키를 저장하면 macOS는 Keychain, Windows는 자격 증명 관리자(`keychain:<account>`)를 쓰고, 둘 다 없는 Linux·FreeBSD에서는 data root 아래 0700 디렉터리의 0600 파일(`file:`)로 저장한다(`MASAMONG_SECRET_STORE=file`이면 어디서나 파일). 파일은 암호화되지 않고 권한(Windows는 소유자 전용 ACL)으로만 보호된다. 설정·로그·문서·백업에는 키 원문을 적지 않는다. Open-Meteo는 기본으로 키 없이 동작한다.

채널마다 (`masamong channels configure --guild_id G --id C ...` 또는 관리 콘솔):

| 키 | 값 | 뜻 |
|---|---|---|
| `respond` | `always` · `mention` · `command` · `off` | 모든 메시지에 답 / 이름·@·답장일 때만 / `!명령`만 / 안 함 |
| `capture` | `true` | 이 방 메시지를 기억으로 저장 (전역 `memory.capture`도 켜야 함) |
| `memory_use` | `on` · `off` | 답할 때 기억 검색 |
| `persona_ref` | `warm_ko` · `friendly_ko` · `friendly_en` 등 | 말투와 **답변 언어**(페르소나의 locale) |
| `rules` | 문장 | 이 채널 추가 규칙 (예: "근거 언급하지 마") |
| `memory_view.blocks` | 블록 ID 목록 | 이 채널에서 추가로 떠올릴 방 (예: 카카오방). `channels view attach` |

**범위 규칙:** 한 채널은 자기 방 + 명시적으로 붙인 블록만 검색한다. Discord 채널끼리 자동으로 합치지 않고, 다른 서버·DM 이야기를 끌어오지 않는다.

## 4. 기억 블록 만들기

관리 콘솔의 `/blocks`에서 카카오톡 CSV를 가져온다. 마법사는 다음 순서를 지킨다.

1. 파일을 올리고 형식·방·시간대·기간·중복·관찰 수를 미리 본다. 따옴표가 어긋난 행은 행 단위로 복구하며, Excel로 다시 저장한 CP949 CSV도 읽는다.
2. 블록 이름과 메모를 정하고 예상 처리 시간·비용·사용할 예산을 확인한다. 공급자가 비용을 반환하지 않으면 토큰 수×모델 단가로 계산하고, 단가를 모르면 `unknown`으로 표시한다.
3. 백그라운드 준비를 시작한다. 작업 화면에서 진행률·남은 시간·실제 비용·실패 이유를 확인하고 취소하거나 실패분을 재시도한다. 재시작 뒤에도 job과 상태를 이어서 본다.
4. 준비된 블록을 `/blocks?view=channels`에서 대상 채널에 연결한다. 채널은 자기 대화와 명시적으로 연결한 블록만 검색한다.

CLI에서도 같은 원문 계약을 사용할 수 있다.

```bash
M="masamong --data-root <dir>"
$M imports start --source raw --path <allowlisted-raw-file> --rooms "discord:G:C,discord:G:C2"
$M imports start --source kakao_csv --path <csv-file> --room kakao:friends --label "친구방" --timezone Asia/Seoul
```

같은 파일을 다시 넣어도 관찰 ID·Discord 메시지 ID로 중복을 막는다. 원문 파일은 읽기만 한다. 방 첨부 파일 Action과 `rag_staging`은 기존 API 호환을 위해 남아 있지만 새 GUI에서 자료를 관리하는 기본 경로는 블록 import다.

**금지 입력:** `docs/RAW_DATA_POLICY.md`에 따라 기존 처리 산출물과 샌드박스 벡터·요약을 제품 입력이나 fallback으로 재사용하지 않는다. `imports.start`는 원문 `raw`와 `kakao_csv`만 받는다.

## 5. 블록 준비와 색인

```bash
$M memory reindex --dry_run true            # 유료 호출 없이 할 일·예상 비용
$M memory reindex --budget_usd 0.50         # 실행 (한도에서 멈추고 다음에 이어감)
$M memory reindex --rooms kakao:friends --limit 2000
$M memory blocks prepare --source_room kakao:friends --dry_run true
$M memory blocks prepare --source_room kakao:friends --budget_usd 0.50
```

- `--dry_run` 또는 GUI 미리보기는 실제 provider를 호출하지 않고 예상 leaf·토큰·비용·시간·예산을 보여준다. 예상 시간은 이전 준비 실행에서 측정한 속도를 사용한다.
- 방의 leaf를 다시 자르고(같은 첫 메시지 → 같은 leaf ID, 본문이 바뀐 leaf만 다시 임베딩), 같은 본문의 leaf가 이미 벡터를 갖고 있거나 캐시에 있으면 무료, 없으면 임베딩 → (켜져 있으면) 요약·요약 임베딩 → 메모리 색인 교체.
- 벡터는 leaf 행에만 저장한다(float16). 임베딩 캐시는 질문 벡터와, 모델을 바꿀 때 leaf에서 밀려난 이전 공간의 벡터만 갖는다. `dimensions`를 줄이면 저장된 벡터를 잘라(Matryoshka) 새 공간으로 옮기므로 재임베딩이 없다.
- 메모리 색인은 벡터를 int8(행마다 배율 하나)로 들고 있어 float32의 1/4이고, 전문 검색 색인(FTS5)은 본문을 따로 저장하지 않는다(contentless).
- 실시간 방의 마지막 leaf는 8개가 차거나 30분 조용해질 때까지 **열려 있어** 임베딩하지 않는다. 그 사이 최근 대화는 답변 프롬프트의 `<최근채팅>`으로 보인다.
- 데몬(`masamongd`)은 시작할 때 색인을 올리고, `index_interval_min`마다 새 메시지가 들어온 방만 이어서 색인한다.
- 색인은 임베딩 묶음과 요약을 `memory.index_workers`개(기본 8, 1~256)까지 동시에 보낸다. 유료 OpenRouter는 모델별 분당 한도가 없어 8로 문제없이 돌았고, 처음 대량 색인(카카오 수십만 줄 등)을 빨리 끝낼 때는 100 이상으로 올려도 된다. 임베딩 호스트가 429를 자주 돌려주면 낮추고, 미리보기의 예상 시간도 이 값으로 계산한다. GUI에서는 블록 → 설정 → 준비 카드의 "색인 동시 요청 수"다.
- 비용은 provider가 반환한 실제 `usage.cost`를 우선한다. 응답에 비용이 없으면 모델 단가와 토큰 수로 추정하고, 단가가 없으면 `unknown`으로 남긴다. 먼저 `--dry_run`으로 확인하고, 요약 없이(`memory.summaries: false`) 시작해도 검색은 동작한다.
- 공급자 호출 일일 한도는 인스턴스 시간대 기준으로 `tool_usage`에 기록한다. 데몬 재시작이나 설정 변경으로 Registry를 다시 만들어도 그날 사용량과 남은 한도는 유지된다.

### 일괄 처리 모드 (`mode=batch`)

`memory blocks prepare`는 `--mode batch`(또는 블록 기본값 `memory blocks update --mode batch`)로 제공사의 일괄 작업에 맡길 수 있다. 값은 정가의 약 절반, 결과는 보통 몇 분~몇 시간, 길어도 약 24시간(호스트에 따라 48~96시간)이다. 일괄은 항상 백그라운드 작업으로 돈다.

- **지원**: OpenAI, Anthropic(대화·요약만), Google Gemini, OpenRouter, NanoGPT(대화만). 그 밖의 OpenAI 호환 호스트(CometAPI, OpenGateway, 직접 입력)는 일괄을 못 쓰므로 바로 실행한다. 일괄로 못 보낸 부분과 실패한 항목은 일괄이 끝난 뒤 같은 작업이 바로(live) 처리한다.
- **사전 점검**: `--dry_run true --mode batch`는 `report.estimate.total_usd`(바로)와 `batch_usd`(일괄)를 함께 준다. 둘이 같으면 호스트가 일괄을 못 받는다는 뜻이다(콘솔은 이때 선택지를 숨긴다).
- **계획 저장**: 보낸 일괄의 계획(방, 상태, 항목 수, 제공사 batch ID)은 `memory_batch_plans` 표에 방마다 한 줄 저장한다. 재시작해도 남고, 같은 방을 다시 준비하면 새로 보내지 않고 이 계획을 이어서 기다린다(`batch_resumed: true`). 블록 목록의 `waiting_batch`·`batch{items, submitted_at}`가 이 계획에서 나온다. 계획이 있는 동안 블록 상태는 `preparing`이고 그 채널의 Discord 자동 갱신은 멈춘다.
- **작업 진행**: 단계 `batch`, 라벨 `batch <pending|running> 완료/전체`, ETA 없음. 결과 JSON에 `mode`, `batch_items`, `batch_failed`, `live_items`, `batch_estimate_usd`가 들어간다.
- **취소**: `$M jobs cancel --id <작업ID>`(콘솔의 작업·블록 화면 취소도 같다)가 제공사에 열린 일괄의 취소를 요청한다. 계획은 `draining` 상태로 남고(방은 계속 잡혀 있음), 모든 그룹이 제공사에서 끝날 때까지 백그라운드에서 결과를 받아 저장한 뒤 지운다. 작업 자체는 취소로 끝난다. OpenRouter는 취소 API가 없어 끝까지 처리된다. 끝난 항목은 비용이 청구되고 저장되며 바로 처리로 넘어가지 않는다.
- **계획 세대**: 계획마다 `generation`이 있고 저장·적용·삭제는 (방, 세대) 비교 후에만 한다. 늦게 도착한 이전 실행의 적용·정리는 아무것도 바꾸지 않는다. 적용 체크포인트와 `memory_spend`는 한 트랜잭션으로 쓰므로, 적용 도중 꺼져도 비용이 두 번 잡히지 않는다.
- **전송**: batch 생성 요청은 재시도하지 않는다. 보내기 전에 계획에 `submit: pending`과 키를 저장하고, 답이 끊기면 OpenAI는 `metadata.masamong_submit`, NanoGPT는 입력 파일로 제공사 목록에서 찾는다. 찾으면 이어서 기다리고, 접수되지 않았으면 그 그룹을 버리며, 알 수 없으면 계획이 `submit_unknown`이 되어 방을 잡아 둔다(작업 코드 `BATCH_SUBMIT_UNKNOWN`). 제공사 콘솔에서 확인한 뒤 `$M memory blocks update --source_room <방> --discard_batch true`로 정리한다. 4xx 거부는 `BATCH_SUBMIT_REFUSED`로 끝나며 바로 처리하지 않는다(`ErrBatchUnsupported`일 때만 바로 처리).
- **제공사 바뀜**: 각 그룹은 보낸 제공사의 `provider{id, base_url, api}`(비밀값 없음)를 기억하고 그 제공사로 조회한다. 설정에서 그 제공사가 사라지면 `BATCH_PROVIDER_GONE`으로 바로 멈춘다. 결과 내려받기가 일시적으로 실패하면 최대 6시간 다시 시도하고, 계속 못 읽으면 `BATCH_RESULTS_UNREADABLE`로 멈추되 계획과 제공사 쪽 결과는 남겨 둔다.
- **재시작**: 기다리는 중에 서비스를 정상 종료하면 다음 시작 때 같은 작업 ID로 다시 시도한다(새 작업을 만들지 않는다). `draining` 계획은 작업 없이 백그라운드에서 이어서 받는다.

## 6. 확인

```bash
$M memory search --guild_id G --channel_id C --query "캠핑 어디 가기로 했지"   # 근거·점수·검색 경로
$M messages search --rooms kakao:friends --query "텐트" --top_k 20             # 모델 호출 없는 원문 어휘 검색
$M chat --guild_id G --channel_id C --message "요즘 누가 제일 바빠?"            # 실제 답 (저장하지 않음)
$M memory blocks list      # 방·블록·색인 상태·카운트
$M usage                   # 이번 달 모델 비용(공급자 보고 우선)
$M trace show --id <tr_…>  # 턴 기록(본문 없음: 검색 경로·시간·비용)
```

Discord에서는 `respond`에 맞는 메시지에 답하고, 답하는 동안 "입력 중" 표시를 띄운다. 멘션은 보내지 않는다(allowed mentions 없음).

관리 콘솔의 **블록(`/blocks`)** 화면은 블록 상세·예상 비용·준비 실행·취소·재시도·채널 연결을 제공하고, 설정 탭(`/blocks?view=settings`)에서 색인 recipe와 검색 모드를 관리한다. **기억 탐색(`/memory`)** 화면은 의미 검색과 원문 검색을 같은 범위에서 제공한다. `/sources`는 `/blocks`, `/index`는 설정 탭으로 리다이렉트한다. 원문 검색은 외부 provider를 호출하지 않고 `cost_usd=0`이며 플랫폼 계정 ID를 결과에 포함하지 않는다.

## 7. 말투 정책 (친구)

마사몽은 팩트체크 봇이 아니라 친구다. 답변 규칙(언어팩 `internal/lang/packs/ko.json`의 `chat.memory_rules`, 샌드박스 `bot_runtime.MEMORY_RULES`와 같음):

- 기억은 "그때 ~했잖아", "~였던 것 같은데"처럼 자연스럽게 꺼낸다. 출처·근거·"대화에 나와 있다/없다" 같은 보고 말투는 쓰지 않는다.
- 기억이 없거나 흐릿하면 대충 넘기거나 농담·추측으로 받아쳐도 된다. 조금 틀려도 된다.
- 다만 사람을 곤란하게 만드는 거짓 소문(연애·건강·돈·범죄)은 지어내지 않고, 도구 결과(날씨·시세)는 바꾸지 않는다.

웹 검색 도구(`search.*`, `web.*`, `places.*`)가 쓸 만한 결과를 돌려준 턴에는, 언어팩 `chat.tool_conclusion`(ko·en)이 답변 프롬프트의 도구 결과 블록 끝에 한 줄 붙는다: "첫 줄에 결론부터 말하고, 출처나 근거를 줄줄이 나열하지 마라. 덧붙일 말은 그 뒤에 짧게." `chat.answer_template`과 `chat.memory_rules`는 샌드박스와 같게 그대로 두고, 다른 도구 안내(`tool_assumed`·`tool_queued`·`tool_schedule`)와 같은 자리에서 도구 턴에만 렌더된다(날씨·환율 턴과 한국어 골든은 바뀌지 않는다). 답을 자르거나 다시 쓰는 후처리는 없다. 말풍선 나누기(`shape.go`)는 첫 줄·첫 문단을 첫 말풍선(트림이면 보이는 앞부분)에 그대로 두므로 결론이 먼저 보인다. 이 안내를 넣은 효과(답 길이, 첫 문장이 결론인 비율)는 라이브로 재야 한다.

## 8. 날씨·외부 provider

날씨 도구는 한국 지명과 오늘 관측에서 KMA를 먼저 사용한다. KMA가 장애이거나 키가 없으면 Open-Meteo로 자동 대체하며, 한국 지명은 KMA 격자 좌표를 Open-Meteo에 넘겨 지명 검색 오류를 피한다. 해외 지명과 최대 14일 예보(`day_offset` 0–13, 일주일 너머는 대략적이라고 답에 밝힘)는 키 없이 Open-Meteo를 사용한다. 지명을 찾을 수 없는 경우와 provider 장애는 서로 다른 오류로 표시한다. 재난 조회는 KMA를 사용하므로 별도 KMA 상태가 필요하다.

## 9. 비용·장애

- 모든 호출 비용은 `memory_spend`(일·종류별)에 쌓인다. 공급자가 `usage.cost`를 주면 그 값, 아니면 호출 종류별 추정치.
- 도구 루프의 모델 호출은 `llm_calls`에 역할 `tool_loop`로 한 라운드에 한 행씩 남고, 폴백이 답했으면 `fallback`과 실제로 답한 모델이 적힌다(로그의 "model failed, its fallback answers"와 맞춰 볼 수 있다). 턴 비용(`turn_log`의 `cost_usd`)은 이 행들의 합에 검색 서비스가 청구한 값(`tool_calls.cost_usd`)을 더한 것과 같고(테스트로 고정), 검색 비용을 알리지 않는 서비스는 0이다. `tool_calls.provider`는 검색을 답한 서비스(`web_search.order`의 id)다. 도구 안에서 따로 부르는 모델(운세 등)은 `llm_calls`에 남지만 턴 비용에는 아직 들어가지 않는다.
- 턴 상세의 `llm_calls`에는 기억 검색의 실제 임베딩·재순위 호출과 색인의 요약 호출도 기록된다. 캐시 적중은 제외하고, 색인 작업은 `job_id`와 역할별로 호출 수·토큰·비용·지연을 합산해 1,000건 또는 1분마다 한 행씩 쓴다(비정상 종료 때 잃는 것은 한 구간뿐, 종료 시 남은 집계도 쓴다). 턴도 작업도 없는 호출(콘솔 `memory.search`, 평가, 타임라인)은 장부에 남기지 않는다. 이 기록은 `memory_spend` 예산 집계에 더해지지 않는다(비용은 그쪽에 이미 있다).
- 임베딩 API 지연은 0.5~20초로 들쭉날쭉하다. 질의 임베딩은 0.8초 안에 답이 없으면 같은 요청을 한 번 더 보내 먼저 온 쪽을 쓰고, 같은 질문은 캐시에서 바로 꺼낸다.
- 재순위(R2) 실패 → R0 결과로 답한다. 기억 검색 실패 → 기억 없이 답한다. 플래너 출력이 깨지면 → 기억 검색을 하지 않는다(무작정 전체 검색 금지).

## 10. 대화 흐름 (2026-10-11, [계획](plan-memory-conversation.md) P1·P2)

바쁜 방에서도 부른 사람의 대화만 보고, 친구처럼 짧게 주고받기 위한 동작이다. 설정은 채널마다 콘솔 **방 → 대화** 카드에 있다.

| 설정 | 기본값 | 하는 일 |
|---|---|---|
| `attribution` | `on` | 답장·멘션·봇 답·같은 사람 연타·이어 말하기 간격으로 **부른 사람의 대화만** 골라 답변과 플래너에 넣는다(`internal/conversation`). 다른 대화는 빠진다. "저거 어때?"처럼 다른 줄을 가리키면 작은 분류기가 그 줄만 데려온다(실패하면 안 데려옴). `structural`은 분류기 없이 연결선만, `off`는 예전처럼 최근 줄 전부 |
| `name_call` | `addressed` | 멘션·답장 없이 이름만 나온 메시지는 분류기가 "봇에게 한 말"이라고 판단할 때만 답한다. 봇 얘기("마사몽 또 고장났네")에는 답하지 않는다. `always`는 이름만 나와도 답, `off`는 이름으로는 안 부름 |
| `conversation.follow` | `off` (실험) | 봇이 방금 답한 사람이 태그 없이 이어 말하면 구조 점수(봇이 물었나, 다른 사람이 끼었나, 다른 사람을 불렀나)로 판단한다. **꺼져 있어도 판정은 `conversation_log`에 남는다**(D7). 나중에 이 기록으로 기본값을 정한다 |
| `conversation.thread` | `offer` | 한 사람과 길게 이어지는 대화(15분 안 6턴, 긴 답, 도구 3회 이상, 다른 대화 4줄 이상 끼어듦 등 3점 이상)에 답 아래 버튼으로 스레드를 제안한다. 대화당 1회, 거절하면 30분, 채널당 시간당 2회. 여러 명이 함께 부르는 대화에는 제안하지 않는다. `auto_task`(실험)는 여러 단계 작업이면 바로 만든다 |
| `conversation.thread_follow` | `participants` | 봇이 만든 스레드에서는 태그 없이 답한다. 단, 다른 사람에게 한 말과 "ㅋㅋ"·"ok" 같은 빈 말은 넘긴다 |
| `conversation.thread_recap` | `plan` | 스레드가 끝나면(30분 조용, [그만] 버튼, "그만"·"마무리") 계획·결정이 나온 경우에만 부모 채널에 1~3줄 요약을 올린다 |
| `conversation.reply_shape` | `bubbles` | 짧은 두세 문단은 0.8~2.5초 간격으로 따로 보내고, 700자를 넘는 답은 앞부분만 보내고 [더 보기] 버튼을 단다. `trim`은 버튼만, `plain`은 예전처럼 |
| `conversation.banter` | `off` (실험) | 누군가 봇을 두고 장난스럽게 말하면(이름 분류기가 "봇에 대한 말"이고 어조가 장난) 한 줄이나 이모지로 받아친다. 진짜 불만에는 안 함. 한 줄 시간당 2, 이모지 4, 방이 빠르면(1분 6줄 이상) 이모지만, 받아친 답에 👎가 붙으면 2시간 동안 한 줄 금지. 받아치는 답은 기억 검색·도구 없이 한 줄이고, 진짜 불만이거나 받아칠 분위기가 아니면 답하지 않는다. 답이 꺼졌거나 월 예산을 다 쓴 방에서는 분류기도 부르지 않는다. 횟수와 👎 금지는 메모리라 재시작하면 풀린다. `shadow`는 했을 상황만 `conversation_log`(kind `banter`)에 남긴다 |
| `conversation.room_style` | `off` (실험) | 관리자가 승인한 "이 방 말투" 메모를 페르소나 뒤에 붙인다(아래 11절) |

- **스레드는 부모 채널의 일부다.** 페르소나·규칙·캡처·일시정지를 물려받고(스레드에 자기 설정이 있으면 그것), 기억 검색에서 부모와 스레드가 서로를 본다. 봇 스레드의 첫 메시지는 지금까지의 요지와 [그만] 버튼이고, 부모 대화의 최근 턴(최대 16개)을 씨앗으로 가져간다.
- **`always` 방**도 다른 사람에게 답장·멘션하거나 이름을 부른 메시지에는 답하지 않는다(LIVE-13).
- **페르소나 v2**(`friendly_ko_v2`, `warm_ko_v2` 등): 특성 나열 대신 행동 규칙(한 줄 질문엔 한 줄, 세 줄 이내, 상담원 말투·목록 금지, 약점 놀림 금지, 모르면 "찾아볼까?")을 쓴다. 페르소나를 고르지 않은 방의 기본값이다. v1을 고른 방은 그대로이고, v1을 숨기면 그 v2도 기본값에서 빠진다.
- **기록:** `conversation_log`(본문 없음, 보존 `turns`)에 이름 호출·이어 말하기·스레드 판정과 그 뒤 결과(`retagged` 등)가 남는다. 이어 말하기를 건너뛴 사람이 60초 안에 다시 태그하면 `retagged`, 이어 말하기에 답한 뒤 60초 안에 다시 태그하면 `retagged_after_answer`로 남아 두 비율을 견줄 수 있다. 모델 호출은 `llm_calls`, 도구 호출은 `tool_calls`(매개변수 이름만), 전송은 `delivery_ledger`에 남고, 콘솔 턴 상세에서 함께 본다. 채널 `logging.level`이 `off`면 턴 기록에 본문을 남기지 않고, `errors`면 오류 턴만 남긴다(D9).
- **투표:** 봇이 올린 Discord 투표의 표와 취소가 봇의 투표 기록에 반영되고, 투표 메시지를 지우면 투표가 닫힌다. 봇이 꺼져 있던 동안의 표는 다시 받지 못한다.
- **재시작:** 종료 시 새 답은 받지 않고 진행 중인 답은 12초 더 마무리한다. 생각하는 중이든 보내는 중이든 못 끝낸 답은 "재시작 중" 안내를 남긴다(LIVE-20). 열려 있던 봇 스레드는 재시작 시점부터 다시 조용한 시간을 센다(재시작했다고 바로 닫지 않음).
- **받은 메시지 다듬기**(`internal/connectors/discord/inbound.go`): 전달(forward)한 메시지는 원문을 `↪ forwarded: …`로, 글 없는 스티커는 `[sticker: 이름]`으로 읽어 저장과 답변에 같은 글을 쓴다(저장·동의 검사는 그대로). 스티커나 전달이 붙은 멘션은 "이름만 부른 말"로 보지 않는다. 같은 메시지 ID의 `MESSAGE_CREATE`는 5분 동안(최대 2000개) 한 번만 처리해, RESUME 때 다시 와도 두 번 저장하거나 답하지 않는다. 긴 답을 나눌 때는 2000자 제한 외에 17줄쯤에서 먼저 끊는다(나눠야 할 때만, 코드 블록 안은 피함).
- **"그만" 멈춤:** 그 사람이 그 채널에서 받고 있는 답(도구·모델 호출, 아직 안 보낸 말풍선)이 진행 중일 때 메시지 전체가 언어팩 `features.turn_stop_cues`("그만"·"멈춰"·"stop" 등, 봇 멘션과 끝의 문장부호는 무시)이면 그 답을 취소하고 ✋을 단다. 취소된 답은 "재시작 중"이나 오류 안내를 남기지 않고, 그 메시지는 새 대화 턴을 시작하지 않는다. 진행 중인 답이 없거나 다른 사람에게 한 말이면 평소 메시지다. 스레드 "그만"(`thread.stop_cues`)과 끼어들기 `quiet_cues`는 그대로 동작한다. 턴 기록의 결과는 `canceled`.
- **이름만 부른 메시지:** 분류기가 "봇에게 한 말"이라고 판단한 뒤에야 입력 중 표시를 띄운다. 봇에 대한 말일 뿐이면 턴 기록에 글을 남기지 않는다(채널 `logging.level`과 상관없이). 스레드 안의 말과 이어 말하기로 고른 말에는 이 분류기를 쓰지 않는다.
- **비공개 스레드**는 부모 채널을 물려받지 않는다. 그 안의 말이 부모 채널의 기억 검색에 섞이지 않게 하기 위해서다(따로 설정하지 않으면 기본 채널처럼 동작).
- **버튼:** [더 보기]와 스레드 제안 버튼은 한 답에 같이 달릴 수 있고, 하나를 눌러도 다른 버튼은 남는다. [더 보기] 내용은 1시간(메모리) 보관이라 그 뒤나 재시작 후에는 "다시 물어봐 달라"는 안내가 뜬다. 보내지 못한 답의 스레드 제안은 제안 횟수에 세지 않는다.
- **스레드 정리:** 부모에서 가져온 씨앗 턴은 요약 근거가 아니다. 스레드 안에서 나온 말만으로 계획 여부를 판단한다. 닫힌 스레드 행은 계정 ID를 지우고 `turns` 보존 기간 뒤 삭제된다. "그만"은 그 스레드에서 봇과 이야기하던 사람이 다른 사람에게 하지 않은 말일 때만 스레드를 닫는다.
- **끼어들기 물러서기**(자동 개입 `shadow`·`conservative` 방에서만, P5-1): 봇이 스스로 끼어든 뒤 10분 안에 누가 언어팩 `quiet_cues`("조용히 해" 등, 메시지 전체)라고 하거나 그 말에 👎를 누르면 그 방은 2시간 끼어들지 않는다(🤐 반응). 누가 봇을 부른 뒤 5분은 끼어들지 않는다(방금 대화한 중). 아무도 받지 않은(답장·반응·호출 없음) 끼어들기가 같은 종류로 세 번째부터 이어지면 그 종류의 문턱을 0.1씩, 최대 0.2 올리고, 누가 받아 주면 되돌린다. `chime_off_cues`("끼어들기 꺼")는 말한 사람 본인의 끼어들기 동의 철회다(개인정보 메뉴와 같은 `participation` 동의, ✅ 반응). 판정은 `conversation_log` 종류 `backoff`(`quiet_cue`·`chime_off`·`disliked`)로, 걸러진 후보는 `filtered`의 `muted`·`after_call`로 남는다. 상태는 메모리라 재시작하면 풀린다(동의 철회는 남음).

## 11. 방 말투 (실험, 기본 꺼짐, P5-2)

방마다 "이 방은 이렇게 말한다"는 300토큰 이내 메모를 만들어, 관리자가 승인하면 페르소나 뒤에 붙인다. 콘솔 **방 → 동작 → 방 말투** 카드, Action `room.style.show|build|preview|decide`.

1. **분석**(`room.style.build`): 최근 30일 사람 메시지(최대 600개, 동의 철회한 사람 제외)에서 길이 분포, 웃음 표기(같은 글자 반복: ㅋㅋ·ㅎㅎ·www, ㅇㅇ·ㅠㅠ 같은 자모 반복은 제외), 이모지 비율, 질문 비율, 언어 비율을 **모델 없이** 센다. `dry_run`은 이 숫자만 보여 주고 비용이 없다. 50개 미만이면 만들지 않는다.
2. **특징 뽑기:** 이름을 뺀 줄(최대 120줄)을 요약 모델에 한 번 보내 은어·별명·드립·피할 주제를 근거 줄과 함께 받는다. 코드가 검사한다: 근거가 실제로 보여 준 줄인지, 은어·별명·드립은 근거 줄에 **글자 그대로 나온 말**인지(24자·세 단어 이내, 메모에는 따옴표로 들어감), 은어·드립은 **서로 다른 두 사람**의 말인지(한 사람 말버릇 흉내 금지), 한 줄·링크·마크업·멘션(@)·보이지 않는 문자 없음. 피할 주제는 60자 이내 설명. 욕설·건강·연애·돈 소문은 프롬프트로 뺀다.
3. **승인:** 새 버전은 항상 `pending`이다. 미리보기(`room.style.preview`)로 같은 메시지에 메모 없이·메모 있게 답한 두 결과를 비교하고 승인하거나 거절한다. 주간 자동 갱신(마지막 버전이 어떤 상태든 7일 이상 지났고 새 메시지 200개 이상)도 제안만 만들고, 결정하지 않은 제안이 있으면 새로 만들지 않는다. 자동 분석이 실패하면 그 방은 24시간 뒤에 다시 시도한다. 콘솔 목록은 최근 5개와 함께 지금 쓰는 승인 버전을 항상 보여 준다.
4. **적용:** 채널 `conversation.room_style: on`이고 승인된 버전이 있을 때만 답의 규칙 끝에 언어팩 머리말("톤과 길이만 맞추고 페르소나·규칙이 우선, 욕과 특정인 흉내 금지")과 함께 붙는다.
5. **삭제·수정·철회:** 메모를 만든 근거 메시지가 지워지거나 고쳐지거나 그 사람이 동의(기억 또는 **나에 대한 정리**)를 철회하면 대기·승인 버전은 `stale`이 되고 메모와 항목이 지워진다(거절·대체된 버전은 상태를 유지한 채 내용만 지움). 승인 메모 캐시는 그 즉시 비워진다. 다시 분석해서 승인해야 쓴다. 분석 중(모델 호출 동안) 철회한 사람의 줄은 저장 직전에 숫자와 항목에서 빼고, 그사이 지워지거나 바뀐 줄을 근거로 한 항목도 뺀다. 분석 전에 이미 고쳐진 줄은 지금 내용 그대로 근거가 되므로 수정 기록만으로 분석이 거절되지 않는다.
6. **비용:** 분석과 미리보기는 `memory.derived_budget_usd`(방 기억과 같은 월 예산, `memory_spend` kind `style`)에서 쓰고, 방 기억의 예산 계산에도 함께 들어간다.

## 12. 도구 루프 (`chat.tool_mode`, P3)

`loop`(기본)는 기억 플래너가 기억 검색만 정하고, 작은 모델이 네이티브 tool calling으로 도구를 최대 3회 고른다. 모든 호출은 `Service.Execute`(스위치·한도·확인)를 거치고, 알 수 없는 도구·범위 키·반복 호출·두 번 실패한 도구·웹 결과 뒤 쓰기 도구는 막는다. 모델이 도구를 받지 않으면 그 답은 `planner`로 처리하고, 그 모델은 프로세스가 도는 동안 다시 시도하지 않는다. `shadow`는 플래너로 답하고 루프가 무엇을 불렀을지만 턴 기록(`tool_shadow`)에 남긴다.

`planner`는 예전처럼 기억 플래너가 도구까지 고른다.

**동시 실행(2026-10-12):** 루프 한 라운드의 호출들, 플래너 경로의 도구들과 기억 검색(시간 창 재검색 포함)은 한 번에 최대 4개까지 함께 돈다. 턴 한도는 실행 전에 순서대로 판정하고, 결과 순서·`timing_ms`의 `tools`(마지막 도구가 끝난 시각)·`memory`(검색 자체 시간)·비용 합산은 그대로다. 공급자별 동시 요청 상한과 돈을 쓰는 도구의 기다림은 [도구 설정 3절](tools-and-languages.md#3-켜고-끄기한도--cli)에 있다. 가짜 도구 측정: 100ms 도구 셋을 부른 라운드가 302ms → 101ms.

**시간 배치(2026-11-07):** 기억 검색은 플래너가 끝나면 루프 전체를 기다리지 않고 진행 중인 모델 호출과 유료 도구가 끝나는 대로 시작하고(`chat.tool_mode: planner`에서도 유료 도구가 끝난 뒤의 잔액을 받으므로, 유료 도구가 있는 턴은 그만큼 기다린다), 원문 질의 임베딩은 턴 시작에 미리 시작한다. 한 번에 끝나는 도구가 성공한 라운드는 다음 라운드를 묻지 않는다(`chat.loop_final`). 프롬프트 내용과 검색 결과는 그대로이고 순서만 바뀐다. 자세한 규칙은 [도구 설정 3절](tools-and-languages.md#3-켜고-끄기한도--cli)에 있다. 루프와 나란히 도는 검색이 받는 남은 예산(`RemainingUSD`)은 루프 뒤에 도는 검색이 받을 값보다 크지 않게 어림한다. 남은 라운드는 그 턴에서 본 가장 비싼 모델 호출 가격으로, 돈을 쓰는 도구가 있으면 라운드마다 0.01달러의 수수료 몫을 더해 빼고, 도는 유료 도구가 끝나기를 기다려 낸 수수료를 반영한다. `chat.tool_model`이 플래너 모델과 다르면 가격을 알 수 없어 루프 뒤에 검색한다. 미리 시작한 질의 임베딩의 비용은 그 턴의 비용과 금액 한도에 한 번 더해진다(검색이 같은 임베딩에 합류해도 다시 세지 않는다).

**견고성(2026-10-11):**

- *인자 복구:* 도구 인자가 JSON으로 읽히지 않으면 거절하기 전에 한 번만 고친다. 코드 펜스, `}`·`]` 앞 쉼표, 끝에 빠진 닫는 괄호, 값 뒤에 남은 닫는 괄호, 문자열 안의 제어 문자만 고친다. 고친 결과도 JSON 객체일 때만 받고, 루프 기록의 그 호출에 `repaired: true`를 남긴다. 열린 채 끝난 문자열, 짝이 맞지 않는 괄호, 값 뒤의 다른 글자는 짐작하지 않고 그대로 `bad_arguments`로 거절한다.
- *결과 울타리:* 루프 모델이 읽는 도구 결과는 턴마다 새로 만든 무작위 값(nonce)이 붙은 `[[tool_result …]]` 표지 사이에 넣는다. 결과 안의 제어 문자와 채팅 템플릿 특수 토큰(`<|im_start|>`, `<|endoftext|>`, `[INST]`, `<<SYS>>` 등, 대소문자 무관)은 지우고, 결과 안의 표지는 표지로 읽히지 않게 바꾼다. 답변 프롬프트의 도구 결과에서도 특수 토큰을 지운다. 지울 것이 없는 결과는 바이트 단위로 예전과 같다(골든 그대로).
- *방 기억 정리:* 방 사건 제목·근거 줄, 방 상태 주제, 사람 카드 항목은 답변 프롬프트에 넣기 직전에 같은 방식으로 정리한다. 프롬프트 블록 구분자(`[[…]]`, `</방 사건 기억>` 같은 블록 태그)와 특수 토큰은 무력화한다. 답변 언어와 기억 언어의 `instruction_cues`에 걸리는 **사람 카드 항목**은 뺀다(카드는 그 사람이 말할 때마다 들어가므로). 사건 제목·근거 줄·주제는 친구들이 한 말과 그 화제라서 빼지 않고 정리만 한다. 한국어 단서가 넓어("답해", "규칙") 평범한 대화가 빠지는 손해가 더 크기 때문이다.
- *길이 초과 재시도:* 답변 모델(대신 답하는 다른 채팅 모델 포함)이 프롬프트가 너무 길다고(`context_length`) 답하면, 대화를 절반으로, 기억 결과도 절반으로 줄이고 방 기억과 주변 채팅을 빼서 한 번만 다시 묻는다. 시스템 프롬프트, 도구 결과, 부른 사람의 메시지는 그대로 둔다. 턴 기록과 진단 기록에 `answer_retry: context_length`가 남고, 호출 기록에는 실패한 호출이 `context_length` 분류로 남는다.
- *재시도 간격:* provider HTTP 클라이언트는 선형 대신 지수 간격에 무작위 흔들림(절반 고정, 절반 무작위)을 쓴다. 기본 재시도 두 번이면 가장 긴 총 대기는 예전처럼 1.5초다. `Retry-After`는 초와 HTTP 날짜를 모두 읽고, 30초 상한은 그대로다.

2026-10-11 실키 측정(같은 키·같은 모델 추천): 도구 회귀 세트 ko 59개 `planner` 45 → `loop` 57, en 59개 49 → 59, 실사용 시나리오 52개 50 → 51(날씨 실패 두 건 해결). 루프가 날씨 지역 추정·환율 실패 시 검색 전환·리마인더 시간 채우기를 더 잘한다. 비용은 약 1.2~1.8배(턴당 0.1센트대), p50 지연은 약 1초 늘었다. 그래서 계획 P3-5 조건대로 `loop`를 기본으로 바꿨다.

## 12-1. 이미지 이해 (`chat.vision`, 2026-10-11)

사용자 결정: **부를 때 첨부된 사진만** 읽는다. 방에 올라온 사진을 배경에서 분석하지 않는다.

- **모으기(`internal/connectors/discord`):** 봇에게 한 말일 때만 모은다: 멘션, 이름 부르기, 봇에게 답장, 대화로 이어지는 `!` 명령, 후속 대화 창이 고른 메시지, 봇이 연 스레드 안의 말. `respond: always` 방에서 봇을 부르지 않은 메시지의 사진은 읽지 않는다. 그 메시지의 첨부, 그 메시지가 전달한 메시지(snapshot)의 첨부, 답장한 메시지(`ReferencedMessage`)의 첨부 순으로 PNG·JPEG·WebP·GIF만 최대 3장. 사진마다 올린 사람(`AuthorID`)을 함께 넘긴다(답장한 메시지는 그 작성자, 전달은 Discord가 원작성자를 주지 않으면 전달한 사람). 게이트웨이는 주소·형식·크기·작성자만 `ChatInput.Images`로 넘기고 내려받지 않는다. 글 없이 부르기만 한 메시지는 `ImageOnly`. 사진과 말을 따로 보낸 경우(`lookback.go`): 사진 없이 부르면 2분 안에 바로 앞에 올라온 사진을 쓴다(부른 사람 본인의 사진이면 사이에 다른 사람 말이 있어도 되고, 본인이 그 뒤에 다른 말을 했으면 쓰지 않는다. 남의 사진은 부르기 바로 위 메시지일 때만). 이때 `ImageEarlier`가 켜지고 답변에는 "바로 앞에 올라온 사진이니 메시지가 사진 얘기가 아니면 언급하지 말라"는 언어팩 `vision.earlier` 문구가 붙는다. 사진 없이 답한 부르기 뒤 45초 안에 같은 사람이 글 없이 사진만 보내면 그 부르기의 나머지로 보고 답한다. 사진 한 장은 한 턴에만 쓰이고, 게이트웨이는 채널마다 최근 메시지 12개의 첨부 주소만 2분 동안 기억한다.
- **동의:** 부른 사람이 아닌 사람이 올린 사진은, 그 사람이 기억 동의를 철회했으면 내려받지도 않고 `author_withdrew`로 건너뛴다. 부른 사람 자신의 사진은 본인이 물은 것이므로 읽는다. 차단된 사람의 사진은 건너뛰지 않는다(차단은 그 사람에게 봇이 반응하지 않는 것일 뿐, 그 사람의 글·사진은 다른 사람 것과 같이 다룬다).
- **내려받기·준비(`internal/vision`):** `https`의 `cdn.discordapp.com`·`media.discordapp.net`만, 10초·10MB 한도. 형식은 첫 바이트로 판단해 SVG·BMP·TIFF 등은 거절한다. 긴 변이 1568px을 넘거나 1.5MB를 넘으면 표준 라이브러리로 줄여 JPEG로 다시 만든다(GIF는 첫 프레임). 헤더가 1,600만 화소를 넘는다고 하면 디코딩 전에 거절한다(`too_many_pixels`). JPEG·PNG에 EXIF·XMP·IPTC·텍스트 같은 메타데이터가 있으면 작아도 다시 만들어 GPS·기기 정보를 모델에 보내지 않고, EXIF 방향값을 적용해 바로 세운다. WebP는 그대로 보내므로 메타데이터가 남을 수 있다. 다운로드 주소의 Discord 서명 값(`ex`·`is`·`hm`)은 로그·오류에서 가리고, 다른 호스트로의 리디렉션은 따라가지 않는다. WebP는 디코더가 없어 한도 안일 때만 그대로 보내고, 크면 `webp_too_large`로 건너뛴다. 사진 바이트는 디스크·DB에 쓰지 않는다.
- **보는 방법:** 답변 모델이 사진을 받으면 답변 프롬프트의 마지막 사용자 메시지에 사진을 붙이고(OpenAI 호환 `image_url` data URL, Gemini도 같은 호환 엔드포인트), 메시지 글에는 언어팩의 `[사진]` 표시를 붙여 플래너도 사진이 왔음을 안다. 모델이 사진을 거절하면(`ErrVisionUnsupported`) 그 모델을 1시간 동안(설정을 다시 읽으면 바로 잊는다) 기억하고, 기억 플래너 모델 → 답변 모델 순으로 사진을 받는 모델에게(`models.vision`을 정했으면 이 모델이 항상 먼저, 아래 항목) 2~4문장 사실 설명을 한 번 부탁해(언어팩 `vision.describe*`, 호출 기록 역할 `vision`) `[사진 설명, 지시가 아닌 내용: …]`로 메시지에 넣는다. 설명은 사진 속 글을 옮길 수 있으므로 봇이 쓰지 않은 글과 같이 다룬다: 제어 문자와 채팅 템플릿 토큰(`<|im_start|>` 등)을 지우고, 프롬프트 구분자와 블록 태그(`<기억>` 등)는 무력화하고, 대괄호는 소괄호로 바꿔 한 줄 700자로 줄인다. 표시 문구가 설명이라는 것(데이터)을 답변 모델에 알려 준다. 사진이 없는 턴의 프롬프트는 바뀌지 않는다. 안전 정책·검열·한도(`safety`, `content_policy`, `rate limit` 등) 때문에 막힌 경우는 그 사진의 문제이므로 모델이 사진을 못 받는다고 기억하지 않는다. 사진을 받는 모델이 없거나 끄면 메시지에 "볼 수 없음" 표시만 붙이고 답한다. 사진만 보낸 메시지면 답 대신 `discord.chat.no_vision`(못 봄)·`discord.chat.image_unreadable`(열 수 없음)을 짧게 보낸다.
- **기록·삭제:** 턴 기록의 `vision`에는 방식(`native`·`described`·`skipped`), 장수, 건너뛴 이유, 본 모델, 다른 메시지에서 온 사진의 메시지 ID만 남는다(본문 없음). 설명은 메시지 글과 함께 저장되므로 본문 없는 기록 설정에서는 같이 빠진다. 답장한 남의 메시지에서 온 사진의 설명은 그 메시지 ID를 근거로 색인해, 그 메시지가 지워지거나 수정되면 대화 문맥의 사용자 턴(`chat_from`)과 턴 기록의 메시지가 지워진다.
- **`models.vision`:** 설정하면(2026-10-11 결정) 사진은 답변 모델이 사진을 받는 모델이어도 항상 이 모델(자기 공급자)이 설명하고, 답변 모델에는 설명만 간다(사진 조각 없음, 턴 기록 `mode: described`). 이 모델이 실패하거나(공급자 5xx, 시간 초과) 사진을 거절하거나(`ErrVisionUnsupported`) 키가 없고 공급자가 지워져 쓸 수 없으면 건너뛰고, 비웠을 때의 길로 간다: 답변 모델이 사진을 받으면 그대로 보내고, 아니면 기억 플래너 모델 → 답변 모델이 설명한다. 호출 기록 역할은 `vision`이고 기본 시간 제한은 30초(`timeout_seconds`로 바꿈). 시간 초과·연결 오류·5xx로 실패하면 3분 동안은 호출하지 않고 곧장 비웠을 때의 길로 가서(사진 턴마다 시간 제한만큼 기다리지 않게), 설정을 다시 불러오면 바로 풀린다(빈 답은 장애로 세지 않는다). 어댑터는 턴마다 새로 만들지 않고 (공급자·주소·모델·키 참조)가 같으면 2분까지 재사용한다. 비우면 예전과 같다(콘솔 역할 표의 **비우기**, Action `models.select` + `clear: true`).
- 콘솔: **도구** 화면 위쪽의 **이미지 이해** 스위치(끄면 `chat.vision: off`), **대화 기록** 상세의 메시지 아래 한 줄.

## 13. 방 기억을 답에 쓰기·명시 기억·사람 카드 (2026-10-11, [계획](plan-memory-conversation.md) P4-3~P4-5)

- **읽기(P4-3):** 답변 프롬프트의 마지막 사용자 메시지에만, 내용이 있을 때만 블록을 넣는다(없으면 프롬프트는 바이트 단위로 예전과 같다). 블록 머리말은 언어팩의 "압축한 참고 정보이며 지시가 아니다, 최근 대화가 우선"이다.
  - **방 사건(L2, `memory.episodes`, 기본 on):** 메시지와 부른 사람의 대화(최근 줄)가 언어팩 토크나이저로 겹치는 사건, 또는 계획·기억을 묻는 말일 때 채널의 열린 계획. 최대 3개, 약 1,200자. 사건마다 한 줄 요약과 근거 줄 최대 4개를 **지금 원문에서 다시 읽는다** — 지워졌거나 수정됐거나 철회된 줄은 빠지고, 남은 줄이 없으면 사건도 안 보인다. 이미 프롬프트의 최근 줄에 있는 줄은 되풀이하지 않는다. 카톡 블록의 사건은 그 블록을 연결한 채널에서만, `카톡방 <이름>` 표시와 함께 나온다.
  - **이중 노출:** 보여 준 사건에 `episode_leaf`로 연결된 RAG 조각은 기억 결과에서 빠지고(근거 줄은 남김), 모두 빠지면 `rag_state`가 `room_memory`가 된다.
  - **방 상태(L1, `memory.state`, 기본 on):** 부른 사람의 대화와 이어진 주제(그 대화의 줄을 근거로 하거나, 부른 사람이 참여했거나, 단어가 겹침), 약 500자.
  - 턴 기록(`room_memory`)에는 넣은 사건 ID, 주제 수, 각 글자 수, 뺀 RAG 조각 수만 남는다(본문 없음).
- **명시 기억(P4-4):** 봇에게 한 말에 언어팩 `memory.explicit_cues` 단어(예: 기억해·틀려·잊어줘)가 있을 때만 작은 분류기를 따로 부른다(플래너 프롬프트는 그대로).
  - *기억해:* 말한 사람 본인의 사실을 `episode_item`(kind fact)으로, 그 메시지를 근거로 저장한다. 봇에게 하는 지시("앞으로 영어로 답해")는 분류기 판단과 언어팩 `instruction_cues` 양쪽으로 거부한다. 같은 주제(key)를 다시 말하면 예전 것을 바꾼다. 남에 대한 사실은 말한 사람의 사건 사실로만 남고 카드가 되지 않는다. 메시지를 저장하지 않는 채널에서는 근거가 없어 저장하지 않는다.
  - *틀려:* 가리킨 항목을 숨기고, 그 사건은 같은 원문에서 다시 만들지 않는다(`regen=3`).
  - *잊어줘:* 미리 보기만 하고 `/잊어줘`(Action `memory.mine.forget`)의 확인 버튼으로 지운다.
  - **`/내기억`**(`memory.mine.show`)은 이 서버에서 나를 말한 사람(`by_refs`)이나 문장 속 사람으로 가진 항목과 내 카드를, **`/잊어줘`**는 그 전부(또는 채팅에서 고른 항목)를 미리 보기 → 확인으로 지운다. 둘 다 나만 보이는 답이고, Discord에서는 언제나 누른 사람 본인 것만 다룬다. 확인 토큰은 미리 본 내용의 지문이라, 그사이 바뀌면 다시 미리 보기를 보여 준다.
- **사람 카드(P4-5, `memory.cards`, 기본 off):** 서버 × 사람마다 최대 400자. 본인이 자기 얘기로 한 사실이 서로 다른 2일, 2개 이상의 사건(중요도 3 이상)에서 나오고 근거가 모두 사람 메시지일 때만 모델 없이 올라간다. "기억해"로 저장한 본인 사실은 바로 올라간다. 항목마다 근거 ID와 대체 키가 있어 새 항목이 예전 것을 대체한다. 답에는 부른 사람의 카드(약 300자)와 대화·멘션에 나온 다른 사람 최대 2명(각 150자)만 넣는다. 카톡 화자는 카드가 없고 Discord 계정과 합치지 않는다. 답장·멘션 횟수는 사람 쌍마다 숫자만 센다(`person_relation`). 근거가 지워지거나 수정·철회되면 그 항목이 지워지고, 철회·`/잊어줘`는 카드와 관계 수를 지운다.
- **고친 것:** 자기 설정이 없는 봇 스레드도 부모 채널이 저장하면 방 기억을 만든다. 한 구간이 "그사이 줄이 바뀜"으로 두 번 연달아 거부되면 사건 없이 봉인해 매번 모델을 부르지 않는다.
- 콘솔에서는 **사람·권한 → 사람 열기 → "서버 안의 기억"**에서 서버를 고르면 그 사람의 명시 기억·카드·항목(`memory.mine.show`)을 보고, 미리 보기 → 확인(`memory.mine.forget`, 확인 토큰)으로 지운다. `memory.episodes`·`memory.state`·`memory.cards` 스위치는 **기억 블록 → 기억 방식 → 방 기억**에 있다. 방별 카드 보기는 아직 없다.

## 14. 엄격한 개인정보 옵션 (P4-7, 기본 꺼짐)

서버마다 `guilds.<서버 ID>.privacy`로 켠다([설정 레퍼런스](wiki/설정-레퍼런스.md)). 모두 기본 꺼짐이다(2026-10-11 사용자 결정: 친구 서버용이라 기본은 자유롭게 기억).

콘솔에서는 **서버·방** 화면의 서버 카드 → **엄격 개인정보 (선택)**에서 서버마다 네 스위치를 켜고 끈다(끄면 설정에서 지워져 기본값을 따른다).

- `own_card_only`: `turnCards`가 부른 사람 카드만 넣는다.
- `no_hearsay`: 방 사건을 고를 때 문장 속 사람이 말한 사람(`by_refs`)에 없는 항목을 뺀다. 남은 항목이 없거나, 사건 제목이 남은 항목을 말한 사람이 아닌 사람을 가리키면("영희 이별") 그 사건은 보이지 않는다. 방 상태의 화제도 제목·요지가 그 화제의 근거 줄을 쓴 사람이 아닌 사람을 가리키면 빼고, 화제의 사람 목록에는 근거 줄을 쓴 사람만 남긴다.
- `no_sensitive`: 카드 승격 전에 언어팩 `memory.sensitive` 분류기에 한 번에 묻고, 결과를 사실 문장의 해시로 kv에 저장한다(같은 사실은 다시 묻지 않음). 예산이 없거나 분류가 실패한 사실은 넣지 않고 다음 정리 때 다시 본다. 비용은 `memory_spend` kind `card`로 파생 예산에 들어간다. "기억해"는 명시 기억 분류기의 `sensitive`가 참이면 `sensitive`로 거절한다. **범위는 카드와 "기억해"뿐이다.** 방 사건 항목과 방 상태 화제는 분류하지 않는다(매 정리마다 분류 비용이 들기 때문). 남의 민감한 얘기를 답에서 빼려면 `no_hearsay`를 함께 켠다.
- `card_channel_only`: 카드 항목의 근거 관찰이 **모두** 이 채널의 방(스레드 포함, 카톡 블록 제외)에 있어야 쓴다. 승격된 항목은 여러 채널의 근거를 합치고 문장은 그중 어느 채널의 것일 수 있으므로, 다른 채널에서도 나온 사실은 어느 채널에서도 쓰지 않는다.
- **나에 대한 정리**(동의 범위 `profile`, 옵트아웃): 철회하면 그 사람의 카드와 관계 수를 모든 서버에서 지우고, 그 사람의 줄을 근거로 한 방 말투 버전을 `stale`로 만들며, 승격·답·방 말투 분석에서 뺀다. 철회 전에 시작한 승격 정리나 방 말투 분석이 철회 뒤에 저장되더라도, 저장 트랜잭션에서 동의를 다시 읽어 카드를 지우고 그 사람의 줄을 뺀다. 대화 기억(`memory`) 자체는 그대로다. "기억해"로 남긴 본인 사실도 대화 기억이라 남는다(`/내기억`에 보이고 `/잊어줘`로 지움). 다시 동의하면 그 사실들로 카드가 다시 만들어진다. 이 범위는 서버 옵션과 상관없이 항상 쓸 수 있다(쓰지 않으면 아무것도 바뀌지 않음).
- **끼어들기 끄기 말**("끼어들기 꺼")은 개인정보 철회 명령과 같은 흐름을 탄다: 같은 잠금으로 기록하고, 수집 모드가 그 사람에 대해 남긴 참여 기록을 지운다.


## 15. 메시지 단위 벡터 (`memory.message_vectors`, 기본 켜짐)

leaf(8줄)의 벡터는 줄들의 평균이라, 긴 leaf에 묻힌 한 줄짜리 사실("텐트는 내가 챙겨 갈게")이 질문과 멀어질 수 있다. 이 옵션은 닫힌 leaf 안의 메시지를 **하나씩 따로 임베딩**해, 질문과 가장 가까운 메시지가 속한 leaf를 후보에 더 얹는다. 화면에는 메시지가 아니라 늘 leaf와 그 문맥이 나간다. **측정 뒤 기본은 켜짐이다**(아래 "측정과 결정"). 끄려면 `memory.message_vectors: false`.

- **현재 폭 규칙 (2026-10-13)**: MRL 모델은 leaf 폭이 설정되어 있고 512 이하이면 그 폭을 쓰며, 그 밖에는 512차원을 쓴다. 명시적 leaf 전체 폭 4096도 MRL 목록에 든 모델이면 메시지 벡터는 512차원이다. `hosts.json`의 `embed_widths`에 없는 모델은 MRL로 가정하지 않고 **그 설치의 실제 leaf 벡터 폭**을 쓴다. 저장된 leaf 벡터가 있으면 그 폭이 `models.embed.dimensions` 명시 설정보다 우선한다. 단, 기존의 명시 4096→전체 폭(leaf 공간의 0) 특례는 유지하며 비-MRL 메시지는 저장된 leaf의 실제 폭을 따른다. 공간 이름은 `모델:<실제 메시지 폭>:l2`이며 `0`을 쓰지 않는다. leaf 폭을 아직 모르면 메시지 임베딩을 대기하고, 같은 색인 패스에서 leaf 임베딩 뒤 폭을 확정해 진행한다. 기존 비-MRL 명시 폭의 leaf 절단 문제는 [BACKLOG의 WIDTH](BACKLOG.md#0-남은-결정과-기술-한계)에 남긴다. 측정 전용 `Settings.MessageDims`와 평가 도구 `-msgdims`는 1..1024를 그대로 받는다.

- **측정과 결정 (2026-10-12)**: 검색만 재서 켬/끔을 비교했다(문항 세트 3개 × 답이 있는 40문항, R@5, int8 저장, `rrf_weight` 0.1). 켜기 전 → 켠 뒤.

  | 세트 | 단일 메시지 문항 R0 | 단일 메시지 R2 | 흐름(span) 문항 R0 | 흐름 R2 |
  |---|---|---|---|---|
  | Discord | 25 → 26 | 31 → 32 | 30 → 30 | 37 → 37 |
  | 카카오 A | 20 → 21 | 26 → 30 (65% → 75%), 후보 풀 27 → 32 | 23 → 22 | 25 → 26 |
  | 카카오 B | 25 → 25 | 31 → 33 | 20 → 21 | 20 → 21 |

  세트당 40문항이라 1~2문항 차이는 잡음이다. 단일 메시지 문항은 카카오 A R2에서만 뚜렷하게(+4) 좋아졌고, 흐름 문항은 잡음 안에서 그대로라 해치지 않았다. **한계**: 단일 메시지 문항의 정답(gold)은 메시지 한 줄에서 만들어서 메시지 단위 벡터에 유리하게 치우쳐 있다. 그래서 효과는 "카카오 A에서 긴 조각에 묻힌 한 줄을 건진다" 쪽으로 읽고, 다른 질문에서의 이득을 기대하지 않는다. 그래도 비용이 작고(아래) 흐름 문항을 해치지 않아 기본을 켠다.

  | 세트 | 임베딩 대상 / 전체 메시지 | 색인 비용 | 색인 시간 | DB 크기(끔 → 켬, int8) | 힙(켠 뒤) |
  |---|---|---|---|---|---|
  | Discord | 32,927 / 56,328 | $0.0080 | 9분 14초 | 118 → 167 MiB (+48) | 99.8 MB |
  | 카카오 A | 40,592 / 75,439 | $0.0072 | 10분 26초 | 176 → 235 MiB (+58) | 116.5 MB |
  | 카카오 B | 33,801 / 102,132 | $0.0053 | 9분 02초 | 237 → 285 MiB (+48) | 134.6 MB |

  임베딩은 qwen3-embedding-8b 1024차원이고 시간은 저사양 i5-6400T에서 쟀다. 힙은 끌 때보다 33~40 MB 많고, 색인 불러오기는 2~2.5초 늘었다. DB 증가는 float16+임베딩 캐시 사본이던 첫 버전(+277/+343/+285 MiB)보다 훨씬 작다.
- **업그레이드하면**: 설정에 `memory.message_vectors`가 없으면 켜짐으로 읽는다(콘솔 스위치도 켜짐). **업데이트하는 순간에는 아무것도 임베딩하지 않는다.** 메시지 벡터는 일반 색인 한 번(`IndexRooms`) 안에서, 잎·요약 임베딩이 끝난 뒤 마지막 단계로 만든다. 그 한 번이 도는 때는 셋이다. (1) **자동**: 백그라운드 색인(`memory.index_interval_min`마다, `memory.embed` 켜짐)이 도는 방은 새 메시지가 들어와 대기열에 오른 방(자동 갱신이 꺼지지 않은 블록)이다. 비-MRL leaf 폭이 섞이면 폭이 다른 활성 leaf를 가진 조용한 방도 자동 갱신이 켜져 있을 때 대기열에 올린다. 그 방의 닫힌 leaf에 있는 **기존 메시지까지 모두** 이 한 번에 대상이 되고, 한 번의 비용은 `memory.index_budget_usd`(기본 1.00)로 막힌다. 예산에 닿으면 `stopped_by=budget`으로 멈추고 방을 대기열에 되돌려 다음 번이 이어 간다(예산은 잎·요약과 같이 쓰고 메시지 벡터가 맨 끝이다). (2) **수동**: 블록 준비(`memory.blocks.prepare`, 콘솔에서 블록 준비)와 `memory reindex`(방을 주지 않으면 모든 방, `budget_usd`로 한도 지정). (3) leaf 폭 수리가 필요하지 않은 조용한 방(가져오기만 한 카톡 블록 포함)과 자동 갱신을 끈 블록의 메시지 벡터 생성은 (2)로 한다. 예산 밖의 자동 지출은 없다. 아직 만들어지지 않은 동안 검색은 이전과 같다(메시지 벡터가 없으면 `message_dense`는 일하지 않는다). 남은 일은 `runtime.doctor`의 `message_vectors`가 `pending_index` / `pending_messages:N`으로, 콘솔 색인 카드의 "임베딩 대기 메시지" 수로 보인다. 처리가 끝나면 `ready` / `messages_embedded:N`이 된다.
- **512 업그레이드 (MRL 모델)**: `모델:1024:l2` 공간의 행은 `모델:512:l2` 공간과 비교하지 않는다. 업데이트 순간 임베딩하지 않고, 다음 `IndexRooms`가 아직 새 공간에 없는 메시지를 다시 임베딩한다. 그동안 검색은 오류 없이 `message_dense` 후보만 줄어 메시지 벡터를 일부 끈 것과 같은 품질로 동작하며 leaf 검색은 계속된다. 표는 `observation_id`가 기본 키라 새 행이 기존 행을 교체하고 이력이 쌓이지 않는다. 저사양 장비에서 메시지 10만 개당 임베딩 비용은 1센트 미만, 시간은 수십 분으로 예상하고 월 임베딩 예산에 포함한다. 이전 1024 바이너리로 되돌리면 공간 이름이 달라 새로 재임베딩한다. 같은 공간에 폭이 맞지 않는 행이 있어도 `errColdMessageDims` 경로는 스트리밍을 접고 안전한 경로로 다시 읽으며 오류로 종료하지 않는다.
- **MRL 목록 밖 모델의 업그레이드**: 이전 기본 공간은 `모델:1024:l2`였고, 명시 leaf 폭이 1..1024이면 그 폭이었다. 새 공간은 `모델:<실제 leaf 폭>:l2`다. 명시 폭보다 공급자 반환이 짧아도 저장된 leaf 폭을 따른다. 숫자 폭이 달라지면 업데이트 순간에는 임베딩하지 않고 다음 `IndexRooms`에서 메시지 벡터를 다시 만든다. 같은 공간·활성 recipe의 leaf 폭이 섞이면 메시지 공간을 확정하지 않고 메시지 임베딩을 보류한다. leaf 임베딩에서 관측한 반환 폭과 길이가 다른 leaf만 재임베딩 대기로 올린다. 관측 폭이 없는 재시작 직후에는 가장 흔한 저장 폭과 다른 leaf만 선택하므로 이미 맞는 leaf를 다시 호출하지 않는다(수리 대상은 기존 폭의 캐시를 재사용하지 않는다). 자동 갱신이 켜진 조용한 방도 수리 대상으로 올리고 한 폭으로 수렴할 때까지 대기열에 남긴다. 수렴한 뒤 메시지 공간을 확정한다. 새 leaf 호출 전에는 공급자의 leaf 폭 변경을 자동으로 감지하지 않는다. 메시지 반환만 저장 leaf보다 짧으면 leaf를 다시 임베딩하지 않고, 해당 공간의 메시지 호출도 leaf 폭이 바뀔 때까지 기다린다. 재시작은 메시지 대기를 초기화하지만 균일한 leaf를 재호출하지 않는다. 대기 해제는 색인 패스에서만 하며 진단 조회는 읽기만 한다. 진단의 `message_vectors`에 `waiting:leaf_width_mixed` 또는 `waiting:provider_width_short:<반환폭>/<leaf폭>`이 나온다. 이전 폭과 실제 폭이 같으면 공간을 유지한다. 재임베딩 동안에는 옛 공간 행을 쓰지 않아 `message_dense` 후보만 줄고 leaf 검색은 계속되며, 새 행은 `observation_id` 기준으로 기존 행을 교체한다. 진단의 `pending_messages:N`은 기존 행이 있는 상태에서도 새 공간의 대기를 세고, 부분 재색인 뒤 줄어 완료하면 0이 된다.
- **디스크 정리**: 512차원 int8 행은 배율 4바이트를 더해 벡터 payload가 행당 516바이트(약 0.5KB)다. `observation_id` 행을 교체해도 SQLite 파일의 빈 페이지는 즉시 줄지 않는다. 기존 백업의 `VACUUM INTO`는 압축된 사본을 만들 뿐 원본 DB를 줄이지 않으며, 별도 실 DB VACUUM 작업은 없다.
- **끄기**: 설정에 `memory.message_vectors: false`를 둔다(콘솔 스위치를 끄면 명시적 `false`를 저장한다. `config.patch`로 키를 `unset`하면 다시 기본인 켜짐). 끄면 새 벡터를 만들지 않고 검색에도 쓰지 않으며 진단·상태에서 사라진다. 이미 저장된 벡터는 지우지 않으므로 다시 켜면 이어서 쓴다.

- **켜기·끄기**: 콘솔 블록 → 설정 탭의 "메시지 단위 검색" 스위치(설정이 없으면 켜짐으로 보인다), 또는 `memory.message_vectors: true`/`false`. 콘솔은 **다시 켜기 전에** 예상치(처리할 메시지 수, 토큰, 비용, 시간, 벡터 저장량)를 보여 주고, 확인하면 설정을 저장한 뒤 모든 블록의 준비(`memory.blocks.prepare`)를 이어서 시작한다. 저장량은 알려진 메시지 폭 × 메시지 수의 양자화 벡터 payload이며 SQLite 행·색인 메타데이터는 제외한다. 전체 폭 모델의 실제 폭을 모르면 첫 색인 후 저장량을 확인할 수 있다고 표시한다. 설정 저장이 실패하면(다른 곳에서 설정이 바뀌었거나 저장 오류) 준비를 시작하지 않고 오류를 보여 준다. 이미 준비 중인 블록, 이미 실행 중이라고 답한 블록, 시작하지 못한 블록은 따로 세어 알려 준다. 끄는 것은 명시적 `false`를 저장하는 것뿐이다(저장된 벡터는 남고, 새로 만들지도 검색에 쓰지도 않는다). 예상치는 `memory.blocks.list`에 `message_vectors_estimate=true`를 주면 설정이 꺼진 채로도 받는다. 아직 기억 조각(닫힌 leaf)에 들어가지 않은 메시지(방금 가져온 원문, 바뀐 recipe, 열린 꼬리)는 준비하기 전에는 비용을 알 수 없다. 예상치는 이를 `unprepared`(의미 있는 메시지 수의 상한)로 따로 알리고, 콘솔은 "최대 N개 더, 위 수치에 들어 있지 않음"이라고 적는다. 준비된 것이 하나도 없으면 0을 보여 주지 않고 비용을 계산할 수 없다고만 한다. `memory reindex --dry_run true`의 예상에는 켜져 있을 때 `message_embeds`·`message_tokens`가 비용·시간에 포함된다.
- **대상**: 활성 recipe의 닫힌 leaf에 있는 메시지 중 **의미 있는 글자가 6자 이상**인 것만. "의미 있는 글자"는 **유니코드 글자(L*)와 숫자(N*)뿐**이고 한글 호환 자모(U+3131–318E: ㅋㅋ·ㅠㅠ·ㅇㅇ)는 뺀다. 미배정·사용자 정의 영역·기호·이모지·결합 문자·서식 문자(변이 선택자, ZWJ, 키캡)·문장부호·공백은 세지 않는다. Go와 파이썬의 유니코드 버전이 달라 한쪽에서만 글자로 배정된 새 코드 포인트는 두 구현이 다르게 셀 수 있다(드묾, 그 메시지에 벡터가 생기는지만 달라진다). 짧은 줄("ㅋㅋㅋ", "ㅇㅇ", "👍")이 대화의 대부분이라 이것만으로 비용·저장을 크게 줄인다. 규칙에는 언어팩 단어 목록이 없고, 샌드박스(`message_vectors.py`)와 같으며 `internal/memory/search/testdata/message_dense/`가 둘을 함께 고정한다. 열린 꼬리 leaf는 닫힐 때까지 기다린다.
- **메시지 → leaf 투영**: 한 메시지가 여러 leaf에 들어가는 recipe(overlap)에서는 메시지를 한 번만 임베딩하고, 그 메시지를 **포함한 모든 leaf**로 투영한다(leaf의 점수 = 그 leaf 메시지들의 최고 코사인). 행 순서는 leaf 순서, 그 안에서 메시지 순서이며 동점은 이 순서로 정한다(관찰 ID·시간 순서가 아니다). Go(`search.ProjectMessages`)와 샌드박스(`project_message_rows`)가 같고 공유 픽스처(`projection`)가 둘을 함께 고정한다.
- **임베딩 텍스트**: `화자 라벨: 내용`. 질문이 화자를 말하는 일이 많아서다. MRL 모델은 `models.embed.dimensions`가 1..512로 설정되면 그 차원으로, 그 밖에는 512차원으로 자르고 다시 정규화한다(Matryoshka). MRL 목록 밖 모델은 설치의 leaf 폭과 같게 맞춘다. 공간 이름은 `모델:메시지폭:l2`다. 모델 또는 실제 저장 차원이 바뀌면 새 공간이라 다시 임베딩한다. 샌드박스도 Go와 같은 `internal/providers/openai/hosts.json`의 `embed_widths`를 읽고 모델명 앞뒤 공백·대소문자·마지막 `/` 앞 접두사·`:variant`를 같은 규칙으로 정규화한다. 설정에 `embed_truncatable` 키가 있으면 그 값이 우선하고, 없으면 모델명으로 판정하며 미등록 모델을 MRL로 취급하지 않는다. 비-MRL 메시지 폭과 지문에는 `leaf_vecs.npy`의 실제 폭을 넣고, leaf 벡터가 없으면 메시지를 임베딩하지 않는다. 측정 오버라이드는 `message_dims`다.
- **저장·메모리**: MRL 512차원이면 임베딩된 메시지당 디스크·메모리 벡터 데이터 약 0.5KB다(정확히 int8 성분 + float32 배율 하나, 516바이트; SQLite 행·색인 메타데이터 제외). 전체 폭 MRL은 해당 leaf 폭이 512 이하일 때 그 폭을 쓰며, MRL이 아닌 모델은 설치의 실제 저장 leaf 폭을 쓰므로 더 많이 들 수 있다. 디스크에는 `memory_message_vectors`에 저장하고 메모리의 `MsgVecs`와 같은 양자화라 불러와도 값이 그대로여서 검색 결과가 같다. 임베딩 캐시(`memory_embed_cache`)에는 메시지 벡터를 쓰지 않는다(이 표가 메시지·본문 해시로 키가 잡힌 캐시를 겸한다). 의미 있는 글자가 6자 미만인 메시지는 임베딩하지 않으므로 전체 메시지 수가 아니라 대상 수로 계산한다(실데이터 대상 비율: 카카오 A 약 54%, 디스코드 약 58%, 카카오 B 약 33%). 처음 버전이 쓴 float16 행(`fmt=0`, 행당 약 2KB)은 그대로 읽어 불러올 때 같은 int8로 양자화하며(다시 임베딩하지 않는다), 다시 저장되는 행부터 새 형식이 된다. 그 버전이 임베딩 캐시에 남긴 `kind='message'` 사본은 열 때 한 번 지운다. 재구축 때는 DB의 현재 메시지와 벡터 메타데이터(공간·본문 해시·라벨·저장 시각·형식·길이)를 다시 확인한다. 모두 같은 행은 이전 색인의 불변 int8 행을 공유하고, 새로 생기거나 바뀐 행의 BLOB만 500건 단위로 읽는다. 삭제·수정으로 사라진 벡터나 현재 화자 라벨과 다른 벡터는 새 색인의 검색 대상에 넣지 않는다. 같은 텍스트를 다시 임베딩해도 저장 시각이 바뀌면 새 바이트를 읽는다.
- **무효화**: 메시지 수정·삭제, 계정 철회, 관찰 일괄 삭제, 방 삭제는 해당 메시지의 벡터를 함께 지운다(벡터가 지워진 글을 되살리지 못하게, 저장도 메시지의 현재 본문·해시를 확인한다. 임베딩 캐시에 사본이 없으므로 따로 지울 것이 없다). 화자 라벨이 바뀐 메시지는 벡터에 라벨을 함께 적어 두었다가 다음 준비 때 다시 임베딩한다(라벨이 들어간 텍스트가 달라지므로 비용이 든다). 라벨 열이 생기기 전에 만든 벡터(빈 라벨)는 바뀐 것으로 보지 않는다. 업그레이드가 기록 전체를 다시 임베딩하지 않게 하기 위해서다. 로드 때 DB의 현재 메시지와 대조해(벡터에 적어 둔 화자 라벨 ≠ 현재 라벨, 삭제됨) 맞지 않는 행은 쓰지 않는다. 실행 중인 엔진이 갖고 있는 메시지 목록이 아니라 DB를 읽으므로, 같은 엔진에서 라벨이 바뀐 뒤에도 다음 준비 → 재로드에서 새 벡터가 쓰인다.
- **검색**: 설정이 켜지고 벡터가 있을 때만 `message_dense` 후보가 최종 융합 뒤에 한 줄 더 합쳐진다(`retrieval.message_dense`: `limit` 200 leaf, `rrf_weight` 0.1(실데이터에서 1.0은 리랭커 없이 흐름(span) 질문을 세트마다 3~5문항 떨어뜨렸고 0.1은 ±1 안에 두면서 리랭크 뒤의 이득을 유지했다. 설정으로 바꿀 수 있다), 복구 시도에서는 `limit_scale`을 곱함). 질문은 leaf 공간에서 한 번만 임베딩하고, MRL 메시지 행이 더 좁을 때만 앞 차원으로 잘라 다시 정규화한다. 기존 출처의 run과 보장 슬롯 정책(예약 슬롯은 다른 후보가 가져간 뒤 남은 만큼만 `message_dense`가 가져감)은 그대로지만, 두 번째 RRF가 기존 후보 사이의 상대 순위도 바꾸므로 **최종 순위는 달라진다**. **꺼짐(OFF) = 검색 출력·trace는 켜기 전과 같고, 스키마 마이그레이션과 삭제용 DELETE가 추가된다.** 구체적으로 `Store.Open`이 테이블·인덱스 DDL과 label 컬럼 확인을 한 번 수행하고(설계상 필요한 마이그레이션), 메시지 수정·삭제·방 삭제 때 벡터 DELETE를 설정과 상관없이 실행한다(저렴하고, 켰다 끈 뒤에도 지움이 빠지지 않게 한다). 그 밖의 색인·검색·상태 경로(`MessageSpace` 계산, 상태 조회)는 켜져 있거나 예상치를 요청했을 때만 일한다. 켜면 검색 추적에 `message_dense: {messages_scored, leaves, ms, dims}`가 나온다.
- **확인**: 진단(`runtime.doctor`)에 `message_vectors`(켜져 있고 기억을 쓸 수 있을 때만 나온다. 기본은 켜짐): `pending_messages:N` 또는 `messages_embedded:N`과 `message_dims`를 표시한다. 폭 미확정이면 `message_dims`를 생략하고 `waiting:leaf_width_unknown` 등 대기 코드를 표시하며, 조회 오류도 드라이버 문장 없이 상태 코드로만 남긴다. `memory.blocks.list`의 `memory.message_vectors`에 `{enabled, space, dimensions, stored, pending}`.
- **샌드박스**: `experimental/rag-leaf-parent`가 같은 규칙을 가진다. `config.json`의 `retrieval.message_dense.enabled: true`로 켜면 `prepare.py`가 `message_vecs.npy`·`message_leaf.npy`를 추가로 만들고(유료 임베딩 호출), 꺼져 있으면 아무것도 읽거나 만들지 않는다. **샌드박스의 기본은 꺼짐 그대로다**(자체 `config.json`을 쓰는 실험 도구이기 때문). 제품은 이 기능을 기본으로 켜므로 샌드박스에서 같은 조건으로 재려면 `retrieval.message_dense.enabled: true`를 직접 켜야 한다. 샌드박스는 제품의 MRL 모델 목록을 모를 수 있어 설정 `embed_truncatable`(기본 `false`)로 판정값을 전달한다. 측정용 `message_dims`는 1..1024다. `test_message_vectors.py`가 폭 규칙과 공통 픽스처를 재생한다. 산출물(`message_vecs.npy`는 int8 행 + `message_scale.npy`의 행별 float32 배율로 제품과 같은 양자화이며 이전 float16 산출물도 읽는다, `message_leaf.npy`)과 중단된 준비의 체크포인트는 지문(임베딩 모델, 유효 차원, 관찰별 본문 해시(정규 순서), 관찰→leaf 투영 전체)을 함께 기록하고, 로더는 지문이 현재 인덱스와 같을 때만 읽는다(경계·모델·차원·본문이 바뀐 낡은 산출물은 무시). 지문에 recipe 이름은 넣지 않는다. recipe나 분할 설정을 바꿨어도 임베딩 텍스트와 관찰→leaf 투영이 그대로면 벡터를 다시 쓰며, 벡터는 그 둘에만 달려 있어 안전하다. 이전 float16 산출물은 읽을 때 제품과 같은 방식(float16→float32→int8+배율)으로 양자화해 점수를 매긴다. 이미 준비된 leaf 인덱스에 메시지 벡터만 추가하는 경우에도 비용은 일반 준비와 같은 마무리를 거쳐 원장에 한 번 반영되고 `meta.json`의 `prepare_cost_usd`가 갱신된다.


## 16. 저사양 기기의 재구축과 자동 메모리 한도

leaf·요약·메시지 벡터의 변경 없는 int8 행은 이전 색인과 불변 메모리를 공유한다. 새 행은 각각 독립된 작은 할당을 가지므로 지워진 행 때문에 큰 옛 행렬 전체가 남지 않는다. 새 색인을 만드는 중에도 이전 색인을 쓰는 검색은 같은 행과 배율을 읽는다. 점수 합산, 메시지→leaf 투영 순서, 동점 처리 규칙은 그대로다. 최초 로드에서는 leaf·요약 float16 BLOB을 최대 500 leaf씩 순차 읽고 즉시 양자화한다. 저장된 해시 ID별 무작위 페이지 읽기가 첫 로드 프로파일의 주된 비용이었기 때문이다. 양자화는 `runtime.GOMAXPROCS(0)`만큼 나누되 1코어에서는 goroutine·대기열 없이 직접 처리하고, 최종 행은 원래 leaf 순서로 붙인다. 메시지 벡터도 첫 로드에서는 본문과의 유효성 join을 한 번만 읽고 즉시 소유한 int8 행으로 변환하여, 메타데이터 재읽기와 BLOB의 추가 복사를 피한다. 저장된 차원이 섞여 있으면 기존 정렬된 경로로 돌아가 최초 유효 메시지의 차원을 고르는 규칙까지 유지한다. hot 재구축은 이전처럼 변경된 행만 읽는다.

메시지 배열은 방별 개수로 미리 확보하고 corpus와 같은 문자열 키로 제자리 정렬하여 전체 기록의 중복 복사를 줄였다. 관찰 ID가 유일해 정렬 키가 전순서이므로 안정 정렬 비용을 줄여도 순서가 같다. cold·hot 양자화는 같은 행 변환 함수를 쓰며, cold 행 조회 맵은 행렬에 붙인 뒤 FTS Build 전에 해제해 메모리 피크를 줄인다. FTS n-gram은 토큰마다 문자열을 만들지 않고 최종 문자열에 바로 쓴다. FTS 자체는 계속 메모리에서 재구축한다. 초기 CPU 프로파일에서 FTS는 약 1초(4%)였고 파일 읽기는 약 71%였으므로, 영구 FTS 사본과 그 무효화·삭제 경로를 추가하는 대신 먼저 실제 병목을 줄였다. leaf 본문·관찰 ID와 FTS 재구축 비용은 여전히 남아 있다.

Unique observation IDs make message sorting a total order, so an unstable in-place sort preserves corpus parity. Cold and hot loads share one quantization function, and the cold row lookup map is released before FTS Build to reduce peak memory.

### 큰 방의 leaf 동기화

기존 동기화는 새 메시지가 몇 개뿐이어도 방의 모든 메시지를 읽고 정렬·절단했다. 임베딩은 바뀐 leaf에만 요청했지만, SD 카드 읽기와 Go 할당은 방 전체 크기만큼 발생했다. 이제 SQLite에는 완료된 절단의 체크포인트를 저장하고, 삽입 트랜잭션에서 새 메시지의 최소 정렬 키(`parsed_time`, 원래 방, 관찰 ID)와 개수를 함께 기록한다. 기존 마지막 메시지 뒤에만 추가됐음이 확인되면 마지막 두 leaf의 첫 메시지부터 인덱스로 찾아 읽고, 앞 leaf는 읽거나 고치지 않는다. 같은 `SlicePerRoom`을 실제 leaf 경계에서 다시 실행하므로 고정 창·overlap·idle gap과 첫 관찰 ID 기반 leaf ID가 전체 재절단과 같다. 열린 tail뿐 아니라 idle로 닫혔거나 Kakao 내보내기에서 닫힌 tail도 포함해, 이후 추가와 시간 경과를 같은 규칙으로 처리한다. 방 전체 메시지·leaf·닫힌 leaf 개수도 그대로 보고한다.

<!-- WHY: full-cut provenance refresh, rollback safety and optional startup costs affect operations too. -->
첫 동기화, 늦은 삽입(같은 시각의 정렬 순서가 앞서는 경우 포함), 편집·삭제, recipe·본문 prefix·방에 선언된 시간대 변경, 중단되거나 불확실한 체크포인트는 전체를 다시 자른다. 쓰기 배치 전에 체크포인트를 무효화하고 모든 배치가 성공한 뒤 방 revision을 재확인하는 트랜잭션에서만 복구하므로, 정전·실패·동시 변경 뒤에 부분 결과를 정상 prefix로 재사용하지 않는다. 본문 해시가 같아도 관찰 ID와 마지막 시각은 갱신해 같은 문장의 출처가 바뀐 경우를 놓치지 않는다. 이는 증분 경로뿐 아니라 전체 절단에서도 오래된 출처를 바로잡는 의도적인 정확성 수정이며, 임베딩 본문이 같으면 저장 벡터는 유지한다. TiDB는 문자열 collation이 corpus의 바이트 순서와 같다고 보장할 수 없어 전체 절단을 유지한다. 새 설정이나 대화 내용 로그는 없다.

Both full and incremental cuts intentionally refresh observation IDs and end time for equal body hashes, fixing stale provenance while retaining vectors for unchanged embedding text. First syncs, late arrivals, edits/deletions, recipe/rendering or declared timezone changes, and uncertain checkpoints require full cuts. Checkpoints become valid only after all batches commit and the room revision is rechecked; TiDB retains full cuts because corpus byte-order parity is not guaranteed by its collation.

구 바이너리로 롤백해 방 revision이 바뀌면 새 바이너리의 첫 동기화는 전체 절단으로 복구한다. 새 쓰기는 직전 방 revision부터 `observed_revision`을 같은 트랜잭션에서 이어 갱신하므로, 구 바이너리의 변경 뒤에 새 캡처가 있어도 빠진 변경을 숨기지 않는다. 구 leaf 동기화는 revision을 올리지 않으므로 DB 가드가 leaf 구조와 active recipe 변경도 체크포인트를 무효화한다. 구 바이너리가 recipe·본문 prefix를 바꿨다가 되돌려도 이 무효화는 남는다. 벡터·요약만 저장하는 작업은 재절단을 강제하지 않는다.

After an older binary changes a room revision, the next new-binary sync performs a full cut. Instrumented writes extend `observed_revision` only from the previous room revision in the same transaction, so a later capture cannot hide a rollback gap. Older leaf syncs do not advance revisions; database guards also invalidate checkpoints on leaf structure or active recipe writes, even when a recipe or WithPrefix change is later reversed. Vector and summary updates alone do not invalidate the cut.

새 관찰 인덱스는 만들지 않는다. 기존 `idx_memory_obs_room_live(room, deleted_at, parsed_time, actor_label)`에서 restart 시각 이상의 범위를 찾아 정확한 `(parsed_time, source_room, observation_id)` 경계와 순서를 작은 꼬리에만 적용한다. 미출시 개발 버전에서 만든 `idx_memory_obs_leaf_tail`은 마이그레이션에서 제거하므로, 메시지 수에 비례하는 인덱스 생성·추가 디스크 비용과 시작 지연이 없다. 작은 체크포인트 테이블·가드 생성이 실패하면 Open에서 한 번 경고하고 해당 Store의 증분 경로를 끈 채 전체 절단을 계속 사용한다. 호출자가 넘기는 시간대가 Resync와 인덱스 pass 사이에 달라도 앞 leaf는 위치로 닫혀 있고 마지막 두 leaf의 idle closure는 매번 다시 계산하므로 추가 전체 절단이 필요 없다. 방에 선언된 시간대 변경은 계속 전체 절단한다.

No new observation index is created: the existing room_live index seeks the restart time, then SQL filters and orders the small tail by the exact corpus tuple. Migration drops the unreleased development leaf_tail index, avoiding history-sized index construction, disk overhead and startup delay. Failure to create the small checkpoint schema logs one warning at Open and disables incremental sync for that Store while full cuts remain available. Different caller timezones between Resync and index passes safely reuse the positional prefix and recalculate tail closure; changing the room's declared timezone still requires a full cut.

`masamongd`는 `GOMEMLIMIT`이 없으면 프로세스가 사용할 수 있는 메모리의 60%를 Go 소프트 메모리 한도로 정한다. Linux는 해당 프로세스의 cgroup v2 `memory.max`(부모의 더 작은 한도 포함), cgroup v1 `memory.limit_in_bytes`, `/proc/meminfo`의 `MemTotal` 순으로 확인한다. Windows는 `GlobalMemoryStatusEx`, macOS·FreeBSD는 `sysctl hw.memsize`·`hw.physmem`을 사용한다. 감지할 수 없는 플랫폼은 기존 한도를 유지한다. 512 MiB에서는 약 307 MiB, 1 GiB에서는 약 614 MiB다. 이미 설정된 `GOMEMLIMIT`은 바꾸지 않는다.

적용한 바이트 수·출처·자동 적용 여부를 시작 로그에 한 번 기록하고, 진단(`runtime.doctor`)의 `go_memory_limit`에 같은 정보를 넣는다. 콘솔의 로그 → 진단에 "Go 메모리 소프트 한도"로 표시된다. 새 사용자 설정은 없다. 이 한도는 GC를 조절하는 소프트 한도이며 SQLite·FTS의 Go 힙 밖 할당을 제한하지 않으므로 40%를 남긴다. 메모리가 작은 기기는 실제 작업 집합도 함께 확인한다. 임베딩 폭은 2026-10-13부터 기본 1024다(§3 임베딩 폭). 예전 설정에 `dimensions: 4096`이 적혀 있으면 콘솔에서 1024로 낮출 수 있다(비용 없음).

### 기기 성능 단계

저사양 보강은 1코어·512MB에 맞춰 읽기 연결, SQLite 페이지 캐시, 사진 디코드, 운세 생성, 대기 메시지 재집계를 작게 잡았다. 그 값을 4코어·수 GB 서버에도 그대로 두면, 여유가 있어도 같은 한도로만 돈다. `masamongd`는 저장소를 열기 전에 코어 수(`GOMAXPROCS`. Go 1.25부터 cgroup CPU 쿼터를 반영한다)와 프로세스가 쓸 수 있는 메모리(소프트 한도와 같은 `internal/memlimit` 감지)를 보고 단계를 고른다. 새 사용자 설정은 없다. 운영자는 환경 변수 `MASAMONG_PERF=small|medium|large`로만 단계를 바꿀 수 있다. 다른 값이면 자동 선택을 유지하고, 값 자체는 로그에 남기지 않은 채 경고를 한 번 남긴다.

| 단계 | 조건 | 읽기 연결 | SQLite 캐시 | 사진 디코드 | 운세 동시 생성 | 대기 수 재집계 간격 |
|---|---|---:|---:|---:|---:|---:|
| small | 코어 ≤ 1, 또는 메모리를 알고 1.5 GiB 미만 | 2 | 2000 KiB | 1 | 1 | 2분 |
| medium | 그 사이. 메모리를 모르면 large가 되지 않음 | 4 | 2000 KiB | 1 | 2 | 1분 |
| large | 코어 ≥ 4 이고 메모리 ≥ 6 GiB | min(2×코어, 12) | 32768 KiB | 2 | 4 | 20초 |

**왜 이렇게 나뉘나.** 512MB에서는 사진 한 장의 디코드가 125–170MB라 두 장이 겹치면 메모리가 가득 찬다. 읽기 연결과 페이지 캐시를 키우면 그 메모리를 SQLite가 Go 힙 밖에서 잡는다. 운세 생성과 대기 수 집계(10만 개·1코어에서 약 5초)는 하나뿐인 코어를 붙잡는다. 6GiB·4코어 이상에서는 그 여유가 있으므로 읽기 풀과 캐시를 늘리고, 디코드는 두 장까지만 겹치게 한다. medium은 오늘까지의 고정 값이다. SQLite `cache_size`는 원래 지정하지 않아 엔진 기본인 -2000(2000 KiB)이다. 단계 표의 small 2048 KiB·medium 8192 KiB는 그 기본과 달라, 보통 기기와 작은 기기가 오늘보다 캐시를 더 쓰지 않도록 2000 KiB를 유지했다. 큰 서버만 연결마다 32 MiB다. 캐시는 연결마다 따로라, large의 읽기 연결이 12개면 페이지 캐시만 최대 약 416 MiB(쓰기 1 + 읽기 12)까지 올라간다. 쓰기 연결은 여전히 하나다. API·공급자 동시성, 보존·동기 배치 크기는 기기가 아니라 공급자 한도와 데이터 양에 매여 그대로다.

시작 로그(`tier`, `cpus`, `memory_mib`, `source`)와 진단 `host_profile`에 단계, 코어 수, 메모리 MiB, 출처(`auto` 또는 `env`)가 나온다. 메모리를 모르면 `unknown`이다. 콘솔의 로그 → 진단에는 "기기 성능 단계"로 보인다. 데몬이 꺼져 있어 `masamong` CLI가 인스턴스를 직접 여는 명령(예: `masamong -i doctor`)도 같은 감지를 적용한다. 저장소만 여는 다른 프로세스(테스트, 라이브러리)는 medium을 유지한다. 빌드 머신이 크다고 테스트의 풀과 캐시가 바뀌면 안 되기 때문이다.

### Host performance tier

The low-spec work sized the read pool, the SQLite page cache, picture decode, fortune generation and the pending-message recount for a 1-core, 512 MB host. Leaving those numbers on a 4-core, multi-gigabyte server leaves capacity unused. Before it opens the store, `masamongd` picks a tier from the CPU quota (`GOMAXPROCS`; Go 1.25 and later honor a cgroup CPU quota) and the memory the process may use (the same `internal/memlimit` detection as the soft limit). There is no new user setting. An operator can force the tier with `MASAMONG_PERF=small|medium|large`. Any other value keeps the automatic tier and logs one warning; the value itself is not logged.

| Tier | When | Read connections | SQLite cache | Picture decodes | Fortune generations at once | Pending-count gap |
|---|---|---:|---:|---:|---:|---:|
| small | 1 core or fewer, or a known ceiling under 1.5 GiB | 2 | 2000 KiB | 1 | 1 | 2 min |
| medium | Anything in between. Unknown memory is never large | 4 | 2000 KiB | 1 | 2 | 1 min |
| large | 4+ cores and at least 6 GiB | min(2×CPUs, 12) | 32768 KiB | 2 | 4 | 20 s |

**Why the split.** On 512 MB, decoding one photo takes 125–170 MB, so two at once fill the machine. A larger read pool and page cache is memory SQLite allocates outside the Go heap. Fortune calls and the pending-message recount (about 5 seconds at 100,000 messages on one core) occupy the only core. At 6 GiB and 4 cores there is room to raise the read pool and the cache, and to overlap two decodes but not more. Medium is the fixed behavior from before tiers. `cache_size` was unset, so SQLite's default of -2000 (2000 KiB) still applies. The tier sheet's 2048 KiB for small and 8192 KiB for medium are not that default; keeping 2000 KiB means a small or typical host does not spend more cache RAM than today. Only a large server uses 32 MiB per connection. The cache is per connection, so 12 readers plus the writer can hold about 416 MiB of page cache. The writer connection stays one. API and provider concurrency, and retention and sync batch sizes, follow provider limits and data size, not the machine.

The startup log (`tier`, `cpus`, `memory_mib`, `source`) and the `host_profile` doctor row show the tier, the CPU count, the memory in MiB and the source (`auto` or `env`). Unknown memory is `unknown`. The console shows it under Logs → Doctor as "Host performance tier". A `masamong` CLI command that opens the instance itself because no daemon runs (for example `masamong -i doctor`) applies the same detection. Any other process that opens the store (tests, library users) stays on medium, so a large build machine does not change their pools and caches.

콘솔 집계 `Counts`·`SpaceCounts`와 관련 읽기는 단일 writer 대신 읽기 풀을 쓴다. 대기 메시지 수는 목록과 같은 자격 판정을 사용하되 정렬과 본문·화자 열의 그룹화를 생략한다. 의미 있는 유니코드 글자·숫자 6자 규칙과 overlap에서의 메시지 중복 제거는 그대로다. 그래도 대기 수는 닫힌 leaf의 모든 메시지 본문을 읽어야 해서(짧은 메시지는 벡터가 생기지 않아 매번 다시 나온다) 10만 개·1코어에서 약 5초다. 그래서 콘솔(`memory.blocks.list`)과 진단(`runtime.doctor`, Discord `/status`)은 한 번에 하나만 도는 집계를 함께 쓴다. 집계는 서비스 수명을 따르는 백그라운드에서 돌고, 요청은 자기 ctx로 기다리기만 한다(탭을 닫아도 다른 요청이 기다리는 집계는 계속된다). 콘솔은 그 공간을 처음 볼 때만 기다리고 이후에는 마지막 값을 바로 보여 준다. 진단은 다시 세야 할 때 결과를 기다린다. 공간·recipe·색인 로드 시각·저장 벡터 수·살아 있는 메시지 수가 바뀌었거나 마지막 성공 뒤 10분이 지나면 다시 세는데, 앞 집계가 끝나고(실패 포함) 단계의 간격(small 2분, medium 1분, large 20초. 위 표) 안에는 새로 세지 않는다. 대화가 이어지면 살아 있는 메시지 수가 몇 초마다 바뀌어, 간격이 없으면 5초짜리 집계가 끝없이 이어져 1코어를 계속 쓰기 때문이다. 공간·recipe가 바뀐 경우(운영자의 설정 변경)만 간격을 기다리지 않으며, 다른 공간의 숫자를 이 공간 값으로 보여 주지 않는다. 숫자가 바뀌면 `memory` 이벤트(`pending_counted`)로, 간격 때문에 미룬 집계는 간격이 끝날 때 `pending_stale` 이벤트로 열린 콘솔이 목록을 다시 읽게 한다. 방별 수·기간·화자 수(`Rooms`·`RoomSpans`·`Counts`)는 `idx_memory_obs_room_live(room, deleted_at, parsed_time, actor_label)` 커버링 인덱스만 읽는다(SQLite. 10만 개에서 목록 호출당 약 2초 → 0.1초).


실측(i5-6400T, GOMAXPROCS=1, 1024차원, 메시지 벡터 활성): 100k의 변경 없는 재빌드 heap 피크는 기존 671–688 MiB에서 416.9 MiB로 줄었고, 로드 뒤 heap 208.3 MiB/재빌드 뒤 working set 494.2 MiB였다. 10k 재빌드 heap 피크는 41.6 MiB/working set 80.0 MiB, 재빌드 0.574초였다. 예전 100k 첫 cold 로드는 32.930초였다. 2026-10-12 후속 측정은 같은 합성 DB 사본(메시지 100,171개, leaf·요약 각 12,502개, 메시지 벡터 100,016개)에 기준 `a3ec0e2a`와 수정본을 새 프로세스로 번갈아 3회 로드했다. OS 파일 캐시는 따로 비우지 않았고 CPU·alloc 프로파일을 켰다. GOMAXPROCS=1에서 중앙값은 **15.206 → 8.197초**, heap 표본 피크의 3회 최댓값은 **338.7 → 295.9 MiB**였다(시간 범위 11.188–15.247 → 7.517–9.195초). GOMAXPROCS=4에서는 **13.681 → 10.911초**, heap 피크는 **326.7 → 282.6 MiB**였다(10.499–15.494 → 10.622–15.574초). 총 Go 할당량은 약 **989 → 605 MiB**로 줄었다. 측정 중 다른 `store.test`가 86–104%, 한 표본에서 `vision.test`가 96%, Defender가 59–139% CPU를 사용했다(100%=1코어). 따라서 이전 32.930초와의 직접 비교는 주장하지 않는다. 같은 날 다른 테스트·빌드 없이 다시 쟀다(기준 `a3ec0e2a`, 최종 `e6e381d2`, 같은 사본, 새 프로세스로 기준·최종을 번갈아 각 2회, OS 캐시가 빈 첫 실행 1회는 제외). GOMAXPROCS=1에서 **10.27 → 6.92초**, GOMAXPROCS=4에서 **9.86 → 6.42초**, 총 할당 **989 → 605 MiB**, heap 피크는 314–332 → 283–302 MiB였다. Defender가 실행마다 1.6–2코어를 썼으므로 절대값보다 번갈아 잰 비율(약 1/3 단축)을 본다. 1코어와 4코어 차이가 작은 것은 남은 비용이 SQLite 파일 읽기이기 때문이다. 합성 검색 6개 질의의 60개 결과는 1·4코어의 이전·이후 12회 로드에서 점수·순서가 같았다. 부하와 캐시 조건, 콘솔 집계의 남은 지연은 [부하 테스트](wiki/부하-테스트와-장기-운영.md)의 재측정 절을 참고한다. 이 단독 측정은 daemon main의 자동 메모리 한도 없이 수행했다.

### 상주 메모리 측정 (ADR-18 0단계, 2026-10-13)

[ADR-18](adr/ADR-18-idle-room-unloading.md)의 0단계는 **재지 않고는 정할 수 없는 숫자**만 낸다. 검색 동작, 상주하는 방(지금은 올라온 모든 방), 내려놓기, 설정은 바뀌지 않는다. 숫자는 두 곳에 나온다.

- **진단 `memory_residency`**(콘솔 로그 → 진단, "기억 상주 방")는 다음을 보여 준다.
  - **상주 방 수 / 전체 방 수**와 **준비됨** 방 수. "준비됨"은 색인이 끝나 저장소에 임베딩이 있는 방이고, "상주"는 지금 검색이 읽는 색인에 올라와 있는 방이다. 새로 색인한 방은 다음 재구축까지 준비됨이지만 아직 상주가 아닐 수 있다.
  - **추정 MiB.** 올라온 색인(leaf·요약·메시지 벡터, 메시지 배열, 위치 맵, 인물 표)의 Go 힙을 구조 크기를 더해 어림한 값이다. 실측값이 아니다. 같은 프로세스에서 이전 색인과 공유하는 int8 행은 한 번만 센다. 인물 표는 첫 검색이 만든 뒤부터 센다.
  - **전문 검색(FTS) DB 페이지 바이트.** 두 DB(leaf·요약)의 `page_count × page_size` 합이다. SQLite의 전체 할당이나 RSS가 아니고, **Go 힙 밖**이라 추정 MiB에 더하지 않는다. 읽기가 실패해도 검색에는 영향이 없고 이 값만 빈다.
  - **마지막 재구축의 단계 경계 표본 최대 힙.** 재구축이 읽기 끝·`Build` 끝·메시지 벡터 끝(켜져 있을 때)·발행 직전에서 `runtime.ReadMemStats`로 낸 `HeapAlloc` 중 가장 큰 값이다. **진짜 최대값이 아니다**: 단계 사이에서 더 높았을 수 있고, 아직 수거되지 않은 쓰레기도 들어 있다. 재구축 한 번에 네 번 재고 검색 경로에는 넣지 않는다. 재구축이 끝나지 않았거나 교체돼 버려졌으면 그 단계와 함께 표시한다.
  - 숫자만 나온다. 방 이름·본문·계정은 넣지 않는다.
- **기억 블록 목록의 "예상 메모리"**는 방 크기(메시지 수)로 낸 **모델 추정**이다. 방마다 고정 비용(약 3 MiB)과 메시지당 비용(본문·leaf와 요약 벡터 약 700 B + 메시지 벡터 폭에 비례하는 몫)을 더한다. 계수는 `internal/memory/engine/residency.go` 한 곳에 있고, E4 실측(1024차원)으로 시작해 512 기준 실측(C-4)으로 보정할 예정이다. 방이 아직 올라오지 않았으면 "아직 안 올라옴"이 붙는다. 진단의 추정 MiB(구조 합산)와 이 열(크기 모델)은 서로 다른 방법이라 합이 정확히 같지 않다. 둘의 차이가 C-4에서 계수를 보정하는 근거다.

Stage zero only measures. The `memory_residency` doctor row reports resident vs prepared rooms, an estimate of the index's Go heap (summed structure sizes, shared int8 rows counted once), the full-text databases' page bytes (`page_count × page_size`, outside the Go heap and not SQLite's whole allocation) and the largest heap among the last rebuild's stage-boundary samples (read, build, message vectors, publish; not a true peak). The blocks list's per-room "estimated memory" is a size model (fixed cost plus a cost per message), not a measurement. No room names, texts or accounts appear in either.

## 17. Discord 편집·삭제 조정 큐 복구 / Discord edit and delete queue recovery

Discord 편집·삭제를 저장소에 적용하지 못하면 데이터 폴더의 `discord-message-reconciliation/`에 이벤트별 파일로 보존하고 백그라운드에서 삭제부터 재시도한다. `e-*.corrupt`는 손상된 편집 하나만 격리하며 다른 편집을 막지 않는다. `d-*.corrupt`와 새 레거시 `discord-message-reconciliation.json.unresolved*.corrupt`는 삭제 대상을 알 수 없으므로 해결 전까지 편집 적용을 보류한다. 이 상태에서도 정상 삭제는 계속 처리한다. 업그레이드 전 레거시 `.corrupt`는 삭제 의도가 식별되는 경우에만 차단한다.

Error 로그의 `file`은 확인할 파일, `blocked`는 미해결 파일 수다. 파일에는 개인정보가 있을 수 있으므로 내용을 로그나 지원 요청에 복사하지 않는다. 파일을 안전하게 확인하고 해당 삭제를 처리하거나, 유효한 이벤트를 별도의 정상 `d-*.json` 파일로 복구해 처리가 끝났는지 확인한다. 그 뒤 원본 격리 파일을 같은 위치의 `resolved/` 하위 폴더로 옮겨 해결 완료를 표시한다. 편집 손상 파일도 내용을 확인해 필요하면 유효한 편집으로 복구할 수 있다. 확인 없이 삭제 의도를 해결 완료로 표시하지 않는다. 다음 재시도(최대 약 5분, 지터 포함)에 차단 수가 다시 계산되고 편집이 재개된다. 재시작해도 미해결 상태는 유지되고 안내 로그는 상태 변화 때와 미해결 상태가 6시간 지속될 때 반복된다. `resolved/` 파일은 자동 삭제되지 않으므로 운영자의 개인정보 보관 정책으로 관리한다.

큐 격리 파일의 완료 위치는 `<데이터 폴더>/discord-message-reconciliation/resolved/`, 레거시 격리 파일은 `<데이터 폴더>/resolved/`다. 업그레이드 직후 기존 `d-*.json.corrupt`도 차단 수에 포함된다. 예전에 사람이 삭제를 처리했더라도 파일이 남아 있으면 편집은 보류되므로, 처리 여부를 확인한 뒤 이 위치로 옮긴다. 잘못된 레거시 `at` 시각도 손상으로 격리·집계하며 값은 로그에 기록하지 않는다. 업그레이드 전 레거시 격리의 삭제 여부는 큐 쓰기 잠금 밖에서 읽고 파일 크기·수정 시각이 같으면 재사용한다. 새 삭제는 백오프를 깨우지만 저장소 장애 중 추가 편집은 재시도 간격을 줄이지 않는다.

삭제는 적용에 성공하거나 실패한 의도를 큐에 저장한 뒤 병합 메시지 정리·사진 작업 취소를 실행한다. 수신 후 내구성 있는 적용·저장이 끝나기 전에 강제 종료나 정전이 나면 의도를 잃을 수 있다(적용 재시도 대기만 최대 약 0.5초이며 저장소 지연은 별도다). 적용과 큐 쓰기가 모두 실패하면 오류 로그만 남고 해당 이벤트는 보존되지 않는다. 미해결 큐 상태(차단 수)는 로그뿐 아니라 관리 화면의 알림과 `masamong doctor`(`discord_reconciliation`)에도 "복구를 기다리는 파일 N개"로 표시된다. 경로·ID·내용은 표시하지 않으므로 파일은 데이터 폴더에서 직접 확인한다.

If a Discord edit or delete cannot be applied to storage, the bot saves an event file in `discord-message-reconciliation/` under the data folder and retries deletes first in the background. An `e-*.corrupt` file isolates only that damaged edit and does not block other edits. A `d-*.corrupt` file or a newly quarantined legacy `discord-message-reconciliation.json.unresolved*.corrupt` file may hide unknown deletion targets, so edits wait until it is resolved. Healthy deletes continue in this state. A legacy `.corrupt` file from before the upgrade blocks edits only when a delete intent can be identified.

The Error log's `file` names a file to inspect and `blocked` counts unresolved files. Files may contain private data; do not paste their contents into logs or support requests. Inspect the file securely and handle the deletion, or restore a valid event into a separate normal `d-*.json` file and verify that it has been processed. Then move the original quarantine into a `resolved/` subfolder beside it to mark resolution. A damaged edit can likewise be inspected and restored as a valid edit if necessary. Do not mark a deletion resolved without handling it. The next retry (up to about five minutes, with jitter) recounts blockers and resumes edits. Unresolved state survives restart; instructions repeat when state changes and after six hours while still blocked. Files in `resolved/` are not removed automatically; manage them under your privacy retention policy.

Move resolved queue quarantines to `<data folder>/discord-message-reconciliation/resolved/`, and legacy quarantines to `<data folder>/resolved/`. Existing `d-*.json.corrupt` files count as blockers immediately after upgrading. Even if an operator already handled their deletions, edits wait while those files remain; verify the work and move them to the appropriate folder. Malformed legacy `at` timestamps are also quarantined and counted, without logging their values. Old legacy quarantines are classified outside the queue write lock, and their classification is reused while file size and modification time stay the same. New deletes wake the backoff; additional edits during a storage outage do not shorten the retry interval.

Deletes are applied successfully or their failed intents saved to the queue before held-message cleanup and picture-job cancellation run. A forced exit or power loss between receiving an event and durable application or queue storage can still lose its intent (application retry waits alone total up to about 0.5 seconds, plus storage latency). If both application and queue writing fail, only an error is logged and the event is not retained. The unresolved queue count now also shows in the console's notifications and in `masamong doctor` (`discord_reconciliation`) as "N files are waiting for recovery", not only in logs. It never shows paths, ids or content, so inspect the files in the data folder directly.
