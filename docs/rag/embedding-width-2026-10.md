# 임베딩 폭 측정과 결정 (2026-10-13)

기억 조각(leaf) 벡터의 기본 폭을 4096에서 **1024**로 바꾼 근거와, 메시지 벡터 512 측정 결과를 담은 **측정 기록**이다. 메시지 벡터 512는 2026-10-13 적용했다. 현재 동작은 [기억 운영](../memory-operations.md)의 "임베딩 폭"과 §15에 있다. 측정 도구는 `tools/evaluation/memory_dims/`(§6)다.

> 한 줄 요약: 재순위가 있는 권장 구성에서는 1024가 4096과 품질이 같고(잡음 범위) Go 힙은 21~27% 줄어든다. 재순위가 없는 구성은 흐름형 질문이 1024에서 5문항(120문항 중) 떨어져, 모델 추천만 전체 폭을 제안한다. 메시지 벡터 512는 네 칸 모두 −1문항 이내라 **2026-10-13 적용했다**.

## 1. 사용자 의도 (판단 기준)

- "항상 성능 좋은 시스템에서 돌릴 수는 없어. 극단적으로 초저사양으로 언급하여 그거 개선해달라고 한거지 **보통 우리가 기대하는 임베딩이나 그런 검색 기능 성능은 기대한대로 나왔으면 좋겠음**."
- "벡터가 무작정 크게 한다고 성능이 좋긴하다만 **그만큼에 기대 성능 향상이 안된다**는걸로 앎. 이런 환경에서 **최적 벡터 수**도 좀 평가해서…"
- "결국은 이 서비스는 **24시간 한달이 됐든 몇 개월이 됐든 몇년이 됐든간에 안정적이며 지속 가능한 성능 수준과 유지보수**를 기대하고자 함."
- 저장 방식에 대해: "테스트한건 다 어차피 샘플 데이터임 그럼 1번 계획은 수정해도 되지 않나?" → **"디스크에 4096을 남기고 메모리에 올릴 때만 자르기" 안은 버렸다.** 이유: 운영 중인 V2 인스턴스가 없어 보존할 데이터가 없고, 차원을 다시 올려야 하면 원문으로 다시 임베딩하면 된다(방 하나 약 $0.05, 10분 안팎).

판단 기준: **보통 기기에서 검색 품질은 지금 측정값을 지킨다. 그 안에서 메모리·디스크를 줄여 몇 년 운영해도 버티게 한다.** 품질을 깎아 메모리를 얻는 변경은 하지 않는다.

## 2. 측정 결과 — 메시지 벡터를 끈 폭별 측정

**방법:** 제품 Go(main `3224a3b0`)를 그대로 썼다. 2026-10-11에 실제 기록을 적재한 데이터 루트 3개(디스코드 5.6만, 카카오 A 7.5만, 카카오 B 10.2만 메시지)를 차원마다 복사하고, `config.patch`로 `models.embed.dimensions`를 바꿔 제품의 `adaptSpace`가 자르게 했다(재임베딩 없음). **메시지 벡터는 끈 상태**다. 문항은 단일 메시지 문항(`.masamong-scratch/eval-20261011/gold/*.json`)과 흐름형 문항(`.masamong-scratch/eval-20261012/gold/*.span.json`)이고, 세트마다 답이 있는 40문항과 없는 10문항이다. R0은 재순위 없음(hybrid), R2는 Voyage rerank-2.5-lite다. 비용은 재순위 약 $0.47이었다. 도구는 `tools/evaluation/memory_dims/`(§6)이고, 결과 원본은 이전 장비의 `.masamong-scratch/eval-20261013-dims/`(git 제외)에 있다.

기록 없는 질문에 근거를 비운 수(R2)는 모든 차원에서 같았다(디스코드 8/10, 카카오 A 8/10, 카카오 B 9/10).

**해석:**
- **R2(재순위 있음, 권장 구성)에서는 512까지 품질이 같다.** 1024는 단일 86 대 88, 흐름형 82 대 82로 잡음 범위다.
- **R0(재순위 없음 — CometAPI·OpenAI·Gemini 호스트)에서는 흐름형 질문이 4096 → 2048에서 이미 6~7문항(약 5%p) 떨어진다.** 단일 문항은 그대로다. 256은 흐름형이 무너진다.
- **검색 속도는 차원과 거의 무관하다**(약 20ms, 어휘 검색·융합이 대부분). 임베딩 API 요금은 토큰 단위라 **비용도 무관하다.** 차원이 바꾸는 것은 **메모리와 디스크**뿐이다.
- 메모리 내역(카카오 B 기준): 본문·어휘 색인 등 벡터 아닌 부분이 약 57MB이고 메시지당 약 0.55KB다. leaf 벡터는 int8 기준 `leaf 수 × (차원+4)바이트`로 4096이면 약 58MB, 1024면 약 14.6MB다. 메시지 벡터(기본 켜짐, 1024)는 대상 메시지당 약 1KB다.
- **장기 추정**(메시지당 Go 힙): 4096이면 약 1.6KB, 1024면 약 1.2KB다(메시지 벡터 포함). 활발한 방 1년(약 10만 메시지)은 약 160MB에서 120MB로 줄고, 방 3개 3년(약 100만 메시지)은 약 1.6GB에서 1.2GB로 줄어 **약 25~30% 감소**다. 디스크의 leaf 벡터(float16)는 4배 줄어든다(leaf당 8KB에서 2KB).

**한계:** 문항은 합성·미검수다(신뢰구간 ±13~15%p). 메시지 벡터를 끄고 쟀다(켜고 다시 잰 결과는 §3). 모델은 qwen3-embedding-8b 하나만 쟀다.

## 3. 메시지 벡터를 켠 측정 (4096 대 1024)

**방법:** main `88b1bddf`에서 `DIMS="4096 1024" MSGVEC=1 tools/evaluation/memory_dims/run_sweep.sh`를 그대로 돌렸다. 데이터 루트·문항은 §2와 같다. 메시지 벡터는 세트마다 4096 사본에서 한 번 만들고(discord 약 10분, kakao-a 약 12분, kakao-b 약 14분 — 메시지 3.4만 개에 $0.006 수준) 1024 사본이 복사해 썼다. 재순위 오류 0건이었고, 비용은 재순위 $0.19와 메시지 벡터 약 $0.02로 **합계 약 $0.21**이었다. `agg.py`는 Windows에서 결과 파일을 하나도 못 읽고 있어서(경로 구분자 `\`) 이번에 고쳤다.

**R@5 (R@1) [후보 풀 안 정답 수], 세 세트 합계 120문항:**

| 구성 | 4096 | 1024 | 차이 |
|---|---:|---:|---:|
| R2 단일 | 95 (85) [105] | 93 (84) [103] | −2 |
| R2 흐름형 | 85 (62) [102] | 84 (60) [100] | −1 |
| R0 단일 | 72 (58) [105] | 70 (59) [103] | −2 |
| **R0 흐름형** | **73 (43) [102]** | **68 (41) [100]** | **−5** |

```
세트별 R@5 (4096 → 1024): R0 흐름형 discord 30→26, kakao-a 22→22, kakao-b 21→20
                         R2 단일 discord 32→32, kakao-a 30→28, kakao-b 33→33
기록 없는 질문에 근거를 비운 수(R2): discord 8/10, kakao-a 8/10, kakao-b 9/10 — 두 폭이 같다
Go 힙(색인 로드 후): discord 122.1→96.9MB(−21%), kakao-a 142.9→111.2MB(−22%), kakao-b 160.9→117.3MB(−27%)
```

- 메시지 벡터를 켜도 결과는 메시지 벡터를 끈 §2와 같은 방향이다. 재순위가 있으면 1024는 잡음 범위이고, 재순위가 없으면 흐름형 질문이 빠진다. 빠진 문항은 대부분 discord 흐름형(−4)에서 나왔다.
- 1024의 R0 검색 시간 중앙값은 1.8~2.6초로 찍혔는데, **검색이 느린 것이 아니라 질의 임베딩 캐시가 비어 있었기 때문이다.** 캐시 키에 공간 이름(`모델:폭:l2`)이 들어가는데, 4096 사본은 10-11 측정 때 같은 문항으로 채운 캐시를 그대로 썼고 1024 사본은 문항마다 API를 새로 불렀다(새 캐시 항목 90개, 1024폭 2048바이트). 같은 문항을 다시 물을 때는 6ms였다. 재순위 모드는 같은 질의 벡터를 다시 쓰므로 두 폭이 0.6~0.7초로 같다.

**판정:** R0 흐름형이 **5문항 떨어져** 결정 규칙의 두 번째 경우다(4문항 이상). R2는 단일 −2, 흐름형 −1로 3문항 이내다.
- 기본 폭은 **1024**로 바꾼다(새 설치, 그리고 MRL 모델로 바꿀 때).
- **재순위가 없는 구성**을 추천할 때만 모델 추천(`models.recommend`)이 전체 폭(qwen3-embedding-8b는 4096)을 제안한다. 운영자가 그 추천을 적용할 때만 쓰이고, 설정을 몰래 바꾸지 않는다.
- 512MB급 기기(hostprofile small 단계)는 재순위가 없어도 1024를 유지한다(메모리 우선).

## 5. 구현과 검증 (2026-10-13)


**구현한 것**
- 기본 폭 1024(`config.DefaultEmbedDimensions`). 자를 수 있는 모델과 전체 폭은 `hosts.json` `embed_widths`(`openai.EmbedFullWidth`) 한 곳에 있다. 모르는 모델은 전체 폭(0)이다.
- 모델 전환(`selectModel`): 목록에 있고 전체 폭이 1024를 넘는 모델은 1024, 그 밖에는 0이다. 모델 문자열이 같고 공급자만 바뀌면 폭을 유지한다.
- 추천(`models.recommend`): 임베딩이 바뀔 때만 폭을 제안한다(`embed_dimensions`, `embed_dimensions_reason`, `embed_full_width`, rerank 체크를 끈 경우의 `embed_width_without_rerank_pick`). 재순위 판정은 런타임과 같은 `engine.RerankUsable`이다. 재순위가 없으면 전체 폭(0 저장)이고 small 단계는 1024다.
- 같은 모델의 폭 변경 Action `models.embed_width`: 허용 폭은 0·1024·2048이다(1024 미만은 메시지 벡터가 재임베딩되므로 거절). 낮추면 바로 적용하고, 넓히면 `models.embed_reindex_required` 확인을 받는다. 읽기는 `providers.list.embed_width`(한 스냅샷의 revision·모델·폭·widths·rerank_usable)다.
- 폭이 바뀌어도 채널에 붙인 블록과 준비 기록이 유지된다. 조회 때 같은 방·recipe·모델의 다른 폭 ID를 고정 후보 폭 집합의 별칭 맵으로 인정하고, 블록 ID 형식이 아닌 입력은 바로 미스로 처리한다.
- 콘솔 연결 화면: 폭 표시와 변경(낮춤 확인창, 넓힘 예상치 확인, revision CAS), 재순위 없는 좁은 폭 안내, 추천 창의 폭과 이유, 문구 5개 언어.
- 폭 변경 요청에는 콘솔이 승인한 방향(`direction`: lower·raise)이 함께 간다. 그사이 저장된 폭이 바뀌어 방향이 달라지면 서버가 아무것도 바꾸지 않고 `CONFIG_CONFLICT`로 거절한다(CLI는 생략 가능).
- 검토: 서버는 Sonnet이 두 번 검토해 MERGE를 받았다. 콘솔과 그 뒤 수정은 Sol이 네 번 검토했고, 지적(추천 체크별 폭, revision 기준을 한 스냅샷에서 만들기, 늦은 응답, 추천 창 갱신)을 모두 고친 뒤 MERGE를 받았다. 남은 한계는 [알려진 문제](../KNOWN_ISSUES.md)에 옮겼다.

**제품 경로 확인(필수):** 2026-10-11 실제 기록 데이터 루트 3개(4096 공간)를 새로 복사해, 최종 코드의 `config.patch`로 폭을 1024로 낮추고 단일·흐름형 문항을 돌렸다(메시지 벡터 끔, §2와 같은 조건).
- R@5(120문항 합계): R2 단일 **86**(§2 1024 값 86), R2 흐름형 **82**(82), R0 단일 **68**(69), R0 흐름형 **68**(67). 모두 ±2 안이다. 기록 없는 질문에 근거를 비운 수도 같다(8·8·9/10).
- leaf 벡터는 세 세트 모두 전부 `:0:`(8192바이트)에서 `:1024:`(2048바이트) 공간으로 옮겨졌다(8,280·10,304·14,182개).

## 6. 측정 도구 (`tools/evaluation/memory_dims/`)


| 파일 | 역할 |
|---|---|
| `runner/main.go` | 제품 `application.Service`를 데이터 루트에 열어 평가한다. 명령은 `setup`(원문 적재·색인), `index`(색인 한 번, `-budget`), `search`(문항별 순위·후보 풀·근거 비움 기록, `-modes hybrid,rerank`), `chat`(대화 턴, 답변은 결과 파일에만), `status`, `keep`(사본에서 지정한 방만 남기고 나머지를 제품 `memory.blocks.delete`로 지움), `load`(새 프로세스 한 번의 cold 로드 시간·힙)다. `index`는 메시지 벡터 수·폭·space도 출력한다. **`-dims N`**은 `models.embed.dimensions` 설정, **`-msgvec`**은 `memory.message_vectors` 켜기, **`-msgdims N`**은 메시지 벡터만 N차원으로 자르는 측정 전용 설정(`engine.Settings.MessageDims`, 제품 설정에는 없음)이다. 둘 다 제품의 `config.patch`로 적용한다. 데이터 루트의 설정은 DB에 있어서 `config.yaml`을 고쳐도 반영되지 않는다(2026-10-13에 이 함정으로 첫 측정을 다시 했다). 키는 `EVAL_KEYFILE` 또는 `.private/test-keys/openrouter`다. 본문은 출력하지 않는다. |
| `run_sweep.sh` | 데이터 루트를 차원별로 복사해 단일·흐름형 문항을 순서대로 돈다. 세트를 동시에 돌리면 재순위가 429다. `MSGVEC=1`이면 메시지 벡터를 세트당 한 번 만들어 복사해 쓴다. 환경 변수는 파일 머리말에 있다. |
| `agg.py` | 결과 요약(R@5, R@1, 후보 풀, 근거 비움). 수치만 출력한다. |

데이터 루트가 없으면 `runner setup -root <루트> -raw .private/raw-corpus/<collection>/dated.jsonl.gz -rooms <방> -budget 0.10`로 만든다(임베딩 약 $0.05, 저사양 기기에서 수십 분). 문항(gold)은 `.masamong-scratch/eval-20261011/gold`, `.masamong-scratch/eval-20261012/gold`에 있다(전송 zip에 포함됐다).

## 7. 메시지 벡터 512 측정과 적용 (2026-10-13)


**도구:** `engine.Settings.MessageDims`(측정 전용, config·콘솔에 없음, 1..1024를 허용하고 0이면 제품 규칙 — `TestMessageSpaceAndDimensions`가 고정)와 평가 도구 `-msgdims N`(`5883e4e4`, 기본 0). 메시지 공간이 다른 색인은 넘겨받지 않는다(`Inherit`, 테스트 추가).

**방법:** §3 측정의 `<set>-1024.mv` 루트(leaf 1024, 메시지 벡터 1024)를 그대로 1024 기준으로 다시 돌렸다(§3 실행과 R@5 합계가 모두 같았고, 문항 단위로는 discord R2 단일에서 두 문항씩 맞고 틀림이 바뀌었다 — 재순위 잡음의 크기). 512는 그 루트 사본에 `runner index -dims 1024 -msgvec -msgdims 512`로 메시지 벡터만 다시 임베딩했다(leaf는 그대로). 문항은 §3과 같다(세트마다 답 있는 40 + 없는 10, 단일·흐름형).

| R@5 (120문항 합계) | 메시지 1024 | 메시지 512 | 차이 |
|---|---|---|---|
| R2 단일 | 93 | 93 | 0 (+2 −2) |
| R2 흐름형 | 84 | 84 | 0 |
| R0 단일 | 70 | 69 | −1 (kakao-a) |
| R0 흐름형 | 68 | 68 | 0 (+1 −1) |

기록 없는 질문에 근거를 비운 수는 R2에서 25/30으로 같다. R@1은 512가 같거나 높았다(R2 단일 83→85).

| 세트 | 메시지 벡터 | Go 힙 1024 → 512 | 메시지 벡터 바이트(DB) 1024 → 512 | 512 재임베딩 |
|---|---|---|---|---|
| discord (5.6만 메시지) | 32,927 | 96.7 → 79.8MB (−17%) | 33.8 → 17.0MB | 18분 47초, 약 $0.008 |
| kakao-a (7.5만) | 40,592 | 111.2 → 90.4MB (−19%) | 41.7 → 20.9MB | 15분 1초, 약 $0.008 |
| kakao-b (10.2만) | 33,801 | 117.4 → 100.2MB (−15%) | 34.7 → 17.4MB | 12분 48초, 약 $0.006 |

- 메시지 벡터 표는 메시지마다 한 행이라(`observation_id` 기본 키) 512로 바꾸면 행이 교체된다. DB 파일 자체는 VACUUM 전까지 줄지 않는다.
- 비용: 재임베딩 약 $0.022, 재순위(1024 재실행 + 512) 약 $0.1.

**결정: 적용함(2026-10-13).** 네 칸 모두 3문항 이내(최대 −1)이고, 상주 힙이 15~19%, 메시지 벡터 저장이 절반 준다. MRL 모델은 leaf 폭이 512 이하로 설정되면 그 값을 쓰고, 그 밖에는 512를 쓴다. `hosts.json`의 `embed_widths`에 없는 모델은 MRL이라고 가정하지 않는다. `gemini-embedding-2`처럼 목록에 없는 모델은 설치의 실제 leaf 폭과 `모델:<실제 폭>:l2` 공간을 사용하며, 명시 leaf 폭이 없으면 모델 전체 폭이다. 폭을 모르면 leaf 임베딩까지 대기하고, 진단의 `message_vectors` 행에는 확정된 폭을 표시한다. 기존 비-MRL 명시 leaf 폭의 절단 문제는 [BACKLOG의 WIDTH](../BACKLOG.md#0-남은-결정과-기술-한계)에 남긴다. 측정 override는 1..1024를 받는다.

기존 MRL 설치의 공간 이름은 `모델:1024:l2`에서 `모델:512:l2`로 바뀐다. 업데이트 순간에는 임베딩하지 않고 다음 `IndexRooms`에서 새 공간에 없는 메시지를 다시 만든다. 재임베딩 중에는 예전 공간 행을 쓰지 않아 `message_dense` 후보만 줄며, 검색 품질은 메시지 벡터를 일부 끈 것과 같다. 행은 `observation_id` 기본 키에서 교체된다. SQLite 원본 파일은 자동으로 줄지 않고, 기존 `VACUUM INTO` 백업은 압축된 사본을 만든다. 예상 비용은 메시지 10만 개당 1센트 미만, 저사양 장비에서 수십 분이다.

기존 MRL 목록 밖 모델의 이전 기본 공간은 `모델:1024:l2`이고, 명시 leaf 폭이 1..1024이면 그 폭이었다. 새 공간은 `모델:<실제 leaf 폭>:l2`이며 숫자 폭이 달라졌을 때만 메시지를 다시 만든다. 업데이트 순간에는 임베딩하지 않고 다음 `IndexRooms`에서 진행한다. 공급자가 바뀌어 저장된 leaf 폭이 달라지면 메시지도 새 공간의 대기가 된다. 그동안 옛 공간 벡터는 검색에 섞이지 않아 `message_dense` 후보만 줄고, 새 행은 `observation_id` 기준으로 기존 행을 교체한다.

## 8. 하지 않기로 한 것

- 4096을 디스크에 두고 메모리에서만 자르는 구조.
- MRL이 아닌 모델 자르기. 목록(`hosts.json` `embed_widths`)에 없는 모델은 전체 폭을 쓴다.
- 기기 단계마다 다른 기본 폭. 기기를 옮길 때 재임베딩이 생긴다.
- 폭과 함께 검색 알고리즘(RRF 가중치, 풀 크기, 출처 보장) 바꾸기. 다른 손잡이는 2026-10-12 측정에서 잡음 수준이었다.
- 측정 결과 파일과 데이터 루트 사본 커밋. 실제 대화 기반이라 `.masamong-scratch/`에만 둔다.

**한계:** 문항은 합성·미검수다(세트당 40+10, 신뢰구간 ±13~15%p). 모델은 qwen3-embedding-8b 하나만 쟀다. 기본값을 다시 크게 바꿀 일이 생기면 그 전에 사람이 문항을 검수한다(`gold/*.review.json`).
