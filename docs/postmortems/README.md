# 사고 회고 (Post-mortems)

버그가 실제 운영·커밋·릴리스까지 간 사례를 적습니다. 무엇이 깨졌는지보다 **왜 모든 검사가 놓쳤는지**와 같은 종류의 버그가 다음에는 크게 실패하도록 **무엇을 추가했는지**가 중심입니다. 양식은 DeepSeek Harness의 post-mortem 형식을 참고했습니다.

## 언제 쓰나

세 가지가 모두 맞을 때 씁니다.

- **알기 어려움**: 원인이 겉으로 보이지 않아, 신중한 사람도 처음부터 다시 파헤쳐야 합니다.
- **구조적**: 놓친 이유가 단순 실수가 아니라 테스트·도구·관례의 빈틈입니다.
- **다시 찾기 비쌈**: 실제로 디버깅 시간이 많이 들었고, 또 들 것입니다.

설계 결정과 버린 대안은 [ADR](../adr/)에, 바로잡은 동작은 해당 문서(위키·`docs/`)에 적습니다. 회고는 실패를 돌아보는 기록입니다.

## 양식

1. **30초 요약**: 무엇이 깨졌나, 원인을 쉬운 말로, 왜 빠져나갔나, 남는 교훈. 한 문단.
2. **영향**: 누가 무엇을 겪었나.
3. **경과**: 근거(커밋, 측정값, 로그)와 함께.
4. **원인**: 메커니즘.
5. **왜 놓쳤나**: 어떤 검사가 있었고 왜 못 잡았나.
6. **추가한 안전장치**: 테스트, 도구, 규칙. 링크와 함께.
7. **교훈**: 다른 기능에도 통하는 것만.
