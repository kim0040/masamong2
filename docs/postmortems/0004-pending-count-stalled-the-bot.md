# 0004: 대기 메시지 수를 세는 쿼리가 봇 전체를 몇 분씩 멈춤

상태: 해결 (2026-10-12, `1d5949f2`, 안전장치 `19b7fa50`). 릴리스 전 저사양 점검에서 발견했습니다.

## 30초 요약

메시지 벡터를 기본으로 켠 직후(`22812e3e`), 콘솔 대시보드·doctor·기억 블록 화면이 "임베딩을 기다리는 메시지 수"를 셀 때마다 봇이 멈췄습니다. 메시지 1만 개, 코어 1개에서 메시지 저장 p50이 192초였습니다. SQLite가 조인 순서를 "메시지마다 모든 조각의 id 목록을 훑는" 쪽으로 골라 비용이 메시지 수 × 조각 수로 커졌습니다(1만 개에서 49초, 10만 개면 수십 분). 이 쿼리가 프로세스 전체가 함께 쓰는 **쓰기 연결 하나**에서 돌았기 때문에, 그동안 모든 저장·답변·명령이 기다렸습니다. 테스트와 CI 부하 테스트는 기록이 거의 없는 상태에서만 돌아 빠른 쿼리처럼 보였습니다. 교훈: **기록 크기에 비례하는 조회는 큰 기록으로 재 보기 전까지 싸다고 말할 수 없고, 쓰기 연결에서는 짧은 문장만 돌려야 합니다.**

## 영향

- 메시지 벡터가 켜진 인스턴스(이 커밋부터 기본)에서 콘솔을 열거나 `/status`·`masamong doctor`를 부르면, 저장된 메시지 수의 제곱에 비례하는 시간 동안 봇 전체가 멈췄습니다.
- 측정(i5-6400T, `GOMAXPROCS=1`, `tools/loadtest -seed 10000 -dims 1024`): 판정 FAIL. 3분 동안 대화 99건 중 6건 시간 초과. 메시지 저장 p50 192초, `/help` p50 226초. 45초부터 312초까지 표본 수집조차 멈췄습니다.
- 운영 배포 전이라 실제 사용자 피해는 없습니다.

## 경과

- 2026-10-12: 사용자가 "초저사양 서버에서도 돌아가는지 확인"을 요청했습니다. 부하 도구를 Windows에서도 재게 고치고(`bf68eec6`: working set·핸들 수, `-pprof`, `-message-vectors`) 코어 1개로 돌렸습니다.
- 1만 개에서 FAIL이 나왔습니다. `-pprof`로 15초마다 고루틴 덤프를 받아 보니, 100개가 넘는 고루틴이 `database/sql`의 연결을 기다리고 있었고, 연결을 쥔 쪽은 `memory.blocks.list → messageVectorStatus → CountPendingMessages` 하나였습니다.
- 같은 DB에서 `EXPLAIN QUERY PLAN`으로 확인했습니다. 수정 전 계획은 `SCAN o`(메시지 전체)가 바깥이고, 그 안에서 `memory_leaves`를 자동 인덱스로 찾은 뒤 `json_each`를 펼쳤습니다. 48.7초가 걸렸습니다.
- 같은 시각 독립적으로 돈 Sonnet 감사도 같은 쿼리를 1순위로 보고했습니다(합성 DB: 2천 개 2.0초, 4천 개 8.4초).
- `1d5949f2`: `CROSS JOIN`으로 순서를 고정하고(조각 → id → 메시지는 기본 키로 찾기, 0.35초), 대기 목록·개수·미분할 개수를 읽기 전용 풀로 옮겼습니다. 다시 측정하니 PASS였습니다(저장 p50 6 ms, 답변 p50 0.95초).

## 원인

- `pendingMessageQuery`는 `FROM memory_leaves, json_each(...) JOIN memory_observations ... GROUP BY o.observation_id ORDER BY o.room, o.observation_id`였습니다. 방을 지정하지 않으면(doctor·콘솔·추정) SQLite가 `GROUP BY` 정렬을 피하려고 메시지 기본 키 순서의 스캔을 바깥에 두었습니다. 메시지 하나마다 닫힌 조각 전체의 id 목록을 펼쳤으니 메시지 × 조각 × 8입니다.
- 쓰기 연결은 프로세스에 하나입니다(`storage.Open`: `SetMaxOpenConns(1)`). 긴 읽기는 `Reader()`로 보내는 규칙이 있었지만, 이 쿼리는 `s.DB.DB`를 썼습니다.

## 왜 놓쳤나

- 단위 테스트는 메시지 수십 개로 돌아 계획과 무관하게 빨랐습니다. 결과(개수)만 확인했고 비용은 보지 않았습니다.
- 메시지 벡터 측정(`memory-operations.md` §15)은 검색 품질과 색인 비용을 쟀습니다. 콘솔·doctor 경로는 측정 도구가 부르지 않았습니다.
- CI의 45초 부하 테스트는 저장된 기록 없이 시작합니다(`-seed` 없음). 월간 soak도 마찬가지였습니다. 기록이 비어 있으면 제곱 비용도 0입니다.
- 쓰기 연결을 누가 얼마나 오래 쥐는지는 어디에도 기록되지 않았습니다. 멈춤은 "답이 느리다"로만 보였습니다.

## 추가한 안전장치

- 회귀 테스트 `TestPendingMessageQueryWalksLeavesFirst`(`internal/memory/store`): `ANALYZE`를 한 DB에서 쿼리 계획을 읽어, 조각이 바깥 루프이고 메시지는 기본 키로 찾는지 확인합니다. 수정 전 쿼리에서는 실패합니다.
- 쓰기 연결 점유 기록(`internal/storage/busy.go`, `19b7fa50`): 문장 하나나 트랜잭션 하나가 쓰기 연결을 2초 넘게 쥐면 경고 로그를 남기고 `storage.SlowWriterHolds()`를 올립니다. 로그에는 SQL 앞부분만 남기고, 따옴표 리터럴 앞에서 자르며, 1초에 한 줄로 제한합니다.
- 월간 soak(`.github/workflows/soak.yml`)를 메시지 2만 개가 저장된 상태에서 코어 1개(`GOMAXPROCS=1`)로 시작하게 바꿨습니다.
- 부하 도구: Windows에서도 메모리·핸들을 재고(`metrics_windows.go`), `-pprof`로 멈춘 동안 고루틴 덤프를 받고, `-message-vectors`로 끈 상태와 비교할 수 있습니다.

## 교훈

- 기록 크기에 비례하는 쿼리는 실제 규모(최소 1만 개, 가능하면 10만 개)의 DB에서 `EXPLAIN QUERY PLAN`과 시간을 함께 봐야 합니다. JSON 펼치기(`json_each`)와 큰 테이블을 묶는 조인은 특히 SQLite 계획기가 순서를 잘못 고르기 쉽습니다. 의도한 순서가 있으면 `CROSS JOIN`으로 고정하세요.
- 연결이 하나뿐인 쓰기 풀에서는 "읽기라서 괜찮다"가 통하지 않습니다. 콘솔·진단처럼 사람이 여는 화면의 조회는 `Reader()`로 보냅니다.
- 부하 테스트는 빈 상태가 아니라 오래 쓴 인스턴스처럼 기록을 채운 상태에서, 목표 장비처럼 코어를 줄여서 돌려야 합니다.
