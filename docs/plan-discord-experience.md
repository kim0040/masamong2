## 2. 예약 작업: "매일 12시에 점심 메뉴 추천해줘"

### 2.1 지금 흐름

1. 일반 대화 턴에서 도구 판단 모델이 시각·반복 요청을 `reminders.propose`로 보냅니다. 이 도구의 계약에는 "알림 문구"(`what`)만 있고, **실행할 일인지 알릴 문구인지 나누는 값이 없습니다**([`tools.go:169-179`](../internal/tools/tools.go), `internal/lang/packs/ko.json`의 예약 도구 안내).
2. `remindersPropose`가 `when`·`what`으로 시각 후보와 내용을 만들고 `proposed`로 저장합니다. 반복은 `repeat` 인수(`daily|weekly|monthly|hours`)로 읽습니다([`reminders.go:234-290`](../internal/application/reminders.go), [`reminders_repeat.go:46-111`](../internal/application/reminders_repeat.go)).
3. 사용자가 확인 카드에서 시각·목적지를 고르면 `scheduled`가 됩니다([`reminders.go:434-471`](../internal/application/reminders.go)).
4. 스케줄러가 1분마다 `deliverReminders`를 돌려 시각이 된 예약을 보냅니다([`schedule.go:54-58`](../internal/application/schedule.go), [`reminders.go:750-781`](../internal/application/reminders.go)).
5. **보내는 것은 모델 호출이 아니라 고정 카드입니다**. 본문은 저장된 `content`이고, 제목은 "⏰ 예약 알림"입니다([`reminders.go:845-869`](../internal/application/reminders.go)).

### 2.2 원인

예약 기록에는 "요청을 실행하라"는 정보가 없고, 만기 경로는 `ChatTurn`(도구 판단 → 도구 → 답변)을 부르지 않습니다. 그래서 "점심 메뉴 추천"은 실행할 요청이 아니라 알림 문구로 남습니다. 버그가 아니라 **없는 기능**입니다.

### 2.3 함께 발견한 문제: "매일"이 사라짐

운영 기록(10-14 09:06 KST)에서 확인한 사실은 다음과 같습니다.

- 요청 원문에 "매일"류 표현이 있었습니다. 원문은 열람하지 않고 포함 여부만 확인했습니다.
- 도구 판단 모델은 `reminders.propose`를 `repeat`·`what`·`when` 인수와 함께 불렀습니다.
- 봇 답장에도 반복을 뜻하는 표현이 들어 있었습니다.
- 그런데 저장된 예약은 `repeat_rule`이 비어 있었습니다. 정밀도는 `day_part`("점심")였고, 한 번 보낸 뒤 `sent`로 끝났습니다.

코드상 반복이 빠지는 경우는 `repeat` 값이 비었거나 `none`/`once`일 때뿐입니다. 잘못된 값이면 예약을 거절합니다([`reminders_repeat.go:48-52`](../internal/application/reminders_repeat.go)). 정상 확인 버튼과 `day_part` 정밀도는 반복을 지우지 않습니다. 도구 호출 기록은 인수 이름만 남기고 값은 남기지 않아서, 그때 `repeat` 값이 무엇이었는지는 확인할 수 없습니다.

가장 유력한 설명은 이렇습니다. 도구 판단 모델이 `repeat`에 빈 값이나 `none`을 넣었고, 답변 모델은 도구 결과(반복 없음)가 아니라 사용자 요청을 보고 "매일"이라고 말했습니다.

할 일:

1. **답장이 도구 결과와 어긋나지 않게 하기.** 예약 도구 결과에 반복 규칙을 명시 필드(`repeat: "none"` 또는 규칙 요약)로 넣고, 답변 규칙에 "예약 확인 문구는 도구 결과의 시각·반복만 말한다"를 넣습니다. 확인 카드는 이미 규칙을 보여 주므로 카드와 답장이 다르면 사용자가 헷갈립니다.
2. **요청과 도구 인수가 어긋나면 되묻기.** 요청에 반복 표현이 있는데 `repeat`이 비면 확인 카드에 "한 번만 / 매일" 선택을 띄웁니다. 언어마다 반복 표현이 다르므로 판단은 도구 판단 모델의 출력으로 하고, 코드에서 단어를 맞추지 않습니다. 언어팩의 도구 안내 예시에 "매일 …해줘 → repeat=daily"를 넣는 것이 먼저입니다.
3. **재현 테스트.** `TestLiveScenarios`류 실측과 도구 회귀 세트(`tools_regression_ko.json` 등)에 "매일 점심 12시에 …" 형태를 넣어 `repeat=daily`가 나오는지 봅니다.
4. 도구 호출 기록에 enum 인수 값(자유 텍스트가 아닌 `select` 값)은 남길지 결정합니다. 개인정보가 아닌 값이라 다음 진단에 도움이 됩니다(결정 E-1).

### 2.4 설계: 예약 작업(scheduled task)

**목표**: 정한 시각에 저장한 요청을 실제 봇 턴으로 실행하고 답을 보냅니다. 예를 들어 매일 12시에 점심 메뉴를 추천합니다.

**만들기**

- `reminders.propose`에 `kind=reminder|task`를 더합니다. 기본값은 `reminder`라 기존 기록과 동작이 그대로입니다.
- `task`는 실행할 요청 문장(`task_request`)과 만들 때의 채널(`request_channel_id`)을 따로 저장합니다. 반복·상태·임대(lease) 열은 기존 `reminders`를 재사용합니다.
- 실행 기록은 새 표 `scheduled_task_runs`에 둡니다. 회차 시각, 상태, 답장, 비용, 쓴 도구, 전송 ID, 오류를 적습니다.
- 언어팩 도구 안내: "추천해 줘, 찾아 줘, 정리해서 알려 줘"처럼 동작을 시키면 `task`, 시각에 문구만 띄우면 `reminder`입니다. 애매하면 확인 카드에서 둘 중 하나를 고르게 합니다.
- 확인 카드에는 실행할 요청, 반복, 보낼 곳(채널/DM), 쓸 수 있는 도구, 1회 비용 상한을 보여 줍니다.

**실행**

- 만기 처리에서 `kind=task`면 `runScheduledTask`로 갈라집니다.
- 저장한 요청을 `ChatInput.Message`로 넣어 보통 `ChatTurn`을 돌립니다.
- 말하는 주체는 봇입니다. 요청자 ID는 도구 권한, 개인 한도, 언어, 동의 확인의 주체로만 씁니다.
- 공개 채널 답장의 멘션 차단은 그대로 둡니다.

**허용 도구(초안)**

- 읽기 전용 `search.web`, `places.search`, `weather.query`, `disasters.query`, `finance.quote`, `finance.fx`.
- `web.read`는 요청에 링크가 있을 때만 씁니다.
- `memory.search`는 기본으로 끕니다.
- 투표, 예약, 이미지, 운세 구독, 운영자 정의 HTTP 도구, 관리 Action은 쓰지 않습니다([`tools.go:124-141`](../internal/tools/tools.go)).

**한도(초안, 결정 T-2)**

- 사용자당 활성 task 5개
- 하루 3회, 동시 실행 1개
- 회당 외부 도구 2회
- 회당 전체 비용 `min(설정, $0.03)`

지금 `Guard`의 금액 한도는 도구 판단·답변 호출을 막지 않고 선택적인 도구·기억 작업만 건너뜁니다([`guard.go:10-21`](../internal/chat/guard.go)). 그래서 task용 전체 상한은 새로 만들어야 합니다. 상한 $0.03이면 매일 task 하나의 30일 비용은 최대 $0.90입니다. 운영 기록의 평균 턴 비용 $0.0017로 계산하면 실제는 월 $0.05 안팎입니다.

**실패**

- 도구가 실패하거나 결과가 없으면 그 사실을 답에 그대로 말합니다.
- 모델 실패나 예산 소진이면 정해진 안내를 한 번 보내고, 그 회차를 `failed`/`budget_exhausted`로 기록합니다. 반복 task는 다음 회차를 유지합니다(결정 T-4).
- Discord가 전송을 거절하면 저장한 답을 다시 보냅니다. 모델과 도구는 다시 돌리지 않습니다.

**놓친 회차**

기존 예약 규칙을 그대로 씁니다. 1회성은 30분이 지나면 `missed`로 처리합니다. 반복은 유예 시간 안의 최신 1회만 실행하고, 밀린 회차를 몰아서 돌리지 않습니다([`reminders.go:793-835`](../internal/application/reminders.go)).

**기억**

task의 요청과 답은 일반 대화 기억에 넣지 않는 것을 기본으로 합니다(`Scheduled` 출처를 새로 둡니다). 지금 `ChatTurn`은 기억이 허용되면 요청을 user, 답을 assistant로 저장합니다([`memory.go:1394-1413`](../internal/application/memory.go)). 매일 같은 요청이 기억을 채우지 않게 해야 합니다.

**콘솔**: Action `scheduled_tasks.list/get/pause/resume/cancel/run_now`를 둡니다. Room·People 화면의 예약 목록(`RemindersList.svelte`) 옆에 요청, 다음 시각, 최근 답, 회차 상태, 비용을 보여 주고 멈춤·취소를 할 수 있게 합니다. AGENTS.md 규칙대로 Action과 GUI를 함께 만들어야 끝입니다.

## 3. Discord 카드 디자인: 운세·공지

### 3.1 공통 원인

운세, 공지, 예약 알림, 재난, 도움말 카드는 모두 같은 경로를 지납니다. `action.Card`(제목·본문·필드·푸터·Tone)가 `renderCard`를 거쳐 embed가 됩니다([`card.go:6-32`](../internal/action/card.go), [`render.go:670-772`](../internal/connectors/discord/render.go)).

- **색**: Tone이 비면 초록(`colorOK`)입니다([`render.go:671`](../internal/connectors/discord/render.go)). 그래서 운세, 별자리, 공지, 예약 알림, 지진이 모두 같은 초록입니다. 중립 색 `0x4B5563`은 다크 테마에서 대비가 1.7:1이라 막대가 거의 안 보입니다.
- **푸터**: 푸터는 마크다운이 적용되지 않습니다. 그런데 `fortune.profile_help`, `notices.profile_help.*` 문구가 백틱(`` ` ``)으로 명령을 감싸서 백틱이 글자 그대로 보입니다(`locales/ko.json`의 `fortune.profile_help`).
- **구조**: 운세는 모델 출력 전체를 본문 하나에 붓습니다. 공지는 이미 계산한 중요도 띠(할 일·기회·참고)를 묶지 않고 평평하게 나열합니다.

### 3.2 운세 잘림(먼저 고칠 것)

운영 기록의 운세 생성 5회 중 3회가 정확히 900토큰에서 `length`로 끝났고, 1회는 빈 응답이었습니다. 아침 브리핑과 오늘 운세의 출력 한도는 각각 900·700토큰입니다([`fortune.go:909`](../internal/application/fortune.go), 422-425행).

추정 원인은 두 가지입니다.

- 답변 모델(`deepseek-v4.1-flash`)의 생각(reasoning) 토큰이 한도를 같이 쓰고 있을 수 있습니다.
- 프롬프트가 요구하는 항목 수에 비해 한도가 작을 수 있습니다.

할 일:

1. 운세 생성 호출을 `Effort: "none"`으로 보내 생각 단계를 끄거나, 한도를 올립니다. 요약 호출은 이미 같은 이유로 `none`을 씁니다([`indexing.go:683-684`](../internal/memory/engine/indexing.go)).
2. `finish_reason=length`이면 잘린 글을 그대로 보내지 않습니다. 한 번 더 짧게 요청하거나 마지막 완결 문장까지만 보냅니다.
3. 3.4의 태그 형식은 잘려도 앞쪽 항목이 살아남는 순서로 둡니다.

### 3.4 운세 새 모습

모델이 `KEY: 값` 태그 줄(키는 영어 고정, 값은 사용자 언어)로 쓰고, Go가 embed를 조립합니다. 오늘의 운세 예시는 다음과 같습니다.

```
SCORE: 82
SUMMARY: 총평 한두 문장
WORK: … / MONEY: … / LOVE: … / HEALTH: …
DO: 추천 1 | 추천 2
AVOID: 주의 1
LUCKY_COLOR: … / LUCKY_ITEM: … / LUCKY_TIME: …
```

```
┃ 🔮 오늘의 운세
┃ ○○님 · 10월 15일 (수)
┃ ▰▰▰▰▰▰▰▰▱▱  82/100
┃ 총평 두 문장
┃ 💼 일·학업 … / 💰 재물 … / 🤝 관계 … / 🌿 컨디션 …
┃ ✅ 이렇게 해보세요 (필드)   ⚠️ 조심할 점 (필드)
┃ 🎨 행운의 색 | 🎁 행운 아이템 | ⏰ 행운의 시간   (inline 3열)
┃ 일진 乙巳 · 염소자리 · 오늘 남은 조회 2회        (푸터, 코드가 가진 사실)
```

- **파싱은 보낼 때 합니다.** 캐시에는 원문을 그대로 저장해서 마이그레이션이 필요 없습니다. `SCORE`와 `SUMMARY`가 없거나 인식한 키가 2개 미만이면 지금처럼 원문을 본문에 넣는 방식으로 되돌아갑니다. 그래서 지금보다 나빠지지 않습니다.
- **종류별 키**
  - 상세: 시간대별(아침·낮·저녁), 추천 3, 주의 2, 행운 숫자, 한 줄 요약
  - 이번 달: 초·중·하순, 주목 날짜
  - 올해: 1~4분기, 좋은 시기·주의 시기
  - 아침: 인사, 점수, 총평, 주의, 행운
  - 순위: `RANK: 순위 | 별자리 번호 | 코멘트 | 색 | 숫자` 12줄. 별자리 이름은 번호를 받아 `locales`에서 바꿉니다.
- **점수 막대**: 장식입니다. 숫자를 늘 함께 씁니다. 낮은 점수에 빨강을 쓰지 않습니다(불안 조성 금지 규칙). `▰▱`의 폭은 실기기에서 확인합니다.
- **이모지**: 제목과 섹션 머리글에만 씁니다. 모델이 쓰는 값에는 넣지 않습니다.
- **공개 채널 3줄 요약**: 구조화하지 않습니다. 푸터의 "남은 조회 횟수"는 공개 응답에서 뺍니다. 개인 사용량이 남에게 보이기 때문입니다(결정 D-9).
- **아침 DM 제목**: `2026-10-15` 대신 "10월 15일 (수)"로 씁니다. 요일은 기존 `reminders.weekday.*`를 재사용합니다.
- **등록 카드**: 값이 한 줄에 들어가면 inline, 아니면 non-inline으로 둡니다. 명령 안내는 푸터에서 본문 마지막 줄로 옮깁니다(백틱 문제 해결).

### 3.5 공지 새 모습(1단계: embed)

```
┃ 📚 학교 공지 3건
┃ 10월 15일 (수) · ○○대학교 학부 3학년
┃ **⏰ 할 일 · 1건**
┃ **[장학금 신청 안내](url)**
┃ 마감 **10/20 (D-5)** · 장학
┃ **✨ 기회 · 1건**
┃ [해커톤 참가자 모집](url)
┃ 10/13 · 대회
┃ **📄 참고 · 1건** …
 [⏸ 알림 중지] [⚙ 설정 보기]   (선택)
```

- 중요도 띠별로 묶고 머리글에 뜻을 글자로 적습니다. 그러면 푸터의 범례가 필요 없어집니다. 지금은 `/공지` 맞춤 보기에 푸터가 없어서 아이콘 뜻을 알 수 없습니다.
- 마감일을 둘째 줄 맨 앞에 두고 D-day를 붙입니다. 날짜는 `MM/DD`로 씁니다. 둘째 줄의 공백 들여쓰기는 없앱니다.
- 편입 공지는 대학별로 묶습니다. 면책 문구는 푸터에서 본문 끝 작은 글씨로 옮기고, 푸터에는 발송 시각(`Timestamp`)만 둡니다.
- 4096자를 넘으면 띠 머리글 단위로 끊습니다. 지금 `chunkText`는 줄 단위로 끊어서 머리글이 항목과 떨어질 수 있습니다.
- **2단계(선택)**: 공지 DM에만 Components V2를 씁니다(항목마다 [열기] 버튼, 구분선). `discordgo v0.29.0`이 지원하지만 렌더러가 하나 늘고, embed로 되돌아가는 대비책이 필요합니다(결정 D-7).

## 4. 콘솔: 다른 페이지로 이동이 가끔 안 됨

### 4.1 이동 경로

1. 사이드바 링크를 클릭하면 문서 수준 클릭 처리기가 `navigate()`를 부릅니다([`router.svelte.ts:200-210`](../internal/transport/web/ui/src/lib/router.svelte.ts)).
2. 미저장 확인(guard)을 거쳐 `pushState`와 `route` 상태를 바꿉니다(`router.svelte.ts:59-79`). 모션이 허용되면 `startViewTransition` 안에서 바꿉니다.
3. `App.svelte`의 `$effect`가 경로에 맞는 페이지를 lazy import합니다. 다 받으면 `page`를 바꾸고 `{#key page.C}`로 다시 그립니다([`App.svelte:65-105`, `134-142`](../internal/transport/web/ui/src/App.svelte)).

### 4.2 원인 후보(코드에서 구조 확인, 실제 발생은 미확정)

| 순위 | 후보 | 확인한 사실 | 언제 생기나 |
|---|---|---|---|
| A | **새 페이지를 받는 동안 이전 화면이 표시 없이 그대로 남음** | import 중에는 `page.C`를 지우지 않고, `page.C`가 있으면 로딩 표시보다 먼저 그립니다(`App.svelte:134-142`). import와 CSS preload에 시간 제한이 없습니다(`route-load.ts`). | 처음 가는 페이지의 JS·CSS 응답이 느리거나 멈출 때입니다. 주소창과 사이드바는 새 페이지인데 본문은 이전 페이지입니다. |
| B | **같은 페이지에서 쿼리만 바뀌면 탭·섹션이 안 바뀜** | 페이지가 `let tab = $state(route.query.get('tab'))`처럼 처음 한 번만 읽습니다(`Logs.svelte:21`, `Settings.svelte:31-32`, `Blocks.svelte:36-37`, `Memory.svelte:36-37` 등). 컴포넌트 key는 컴포넌트 함수뿐입니다. | 명령 팔레트로 `/settings?section=…`, `/logs?tab=…`에 가거나, `/index`(→`/blocks?view=settings`) 리다이렉트, 뒤로·앞으로 이동할 때입니다. 상세 페이지(Room·Tool·Block)끼리 이동하면 일부 상태가 이전 대상의 것으로 남습니다. |
| C | **미저장 확인 Promise가 끝나지 않음** | `SaveBar.svelte`의 `ask()`는 대기 중인 resolver를 정리하지 않고 덮어씁니다. 정리(cleanup)에서도 끝내지 않습니다. `navigate`의 `.catch`는 오류를 조용히 삼킵니다(`router.svelte.ts:78`). | 미저장 변경이 있는 Settings·Usage·Tool·Room에서 빠르게 두 번 이동하거나, 확인창이 떠 있는 중에 세션 만료(401)로 `/login` 이동이 겹칠 때입니다. |
| D | 업데이트 뒤 열린 탭의 옛 chunk가 사라짐 | 없는 `/assets/*` 요청에도 `index.html`을 200으로 줍니다([`spa.go:53-78`](../internal/transport/web/spa.go)). | 배포 전에 연 탭에서 아직 안 가 본 페이지로 갈 때입니다. 보통은 재시도 화면이 뜹니다. |
| E | 큰 목록 계산이 메인 스레드를 점유 | Blocks의 채널×블록 탐색, Memory의 전체 목록, Settings의 설정 깊은 복사가 동기로 돕니다. | 데이터가 많은 Blocks·Memory 페이지입니다. |
| F | View Transition 실패 시 주소와 상태가 어긋남 | 이동 기록을 먼저 바꾸고 화면 상태는 transition 콜백 안에서 바꿉니다. 실패를 관찰하지 않습니다(`router.svelte.ts:48-73`). | 모션이 허용된 상태에서 빠르게 연속 클릭할 때입니다. |

이미 막혀 있는 것도 있습니다. A→B로 이동한 뒤 A의 import가 늦게 끝나 B를 덮는 경쟁 조건은 generation과 path 검사로 방어됩니다(`App.svelte:98,101`).

### 4.3 수정 설계

- **A**
  - 진행 중인 이동을 `{id, target, status, startedAt}`로 들고 있습니다. 이전 페이지가 있어도 대상 로딩 표시(상단 진행 막대 등)를 보여 줍니다.
  - 일정 시간(예: 8초)이 지나면 "다시 시도 / 새로고침"을 띄웁니다. 늦게 끝난 import가 다른 이동을 덮지 못하게 id로 막습니다.
- **B**
  - 쿼리에서 오는 값은 `$derived(route.query…)`로 읽거나, route에서 local로 동기화합니다.
  - 편집 중인 값은 대상 엔터티가 바뀔 때만 초기화합니다. 상세 페이지 key에 pathname을 넣는 임시 처리는 쿼리 동기화와 별개입니다.
- **C**
  - 확인 요청을 하나로 직렬화합니다. 새 요청이 오거나 컴포넌트가 사라지면 이전 요청을 `false`로 끝냅니다.
  - guard를 소유자 토큰으로 등록·해제해서, 이전 페이지의 cleanup이 새 페이지의 guard를 지우지 못하게 합니다.
  - `.catch`에서 조용히 삼키지 말고 진단 기록과 안내를 남깁니다.
- **D**: 없는 `/assets/*`는 404로 응답합니다. 앱은 `vite:preloadError`를 받으면 "새 버전이 있습니다 → 새로고침"을 띄웁니다. 미저장 변경이 있으면 자동 새로고침하지 않습니다.
- **E, F**: 성능 기록으로 긴 작업을 먼저 찾습니다. transition 실패 시에도 상태가 마지막으로 승인된 이동과 같게 맞춥니다.

### 4.4 진단(같이 넣기)

이동마다 `navigationId`를 붙이고 클릭 → guard → history → import → render 단계와 시간을 메모리 링 버퍼(50~100건)에 남깁니다. 개발 진단 내보내기로 꺼낼 수 있게 합니다.

- 쿼리·파라미터 값, 사용자 ID, 오류 원문은 넣지 않고 경로 패턴(`/rooms/:guild/:channel`)만 남깁니다.
- "N초 동안 이동이 끝나지 않음"이나 "주소와 화면 불일치"를 감지하면 묶어서 표시합니다.

다음에 증상이 생기면 이 표로 원인을 좁힙니다.

| 보이는 것 | 원인 |
|---|---|
| 주소·사이드바는 새 페이지, 본문은 이전 페이지, import 미완료 | A |
| 쿼리만 바뀌고 탭이 그대로 | B |
| 주소도 그대로, 확인 대기 중 | C |

### 5.11 기다리는 동안 안내·팁

**목표**: 답이 늦어질 때 사용자가 "안 듣고 있나?" 하고 다시 묻지 않게 하고, 그 시간에 마사몽이 할 수 있는 일을 알려 줍니다. 안내는 답이 나가면 사라집니다.

**모양**

```
(사용자 메시지에 답장으로, 알림 없음)
✍️ 답을 쓰고 있어요…
-# 💡 그거 아세요? "매일 아침 8시에 날씨 알려줘"처럼 말하면 예약해 둘 수 있어요.
```

- 진행 단계를 알 수 있으면 첫 줄을 바꿉니다: "🔎 웹에서 찾고 있어요…", "🧠 예전 대화를 떠올리는 중…", "🎨 그림을 그리는 중…". 이를 위해 `ChatInput`에 `Progress func(stage string)` 콜백을 두고, 도구 루프가 도구를 부를 때와 기억 검색을 시작할 때 부릅니다. 단계 이름만 넘기고 도구 인수·내용은 넘기지 않습니다.
- 팁은 둘째 줄의 작은 글씨(`-#`)로 씁니다. 렌더링은 실기기에서 확인합니다. 안 되면 일반 글씨 한 줄로 둡니다.

**언제 띄우나**

- 첫 응답 지연 기준(예: 4초)을 넘었을 때만 띄웁니다. 짧은 답은 지금처럼 "입력 중…"만 보입니다.
- 같은 사람에게는 10분에 한 번까지만 띄웁니다. 대화가 빠르게 오가는 채널에서 안내가 쌓이지 않게 하기 위해서입니다.
- 이어 말하기(follow)로 답하는 턴, 스레드 안, 슬래시 명령에도 띄울지는 결정 W-3으로 남깁니다. 슬래시 명령은 Discord가 이미 "생각하는 중…"을 보여 주므로, 지연 응답(deferred) 메시지를 팁으로 고치는 방식이 자연스럽습니다.
- 채널 설정 `conversation.waiting: off | status | tips`를 둡니다. status는 안내만, tips는 안내와 팁입니다. 기본값은 결정 W-1입니다. AGENTS.md 규칙대로 콘솔 채널 설정 화면(Room)에서 바꿀 수 있어야 합니다.

**답이 나가면 어떻게 없애나**

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 안내를 알림 없이(`SUPPRESS_NOTIFICATIONS`, @silent) 보내고, 답은 새 메시지로 보낸 뒤 안내를 지움 | 휴대폰 알림에 실제 답이 뜹니다. "(수정됨)" 표시가 없습니다. | 메시지가 잠깐 둘 보였다가 하나가 사라집니다. |
| B. 안내 메시지를 답 내용으로 고침(edit) | 화면이 깔끔하고 위치가 그대로입니다. | 알림이 안내 문구로 이미 갔고, 고쳐도 새 알림이 없습니다. "(수정됨)"이 붙습니다. 여러 메시지로 나눠 보내는 bubbles와 안 맞습니다. |

**추천은 A**입니다. 답 전송이 성공한 뒤에 안내를 지워서 빈 화면이 생기지 않게 합니다. 답이 실패하면 안내를 실패 안내로 바꾸거나 지웁니다.

지우기가 실패할 때(권한 부족 등)를 대비해, 다음 시작 때 남은 안내를 정리하는 기록을 둡니다. `delivery_ledger` 옆에 안내 메시지 ID를 저장합니다.

**팁 문구**

- `locales/*.json`에 `waiting.tip.<id>` 형식으로 40~60개를 둡니다. 한국어·영어를 먼저 쓰고, 다른 언어는 영어로 대신합니다.
- 각 팁에 관련 기능을 붙입니다(`tool: weather.query`, `command: fortune` 등). **지금 그 채널에서 실제로 쓸 수 있는 기능의 팁만** 고릅니다. 고르는 기준은 도움말과 같아서, 52ec9522의 `help`/`command_only` 판단을 재사용합니다. 꺼진 기능을 소개하면 안 됩니다.
- 같은 사람에게 최근에 보여 준 팁은 피합니다(최근 10개를 메모리에 기억). 일반 팁(대화 기억, 스레드, 개인정보 명령 등)과 기능 팁을 섞습니다.
- 운영자가 콘솔에서 팁을 끄거나 자기 팁을 더할 수 있게 할지는 결정 W-2입니다. 더한다면 Action(`waiting.tips.list/set`)과 GUI를 함께 만듭니다.
- 예시: 날씨·장소 검색, 예약 알림과 반복, 운세 구독, 투표, 그림 그리기, 링크 요약, "기억해 줘"/"잊어 줘", `!내기억`, 스레드로 길게 얘기하기, 이름만 불러도 답함, 공지 구독.

**지켜야 할 것**

- 안내 메시지는 기억 수집, 백필, 끼어들기 관찰, 이어 말하기 판단, 답장 기록(`reply_messages`)에서 빼야 합니다. 봇 메시지라 대부분 걸러지지만, 메시지 ID로 명시적으로 제외하고 테스트로 고정합니다.
- 안내 메시지에는 멘션을 넣지 않고, 답장 대상 사용자에게도 알림이 가지 않게(`allowed_mentions.replied_user=false`) 보냅니다.
- Discord 요청 한도: 턴마다 보내기 1회와 지우기 1회, 단계 문구 수정은 최대 3회·3초 간격입니다. 채널당 5초에 5건 한도 안에 듭니다.
- 비용: 모델 호출이 없어서 추가 비용은 0입니다.

**측정**: 안내를 띄운 턴 수, 띄운 뒤 답까지의 시간, 안내가 떠 있는 동안 같은 사람이 다시 묻거나 "?"를 보낸 비율을 지금과 비교합니다. 대화 기록 `features`에 `waiting_shown`과 지속 시간만 남깁니다.
