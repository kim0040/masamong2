# 문제 해결 (FAQ & Troubleshooting)

**한국어** | [English](https://github.com/kim0040/masamong2/wiki/Troubleshooting)

문제가 발생했을 때는 가장 먼저 터미널에서 다음 두 명령어를 실행하여 시스템 상태를 점검하세요:

```bash
masamong status    # 백그라운드 서비스 데몬 구동 여부 확인
masamong doctor    # API 키, 외부 공급자, Discord Gateway, 권한, 스토리지 무결성 종합 진단
```

유지보수 복구 중에도 `masamong status`는 데몬이 실행 중이라고 표시합니다(JSON에서는 `ready:false`). 여기에 `maintenance:true`와 한 줄 `message`가 포함되며 `masamong runtime status`도 같은 필드와 문구를 보여 줍니다. `masamong doctor` 역시 유지보수 상태를 명시합니다. `masamong open`은 복구 안내를 엽니다.

관리 콘솔의 **홈** 알림 센터와 **대화 기록(`/turns`)** 화면을 확인하면 봇이 응답을 생성한 과정이나 응답을 건너뛴 상세 원인을 실시간으로 파악할 수 있습니다.

## 봇이 메시지에 응답하지 않을 때

다음 체크리스트를 순서대로 점검해 보세요:

| 점검 항목 | 원인 및 해결 방법 |
|---|---|
| Discord 게이트웨이 연결 상태 | 관리 콘솔의 **연결 → Discord** 상태가 "연결됨"인지 확인합니다. 아니라면 `masamong doctor`로 경우를 구분합니다. 게이트웨이가 READY/RESUMED를 기다리는 동안 `discord: pending`에 `gateway_connecting`이 나옵니다. `gateway_retrying`(시도 횟수, 마지막 오류, 다음 시각이 든 `discord_startup` 항목 포함)이면 시작할 때 Discord나 네트워크에 닿지 못한 것입니다. 첫 연결은 1초에서 최대 30초 간격으로 스스로 재시도합니다. 토큰 거절이나 Message Content Intent 누락(종료 코드 4014)은 재시도하지 않고 `discord: error`와 `gateway_start_failed`를 표시하므로, 토큰을 고치거나 포털에서 Intent를 켠 뒤 `masamong restart`를 실행합니다. 나중에 끊긴 연결은 스스로 이어 붙고, 알림·운세·공지·운영자 알림도 재시작 없이 계속됩니다. 연결됨으로 보이는데 봇이 답이 없다면 **연결 → Discord**의 "연결 상태 점검"을 봅니다. 하트비트 응답이 약 2분 넘게 없으면 "확인 필요"로 표시되고 `masamong doctor`도 `discord: degraded`(`gateway_stale`) 경고를 냅니다. 몇 분이 지나도 그대로면 봇을 다시 시작하세요. 마지막 이벤트 시각은 참고용일 뿐이며, 조용한 서버에서 오래돼도 정상입니다. 이 점검은 읽기 전용이라 스스로 재연결하지 않습니다(재연결은 DiscordGo가 맡습니다). |
| 메시지 본문 읽기 권한 | 설정의 `discord.message_content: true` 설정과 함께 Discord Developer Portal에서 **Message Content Intent**가 활성화되어 있어야 멘션 인식, `!명령어`, 대화 수집이 동작합니다. (슬래시 명령어는 본 권한 없이도 동작) |
| 채널별 응답 모드 설정 | 콘솔의 **서버·방** 메뉴에서 대상 채널의 응답 모드가 `mention` 또는 `always`로 설정되어 있는지 확인합니다. `command`나 `off`인 경우 일반 일상 대화에는 응답하지 않습니다. |
| 봇 호출 키워드 및 멘션 | `mention` 모드에서는 설정의 `instance.bot_names`에 등록된 이름으로 부르거나, @멘션 또는 봇 메시지에 직접 답장(Reply)했을 때만 응답합니다. |
| Discord 채널 권한 누락 | 콘솔의 **서버·방 → 권한** 탭에서 필수 권한(채널 보기, 메시지 보내기, 링크 첨부, 메시지 기록 보기)이 누락되지 않았는지 점검합니다. |
| 시스템 전체 일시 중지 여부 | 콘솔 상단에 "전체 일시 중지됨" 배너가 표시되어 있다면 일시 중지를 해제합니다 (`masamong runtime pause --paused false`). |
| 한도·예산 | **대화 기록**에서 턴 결과가 "limited"나 "budget"이면 일일 한도나 월 예산에 닿은 것입니다. **비용·한도**에서 확인하세요. 봇을 부른 사람에게만 예산이나 한도를 밝히지 않는 중립적인 안내를 그 사람의 언어로 보냅니다. 채널당 1분에 한 번, 같은 채널의 사람당 5분에 한 번으로 제한합니다. 답변을 꺼 둔 방은 조용합니다. |
| 방 대기열 가득 참 | 로그에 `too many replies waiting in this channel`이 보이면 한 방에 메시지가 몰린 것입니다([동시 처리와 성능](https://github.com/kim0040/masamong2/wiki/동시-처리와-성능)). |
| 모델 API 오류 | 턴 상세에서 공급자 오류(401 Unauthorized, 429 속도 제한 등)를 찾고, **연결 → 모델**에서 키를 확인합니다. 콘솔 API에서는 키가 없거나 거절되었거나 공급자가 연결되지 않은 경우를 HTTP 424로 답합니다(502는 공급자가 실제로 답하지 못했을 때만 씁니다). |

## 슬래시 명령어(`/`)가 Discord에 표시되지 않을 때

- 설정 파일에서 `discord.register_commands: true`로 설정되어 있는지 확인합니다.
- Discord 전역(Global) 슬래시 명령어 등록은 Discord 서버 전파에 최대 1시간까지 지연될 수 있습니다. 특정 서버에서 즉시 테스트하려면 `discord.guild_ids`에 해당 서버 ID를 지정하세요.
- 비활성화된 도구의 슬래시 명령어는 목록에서 자동으로 제외됩니다.
- 설정의 `instance.expected_bot_id`와 실제 연결된 봇의 ID가 불일치하는 경우 명령어 등록이 안전하게 거부됩니다 (시스템 로그 확인).

## 봇이 "그건 지금 안 돼"라고만 하거나 날씨·주가·검색을 못 할 때

그 도구의 API 키가 없거나, 하루 한도를 넘었거나, 공급자가 응답하지 않는 상태입니다. 콘솔의 **도구** 화면에서 도구마다 지금 답할 수 있는지와 이유(키 없음, 한도, 연습 모드 등)를 확인하고, **연결** 메뉴에서 키와 오늘 사용량을 봅니다. 국내 날씨는 기상청 키가 없어도 Open-Meteo로 대신 답합니다.

이때 봇의 동작:

- 대화 중이면 "지금은 안 된다"고 한마디만 하고, 키·설정·오류 코드 같은 관리자용 말은 하지 않은 채 대화를 이어 갑니다. 값을 지어내지 않습니다.
- `!시세`, `/places` 같은 **명령**이 답을 못 주면 오류 카드 대신 같은 메시지로 대화를 이어 갑니다. 실패한 도구는 다시 부르지 않고, 다른 도구(시세 대신 웹 검색 등)를 쓰거나 대화로 받습니다. 권한이 없을 때, 대화를 끈 방(응답 안 함), 본인에게만 보이는 명령은 기존 카드 그대로입니다.
- `!도움말`·"뭐 할 수 있어?"는 지금 답할 수 있는 도구만 안내합니다.

## 응답 생성 지연(응답 속도 저하)이 발생할 때

관리 콘솔의 **대화 기록** 메뉴에서 턴별 단계별 소요 시간(플래너, 도구 호출, 기억 검색, 답변 생성)을 분석합니다:

- **모델 답변 생성이 느린 경우**: LLM 공급자 측의 네트워크 지연일 가능성이 높습니다. 응답 속도가 빠른 경량 모델(예: `deepseek-v4.1-flash`)로 교체하거나 공급자 헬스 상태를 확인하세요.
- **기억 검색 단계가 느린 경우**: 재순위(Rerank) 모델 호출에 시간이 소요되는 것이므로, `memory.retrieve: hybrid` 모드로 변경하여 순수 하이브리드 검색으로 전환하면 속도가 대폭 개선됩니다.
- **모델이 아예 멈추는 경우**: 역할마다 제한 시간이 있어(기본 의도 파악 30초, 답변 90초) 넘으면 다른 대화 모델이 이어받습니다. 빈 답이 와도 실패로 보고 다른 모델로 넘깁니다. 오래 생각하는 모델이면 콘솔 **연결 → 모델 → 단가 설정**에서 제한 시간(`models.<역할>.timeout_seconds`, 5–600초)을 늘리세요.
- **여러 채널이 동시에 활성화될 때만 느린 경우**: 동시 처리 한도(`limits.max_concurrent_turns`)를 상향 조정합니다. (단, 모델 API 공급자의 초당 호출 한도(RPM)를 사전에 확인하세요.)

## 모델 사용 비용이 예상보다 많이 발생할 때

- 관리 콘솔의 **비용·한도** 메뉴에서 작업 유형별(대화 생성, 임베딩, 요약, 재순위) 비용 누적 현황을 분석합니다.
- 대화 색인 시 발생하는 비용의 대부분은 단락 요약 생성에서 비롯됩니다. 비용을 절감하려면 `memory.summaries: false`로 설정하여 순수 임베딩 검색으로 운영하세요.
- 상시 응답(`always`) 채널이 있다면 `chat.respond` 코어에 쿨다운 시간(예: 3초)과 사용자별 일일 호출 한도(예: 200회)를 설정하세요 ([도구와 한도](https://github.com/kim0040/masamong2/wiki/도구와-한도)).
- `limits.monthly_budget_usd` 설정은 월간 지출 상한입니다. 한 번뿐인 설정 비용 때문에 이번 달 예산이 소진됐다면 **비용·한도**에서 계산 기준을 지금으로 초기화하세요. 일별 기록은 남고 제공자 사용량·키 한도는 바뀌지 않습니다.

## 관리 콘솔 접속이 되지 않을 때

- 터미널에서 `masamong open` 명령을 실행했을 때 브라우저가 자동으로 열리지 않는다면 터미널에 출력된 보안 1회용 링크를 복사하여 브라우저에 직접 붙여넣으세요.
- 원격 서버 환경이라면 내 컴퓨터에서 `masamong connect user@host` 명령을 통해 SSH 터널을 생성하여 접속하세요. 서버의 `masamong` 바이너리가 표준 PATH에 없다면 `--remote_command`로 절대 경로를 지정합니다.
- 콘솔이 다시 로그인하라고 하면(로그아웃 뒤, 또는 세션이 끝났을 때) 로그인 화면이 내 시스템에 맞는 명령을 보여 줍니다. bash·zsh에서는 `masamong open`, PowerShell에서는 `& "C:\...\masamong.exe" open`이고 `cmd.exe`용 형태가 옆에 함께 나옵니다. 토큰은 데이터 폴더의 `admin/web-token` 파일(Windows는 `%APPDATA%\Masamong\admin\web-token`)이며 `masamong admin token`으로 출력할 수 있습니다. 가벼운 `/lite` 화면은 토큰을 주소가 아니라 요청 본문으로 보내는 양식으로 로그인하므로 브라우저 기록과 로그에 남지 않습니다.
- 프론트엔드 UI 렌더링에 문제가 있을 경우 경량 관리 페이지(`http://127.0.0.1:8787/lite`)에 접속하여 기본 상태 점검 및 재시작 작업을 수행할 수 있습니다.
- 8787 포트가 이미 다른 서비스에서 사용 중이면 서비스가 비어 있는 로컬 포트를 스스로 잡고(로그에 경고가 남음) `masamong open`이 그 주소를 찾아 줍니다. 주소는 데이터 폴더의 `daemon.json`에도 있습니다. 포트를 고정하려면 설정의 `admin.web.bind`를 다른 유휴 로컬 포트(예: `127.0.0.1:8790`)로 바꿉니다.

## Windows에서

| 증상 | 원인과 해결 |
|---|---|
| 설치 직후 `masamong`이 "인식할 수 없는 명령" | 설치 스크립트가 사용자 PATH에 폴더를 넣었지만, 이미 열려 있던 창은 예전 PATH를 갖고 있습니다. **새** PowerShell을 열거나 `& "$env:LOCALAPPDATA\Programs\Masamong\masamong.exe" open`을 실행하세요(설치가 끝날 때 이 줄을 알려 줍니다) |
| `install.ps1`이 "스크립트 실행이 비활성화되어 있다"며 막힘 | `powershell -ExecutionPolicy Bypass -File .\install.ps1`로 실행하세요 |
| 설치가 "tray or daemon processes did not exit"로 멈춤 | `masamong.exe`나 `masamongd.exe`를 아직 붙들고 있는 것이 있습니다. `masamong stop`으로 서비스를 끄고 트레이 아이콘을 닫은 뒤 작업 관리자에서 `masamong`·`masamongd`가 남았는지 확인하고 다시 실행하세요. 설치 스크립트는 먼저 최대 45초 기다립니다 |
| `$env:MASAMONG_..._KEY`나 `setx`로 넣은 키를 못 찾음 | 변수는 설정한 **뒤에 시작한** 프로세스에만 전달됩니다. `masamong stop` 뒤 변수가 있는 창에서 `masamong start`를 하거나, `[Environment]::SetEnvironmentVariable('이름', '값', 'User')`로 사용자 변수를 만들고 새 창에서 서비스를 시작하세요. 트레이 아이콘이나 로그인 시 자동 시작으로 뜬 서비스는 터미널에서 설정한 변수를 보지 못합니다. 키를 콘솔에 입력하면 이런 일이 없습니다 |
| 알림이나 일일 한도가 9시간씩 어긋남 | 프로그램이 IANA 시간대 데이터베이스를 자체로 갖고 있어서 현재 버전에서는 일어나지 않아야 합니다. `masamong doctor`가 불러올 수 없는 `i18n.timezone`이나 기억 색인 시간대를 알려 주니 이름을 고치세요. 예전 버전이면 업데이트하세요 |
| `masamong stop` 뒤에도 트레이 아이콘이 남음 | 현재 버전은 `masamong stop`이 그 데이터 폴더의 트레이도 함께 닫습니다. 예전 버전이면 아이콘 메뉴에서 종료하거나 작업 관리자에서 `masamong.exe`를 끝내세요 |
| 키가 어디에 저장됐는지 모르겠음 | 콘솔에서 입력한 키는 Windows 자격 증명 관리자(`masamong/<계정>` 항목. 제어판 → 자격 증명 관리자 → Windows 자격 증명에서 볼 수 있음)로 갑니다. `MASAMONG_SECRET_STORE=file`이면 `%APPDATA%\Masamong\secrets` 아래 파일로 저장합니다. 기존 `keychain:`·`file:` 참조는 계속 동작합니다 |
| 다른 드라이브나 공유 폴더의 `--data-root` | 서비스가 시작할 때 폴더를 내 계정·SYSTEM·Administrators로 제한합니다. 설정하지 못하면(예: Windows 권한이 없는 일부 네트워크 공유) 이유를 출력하고 시작하지 않으니 로컬 NTFS 폴더를 쓰세요 |
| Windows `doctor`에서 하위 항목 권한 경고가 계속 나옴 | ACL 마이그레이션 표식은 모든 하위 항목을 보호한 뒤에만 기록됩니다. 실패한 항목을 보호할 수 있을 때까지 데몬은 시작할 때마다 다시 확인하고 `doctor`에도 데이터 폴더 확인 필요 항목을 계속 표시합니다. 다른 드라이브로 옮긴 폴더를 `mklink /J`로 연결하는 등 데이터 루트 자체가 정션인 경우는 지원하며, 루트 안쪽 재분석 지점은 건너뜁니다 |
| 콘솔이 알려 준 명령을 붙여 넣으면 오류 | 콘솔은 PowerShell용(`& "C:\...\masamong.exe" ...`)과, 다른 경우에는 `cmd.exe`용 명령을 보여 줍니다. 지금 쓰는 창에 맞는 쪽을 쓰세요 |

## 콘솔에 "복구 필요"가 뜰 때 (유지보수 모드)

복원·초기화·프로그램 업데이트를 마무리하지 못했습니다. 데몬은 DB를 열지 않아 봇·스케줄러·기억 워커는 꺼져 있지만, 데몬 자체는 계속 살아 있고 평소 콘솔 주소(`127.0.0.1:8787`, 사용 중이면 비어 있는 로컬 포트)에 **한국어·영어·일본어·중국어·스페인어로 된 읽기 쉬운 복구 안내**를 띄웁니다. `masamong open`이나 트레이의 **열기**가 이 화면으로 갑니다. `masamong status`는 복구 주소에서 데몬이 실행 중이라고 표시하고(JSON에서는 `ready:false`), `maintenance:true`와 한 줄 `message`도 포함합니다. `masamong runtime status`도 같은 필드와 문구를 보여 주며 `masamong doctor`도 유지보수 상태를 명시합니다. 화면에는 무슨 일이 있었는지와 그 상태에서 쓸 수 있는 복구 명령만 나오며, 원래의 기술 오류는 로그에만 남습니다. 루프백 Host에만 답하고 다른 사이트의 쓰기 요청은 거절합니다.

1. **무엇이 걸려 있는지 봅니다.** `masamong status`는 복구 주소에서 데몬이 실행 중이라고 보여 줍니다(JSON에서는 `ready:false`)며 `maintenance:true`와 한 줄 `message`도 포함합니다. 작업 종류·단계·초기화한 대상 수, 지금 쓸 수 있는 `recovery_commands`는 `masamong doctor`, `masamong runtime status`, `masamongd --data-root <폴더> --maintenance status`에서 확인합니다. 봇과 스케줄러는 계속 꺼져 있습니다.
2. **복구 전에 유지보수 데몬을 멈춥니다.** `retry`·`rollback`·`cancel`·`abandon-update`는 데이터 폴더를 혼자 써야 합니다. `masamong stop`을 실행하면 인증된 중지 API를 통해 유지보수 데몬이 종료됩니다. 안내 화면에도 필요한 경우 `--data-root`를 포함한 중지 명령이 나옵니다. `status`와 `doctor`는 읽기만 하므로 데몬을 멈추지 않아도 됩니다.
3. **화면에 나온 명령만 실행합니다.** 명령이 끝나면 `masamong start`로 서비스를 다시 엽니다.
   - `retry`: 끊긴 복원·초기화·업데이트를 이어 갑니다.
   - `rollback`: 가능한 복원·프로그램 업데이트를 이전 DB·설정 또는 이전 프로그램으로 되돌립니다.
   - `cancel`: 실제 파일을 건드리지 않은 작업을 취소합니다. 데이터가 이미 옮겨졌다는 복구 파일이 없을 때만, 읽을 수 없거나 옛 형식인 표식을 직접 살펴보도록 따로 옮깁니다.
   - `abandon-update`: Masamong을 다시 설치한 뒤, 더 이상 자동으로 처리할 수 없는 프로그램 업데이트 저널에 씁니다. `masamongd --data-root <폴더> --maintenance abandon-update [--yes]`는 프로그램 파일은 모두 그대로 두고 저널만 `.masamong-update.abandoned-<시각>.json`으로 옮깁니다. 파일을 지우지는 않습니다. `--yes`가 없으면 `abandon`을 입력해야 합니다. 이전·스테이징 프로그램 파일도 이 기록을 지울 때까지 남습니다.

초기화가 지우기를 시작한 뒤에는 `retry`로 끝내야 합니다. 데이터를 되살리려면 *초기화 전* 백업을 씁니다. 복원이 준비 단계에서 실패해 실제 파일을 하나도 옮기지 않았다면 스테이징 사본을 지우고 실패를 기록한 뒤 현재 데이터로 봇을 계속 실행합니다. 이 경우 복구 화면은 뜨지 않습니다. 새 DB 설치가 커밋된 복원은 옛 파일을 다른 프로그램이 잠가 지우지 못해도 성공입니다. 시작 때와 매시간 정리를 다시 시도하며, 남은 파일은 `doctor`에 표시됩니다. 파일 잠금을 풀고 재시도할 때도 화면에 나온 명령을 따르세요.

업데이트가 끊긴 뒤 감시 프로세스가 실행 가능한 프로그램 한 쌍을 띄우지 못하면 되풀이하지 않고 멈추며 오류를 `logs/daemon.out`에 남깁니다. 이전 프로그램은 새 한 쌍이 온전하다고 확인될 때까지 프로그램 폴더의 숨김 파일 `.masamong*.exe.old-*`(macOS·Linux는 `.masamong*.old-*`)로 보관됩니다. `install.sh`나 `install.ps1`로 다시 설치하면 프로그램만 바뀌고 데이터 폴더는 건드리지 않습니다([설치](https://github.com/kim0040/masamong2/wiki/설치)). 명령 목록은 [CLI 명령어](https://github.com/kim0040/masamong2/wiki/CLI-명령어#복구-명령-masamongd)에 있습니다.

## "이미 실행 중" 또는 데이터베이스 Lock 오류가 발생할 때

동일한 데이터 디렉터리를 대상으로 두 개 이상의 데몬 프로세스가 동시에 실행되려 할 때 발생합니다. `masamong status`로 기존에 실행 중인 데몬 PID를 확인하고 `masamong stop`으로 정상 종료한 뒤 다시 시작하세요. 프로세스가 비정상 종료된 경우라도 파일 락은 데몬 재시작 시 자동으로 안전하게 해제됩니다.

## 서비스가 저절로 다시 시작됐거나, 계속 꺼질 때

아이콘·`masamong open`·`masamong start`로 띄운 서비스는 감시 프로세스(`masamongd --supervise`) 아래에서 돕니다. 서비스가 비정상 종료되면 감시 프로세스가 1초 뒤부터 간격을 늘려 가며 다시 켜고, 다음 기동 때 콘솔 **로그 → 가동 이력**에 "비정상 종료"와 이유(`exit status 2`, `signal: killed` 등)가 남습니다. 운영자 알림을 켜 두었다면 Discord DM으로도 옵니다.

10분 안에 5번 연달아 죽으면 같은 이유로 계속 실패하는 것으로 보고 재시작을 멈춥니다. 이때는:

1. `logs/daemon.out`의 마지막 부분에서 `supervisor:` 줄과 그 앞의 `panic:` / `fatal error:` 줄을 확인합니다.
2. 설정을 바꾼 직후라면 콘솔 **설정 → 변경 기록**이나 `masamong config rollback`으로 되돌립니다.
3. `masamong start`로 다시 켭니다. 켜지면 멈췄던 이유가 알림으로 한 번 더 나옵니다.

## 설정 저장 시 "충돌(Conflict)" 경고가 발생할 때

다른 브라우저 탭, CLI 명령어, 또는 Discord 관리자 명령을 통해 설정이 먼저 수정된 경우 발생합니다. 다른 관리자의 변경 사항을 실수로 덮어쓰지 않도록 보호하는 정상적인 동작입니다. 브라우저를 새로고침하여 최신 구성을 불러온 뒤 수정을 다시 진행하세요. 콘솔에서는 편집 중이던 초안을 최신 설정 위에 내 수정만 얹어 다시 맞춰 줍니다. 명령줄에서 `masamong config apply --file F --base_revision N`을 쓰려면 고치기 시작한 시점의 리비전이 필요합니다(`masamong config show`가 출력). 없으면 `CONFIG_CONFLICT` "expected N got 0"으로 답합니다([설정 레퍼런스](https://github.com/kim0040/masamong2/wiki/설정-레퍼런스)).

## 시스템 로그 확인 방법

- **관리 콘솔**: **로그** 메뉴에서 실시간 스트리밍 로그(SSE) 및 과거 기동 이력 열람
- **CLI 실시간 로그**: `masamong runtime logs`
- **로그 파일 직접 확인**: 데이터 디렉터리 내 `logs/daemon.log`(Windows는 `%APPDATA%\Masamong\logs\daemon.log`. `Get-Content "$env:APPDATA\Masamong\logs\daemon.log" -Tail 50 -Wait`로 따라 볼 수 있음). 로그 파일이 10MiB에 도달하면 `daemon.log.1`~`daemon.log.5`로 자동 로테이션되며 최대 약 60MiB 내에서 디스크 용량을 안전하게 관리합니다.
- 비정상 종료(Panic) 발생 시 `logs/daemon.out` 파일에 Go 런타임 스택 트레이스와 감시 프로세스의 재시작 기록(`supervisor:` 줄)이 남습니다.
- systemd 서비스로 등록하여 운영 중인 경우 저널 로그로 조회 가능합니다: `journalctl --user -u masamong-*`
- 보안 가드레일에 의해 시스템 로그에는 원문 API 키와 데이터베이스 암호가 절대 노출되지 않습니다.

## 자주 묻는 질문 (FAQ)

**Q. Masamong을 완전 무료로 운영할 수 있나요?**
코어 바이너리, SQLite 데이터베이스, 웹 관리 콘솔, 백업/복원, 키워드 검색, 샌드박스 연습 모드는 일체의 비용 없이 완전 무료입니다. LLM 추론, 금융 시세, 유료 검색 API를 연동하는 경우에만 해당 외부 공급자의 종량제 요금이 발생합니다. 날씨 정보(Open-Meteo)는 별도 키 없이 쓸 수 있지만 무료 API는 비상업용이고 출처 표시(CC BY 4.0)가 필요합니다. 주가(Finnhub)·환율(ExchangeRate-API)은 받은 데이터의 공유·재배포를 제한하니 여럿이 보는 방에서 쓰기 전에 약관을 확인하세요([추후 작업](https://github.com/kim0040/masamong2/blob/main/docs/BACKLOG.md)).

**Q. 한 대의 컴퓨터에서 서로 다른 여러 개의 봇을 실행할 수 있나요?**
네, 가능합니다. 데이터 디렉터리를 분리하여 `masamong --data-root /경로/...` 형태로 각각 실행하면 완전히 독립된 인스턴스로 구동됩니다. 이때 콘솔 바인딩 포트(`admin.web.bind`)도 각각 다르게 지정해야 합니다.

**Q. OpenRouter 외에 OpenAI, Gemini, 로컬 vLLM/Ollama 모델도 연동 가능한가요?**
네. 콘솔 **연결 → 공급자 추가**에서 Google Gemini나 OpenAI를 고르고 키를 넣으면, 연결을 확인한 뒤 역할마다 그 공급자의 최신 모델을 추천합니다. 그 밖의 OpenAI 호환 주소(DeepSeek, 로컬 서버 등)는 **기타 OpenAI 호환**으로 이름과 주소를 넣어 추가합니다. Gemini와 OpenAI에는 재정렬(rerank)이 없어 그 역할만 OpenRouter로 두거나, 재정렬 없이 씁니다. 자체 호스팅 모델은 토큰 단가를 0으로 지정해 비용 장부를 관리할 수 있습니다.

**Q. 키를 넣었는데 "연결 시험 실패: timeout"이 나옵니다.**
공급자까지 가는 네트워크가 느리거나 끊긴 경우입니다(키가 틀리면 "키 거절됨"으로 따로 표시됩니다). 잠시 뒤 **연결 시험**을 다시 누르세요. Gemini는 틀린 키에도 400으로 답하는데, 이것도 "키 거절됨"으로 표시됩니다.

**Q. 웹 검색이 "검색 서비스 키가 없습니다"라고 답합니다.**
연결 화면에서 Tavily·Linkup·Exa·Serper·Brave·TinyFish·카카오 중 하나를 추가하고 키를 넣으세요. 여러 개를 넣으면 **도구 → 인터넷 검색**의 순서대로 쓰고, 한 서비스가 실패하면 다음으로 넘어갑니다.

**Q. 여러 사용자가 동시에 대화를 보내면 어떻게 처리되나요?**
서로 다른 채널의 대화 요청은 백그라운드 워커 풀에서 병렬로 동시 처리되며, 동일한 채널 내에서 발생한 대화는 문맥의 일관성을 위해 도착한 순서대로 순차적으로 정확히 응답합니다. 자세한 내용은 [동시 처리와 성능](https://github.com/kim0040/masamong2/wiki/동시-처리와-성능) 문서를 참조하세요.

**Q. Raspberry Pi와 같은 저전력 싱글보드 컴퓨터에서도 원활히 동작하나요?**
네. 64비트 OS는 `linux_arm64`, 32비트 Raspberry Pi OS는 `linux_armv7` 빌드를 공식 지원합니다. `install.sh` 스크립트가 CPU 아키텍처를 자동으로 감지하여 최적의 바이너리를 설치합니다.
