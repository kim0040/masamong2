# 동시 처리와 성능

**한국어** | [English](https://github.com/kim0040/masamong2/wiki/Concurrency-and-Performance)

마사몽은 요청을 하나씩 순서대로 처리하지 않습니다. Discord 메시지, 슬래시 명령, 버튼, 관리 콘솔 요청, 배경 작업(색인·백업)이 **동시에** 처리됩니다. 이 문서는 동시에 무엇이 어떻게 돌아가는지, 얼마나 버티는지, 어떻게 조정하는지 설명합니다.

## 한눈에

| 상황 | 동작 |
|---|---|
| 서로 다른 채널에 동시에 메시지가 옴 | **병렬로** 답함 |
| 같은 채널에 연달아 메시지가 옴 | **도착 순서대로** 하나씩 답함. 두 번째 답은 첫 번째 대화를 알고 답함 |
| 동시에 답하는 수 | 최대 `limits.max_concurrent_turns` (기본 **8**). 넘치면 순서대로 기다림 |
| 한 채널에 메시지가 몰림 | 실행 중 1개 + 대기 4개까지 받고, 그 이상은 **조용히 건너뜀** (도배 방지) |
| 슬래시 명령·`!명령` | 각각 독립적으로 병렬 처리 |
| 여러 사람이 투표 버튼을 동시에 누름 | **모든 표가 기록됨** |
| 대화 중에 콘솔에서 설정 변경 | 진행 중인 답은 오류 없이 끝나고, 새 설정은 늦어도 다음 답부터 적용 |
| 콘솔과 Discord에서 동시에 설정 변경 | 차례로 적용, 서로 덮어쓰지 않음 |
| 서비스 중지·재시작 | 진행 중인 답을 최대 15초 기다린 뒤 DB를 닫음 |

## 답변 하나가 지나가는 길

```
Discord 메시지
  → 채널 차례 기다리기 (같은 채널의 앞선 답이 끝날 때까지)
  → 전체 동시 실행 자리 기다리기 (max_concurrent_turns)
  → 한도·예산 확인 (앞선 답이 쓴 비용까지 반영된 상태)
  → 플래너 모델 → 도구 실행 + 기억 검색 (함께) → 답변 모델
  → Discord로 전송, 대화 기록 저장
```

한 답변 안의 서로 다른 도구 호출(날씨와 주가 등)과 기억 검색은 한 번에 최대 4개까지 **함께** 실행합니다. 같은 도구 이름의 호출은 모델 순서대로 하나씩 실행해 사용량·cooldown의 예약 순서를 지킵니다. 결과도 모델 순서대로 모읍니다. 취소 후 아직 시작하지 않은 호출은 `cancelled` 결과를 남기고 호출 예약을 돌려줍니다. 패닉은 해당 호출만 `unavailable`로 끝내며 장부에는 부분 비용·실패 분류까지 한 번 기록합니다.

플래너·루프·답변 모델은 시작할 때 호출 수를 예약하고 끝날 때 비용을 더합니다. 선택 작업의 한도는 모델·계획 순서대로 판정하며, 돈 한도가 있으면 실행 중인 모델이 모두 끝날 때까지 취소 가능한 상태로 기다려 비용을 반영합니다. 그래서 기본 설정(`chat.tool_mode: loop`, `limits.per_request_budget_usd: 0.03`)에서는 루프 1라운드의 도구가 함께 출발한 플래너 모델이 끝난 뒤에 시작합니다. 늘어나는 시간은 두 모델의 응답 시간 차이만큼이고, 플래너가 재시도 대기에 걸리면 그만큼 길어집니다(의도한 보수적 동작). 돈을 쓰는 도구도 끝난 뒤 다음 호출을 판정합니다. 따라서 하나씩 실행할 때보다 더 많은 선택 호출을 허용하지 않습니다.

기억 검색은 플래너 결과가 나오면 도구 루프 전체를 기다리지 않고 시작합니다(루프가 아직 돌 때). 호출 수 한도에는 걸리지 않고 돈 한도만 따릅니다. 돈 한도가 있든 없든, 그 순간 실행 중인 모델 호출과 유료 도구가 끝난 뒤에 출발합니다. 첫 호출의 값을 알아야 남은 루프의 값을 어림할 수 있기 때문입니다. 재순위 예산을 판단할 때 끝난 루프는 쓴 만큼 빼고, 도는 중인 루프는 모든 라운드가 지금까지 가장 비싼 모델 호출만큼 들고 유료 도구가 있으면 수수료도 든다고 치고 뺍니다. `chat.tool_model`이 플래너와 다른 모델이면 값을 어림할 수 없어 루프가 끝난 뒤에 검색합니다. 루프가 첫 라운드에서 실패해 플래너가 다시 계획했는데 기억 판단이 달라지면, 앞선 검색을 취소하고 쓴 비용만 남긴 뒤 새 계획대로 검색합니다. 기억이 켜진 턴은 시작할 때 메시지의 질의 임베딩도 미리 시작합니다. 같은 질의를 묻는 호출은 진행 중인 요청을 함께 기다리고, 플래너가 기억을 고르지 않으면 바로 취소합니다. 이 호출은 턴의 호출 수를 쓰지 않고 호출 기록(임베딩)에는 남습니다. 드라이런·연습 모드, `daily_limit`이 있는 임베딩 공급자, 기억 동의를 철회한 사람의 메시지는 미리 시작하지 않습니다.

외부 서비스(Finnhub, 기상청, 환율, Jina Reader 등)의 1~4개 동시 요청 상한은 프로세스 전체의 공유 governor가 지킵니다. 공급자 종류(설정 항목의 별칭이 아닌 공통 공급자 ID)·기본 호스트·자격 증명의 비가역 해시로 구분하므로 같은 호스트·키의 중복 항목과 여러 Registry·Service가 자리를 공유합니다. 설정 재로드와 상한 변경 뒤에도 이전 Registry의 실행 중 요청은 계속 셉니다. HTTP 시도마다 본문을 닫고 자리를 반환하며 패닉에도 반환합니다. 재시도 대기는 자리 밖에서 합니다. 동시 요청 상한은 초당·분당 호출 수를 보장하는 rate limit이 아닙니다.

한도와 월 예산은 **차례가 온 뒤에** 확인하므로, 동시에 몰린 요청이 한꺼번에 예산을 넘기는 일을 줄입니다. 기다리는 시간도 답변 제한 시간(Discord 답변 180초, 그림 그리기를 포함한 턴 기준)에 포함되고, 기다리는 동안에도 "입력 중…"이 표시됩니다.

## 측정 결과

가짜 모델 서버(호출마다 지연)를 붙인 회귀 테스트로 확인합니다. 모두 `go test -race`로 실행합니다.

| 테스트 | 확인하는 것 |
|---|---|
| `TestChatTurnsInDifferentChannelsRunInParallel` | 6개 채널 동시 → 순서대로 처리한 시간의 절반 미만에 끝남 |
| `TestChatTurnsInOneChannelRunOneAtATime` | 한 채널 5개 → 모델 호출이 겹치지 않음 |
| `TestMaxConcurrentTurnsBoundsModelCalls` | 한도 2 → 동시 모델 호출이 2를 넘지 않음 |
| `TestChannelBacklogRefusesInsteadOfQueueingForever` | 한 채널 9개 동시 → 5개 답, 4개 거절 |
| `TestChatTurnsWhileConfigChanges` | 대화 중 설정 변경 6건 동시 → 경합 없음, 변경 누락 없음 |
| `TestConcurrentPollVotesAreNeverLost`, `TestSimultaneousButtonVotesAllCount` | 동시 투표 12건 → 전부 기록 |

참고 측정: 모델 응답이 0.3초 걸리는 조건에서 채널 4개에 20개 답을 동시에 보내면 약 1초에 끝났습니다(순서대로면 약 12초).

## 조정하기

### `limits.max_concurrent_turns`

동시에 모델을 부르는 답변 수입니다(1–64, 기본 8).

| 규모 | 권장값 | 이유 |
|---|---|---|
| 개인·친구 서버 몇 개 | 4–8 (기본) | 충분하고 비용 폭주를 막음 |
| 활발한 서버 여러 개 | 12–24 | 모델 공급자의 분당 요청 한도(rate limit)를 먼저 확인 |
| 무료·저가 모델 요금제 | 2–4 | 공급자 제한에 걸리면 답이 느려지거나 실패 |

```bash
masamong config show   # 현재 값 확인 후 콘솔 설정 화면에서 변경
```

설정 변경은 바로 반영되며, 이미 실행 중인 답은 영향을 받지 않습니다.

### 도배·비용 방지

동시 처리 한도는 "한꺼번에 몇 개"만 정합니다. **얼마나 자주**는 도구 한도로 정합니다([도구와 한도](https://github.com/kim0040/masamong2/wiki/도구와-한도)).

```bash
masamong tools configure --id chat.respond --cooldown_sec 3 --per_user_per_day 200
```

`always` 채널이 있다면 위처럼 쿨다운을 두는 것을 권장합니다.

## 저장소별 특성

저장소는 SQLite 하나입니다(TiDB는 2026-09-28 운영자 결정으로 비활성, [저장소와 백업](https://github.com/kim0040/masamong2/wiki/저장소와-백업)). 쓰기는 연결 1개로 순서대로 처리하며, 쓰기가 짧아서 병목이 되지 않습니다. 긴 읽기와 백업은 별도 연결에서 합니다.

답변 시간 대부분은 모델 호출(수 초)이고 DB 작업은 밀리초 단위라, SQLite로도 동시 답변이 막히지 않습니다. 모델 호출 중에는 DB 연결을 잡고 있지 않습니다.

## 한 데이터 폴더 = 데몬 하나

한 데이터 폴더는 데몬 하나만 사용합니다(`daemon.lock`). 처리량을 늘리려고 같은 폴더로 데몬을 여러 개 띄울 수는 없으며, 필요하지도 않습니다. 한 데몬 안에서 이미 병렬로 처리합니다. 서로 다른 봇은 서로 다른 데이터 폴더로 운영합니다.

`Running` 확인은 데몬이나 트레이가 잠금을 소유했는지 살펴보고 잠금을 계속 쥐고 있지 않습니다. Unix에서는 확인이 소유권 얻기와 겹칠 때 시작하는 쪽이 잠깐 재시도하므로 상태 확인 때문에 새 프로세스가 중복 실행으로 잘못 종료되지 않습니다.

## Gateway 연결과 종료

Discord의 READY·RESUMED 처리도 답변·명령과 같은 작업 수용 잠금 아래 등록됩니다. 종료를 시작하면 먼저 새 작업을 받지 않도록 한 뒤 이미 수용한 처리가 끝날 때까지 기다리므로, DB를 닫기 전에 연결 이벤트 핸들러도 마무리됩니다.

## 문제가 생기면

- **답이 늦음**: 콘솔 **대화 기록**의 단계별 시간(`timing_ms`)에서 어느 단계가 느린지 봅니다. 대부분 모델 공급자 지연입니다. `queue_wait`(채널 차례와 모델 자리를 기다린 시간), `first_send`(턴 시작부터 첫 말풍선이 올라갈 때까지), `post_send`(전송 뒤 기록 쓰기)도 같이 남습니다. 함께 도는 단계(플래너·도구 루프, 도구·기억 검색)는 턴 기록의 `spans`(턴 시작 기준 시작·끝 ms)와 `waited_on`(플래너와 도구 루프 합류에서 더 늦게 끝난 쪽, `loop` 또는 `planner`)으로 봅니다. `max_concurrent_turns`에 자주 막히면 값을 올리세요.
- **일부 메시지에 답하지 않음**: 대화 기록에서 결과가 "한도 걸림"이고 오류가 `too many replies waiting in this channel`이면 채널 대기열이 가득 찼던 것입니다. 정상적인 도배 방지입니다.
- 그 밖에는 [문제 해결](https://github.com/kim0040/masamong2/wiki/문제-해결)을 보세요.

측정한 처리량·지연·자원 사용량과 규모별 용량 계획은 [부하 테스트와 장기 운영](https://github.com/kim0040/masamong2/wiki/부하-테스트와-장기-운영)에 있습니다.
