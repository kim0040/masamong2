## 1. 벡터를 디스크에도 int8로 저장

**현재**: 조각·요약 벡터를 디스크에 float16으로 저장합니다(4096차원에서 벡터 하나 8 KB, 조각 하나에 두 개). 메모리의 검색 색인은 이미 int8(벡터 하나 4 KB)로 들고 있습니다.

**바꾸면**: 디스크 벡터도 int8(행마다 배율 하나)로 저장합니다.

- 기억 디스크가 메시지 1만 개당 약 27 MB에서 약 17 MB로 줄어듭니다. 백업도 같은 비율로 줄어듭니다.
- 검색은 지금도 int8로 하므로 결과는 사실상 같습니다(점수 차이 약 0.001, 상위 10개 일치 97.8% — 합성 데이터 기준).
- 색인을 불러올 때 float16을 풀어 다시 양자화하는 단계가 없어져 조금 빨라집니다.

**대가**:

- float16 원본이 사라집니다. 되돌릴 수 없고, 되돌리려면 전체를 다시 임베딩해야 합니다(유료).
- 나중에 `models.embed.dimensions`를 줄일 때(Matryoshka 자르기) int8에서 자르게 되어 품질이 조금 더 떨어질 수 있습니다.
- 기존 DB는 한 번 변환해야 합니다(배경 작업, 비용 없음).

## 2. SQLite 디스크 동기화 한 단계 낮추기 (`synchronous=NORMAL`)

**현재**: SQLite 기본값(FULL)이라 커밋할 때마다 WAL을 디스크에 동기화합니다. 메시지 하나를 저장할 때마다 fsync가 한 번 일어납니다.

**바꾸면**: WAL 모드에서 널리 쓰는 NORMAL로 둡니다.

- SD카드(Raspberry Pi)나 HDD처럼 fsync가 느린 디스크에서 쓰기 지연이 크게 줄어듭니다. SSD에서는 차이가 작습니다.
- DB가 깨지지는 않습니다(WAL 모드에서 NORMAL은 손상에 안전).

**대가**: 정전이나 OS 강제 종료 때 **마지막 커밋 몇 개(대개 1초 안쪽)**가 사라질 수 있습니다. 프로세스만 죽는 경우에는 잃지 않습니다.

**결정할 것**: 설정 항목(`storage.sqlite_sync: full | normal`)으로 둘지, 기본값을 바꿀지.

## 3. Windows·Linux 데스크톱 자동 재시작

> **구현함 (2026-09-30)**: 권장안 (가)로 만들었습니다.
> - 아이콘·메뉴 막대·`masamong open`·`masamong start`는 서비스를 `masamongd --supervise`로 띄웁니다. 감시 프로세스가 실제 서비스를 자식으로 돌리고, 0이 아닌 코드로 끝나면(런타임 치명 오류, 메모리 부족, 강제 종료) 1초·2초·4초…최대 1분 간격으로 다시 켭니다. 10분 넘게 잘 돌면 간격을 처음으로 돌립니다.
> - 10분 안에 5번 비정상 종료되면 재시작을 멈춥니다(같은 이유로 계속 죽는 경우). 이유는 `logs/crash.json`에 남고, 다음에 켜질 때 가동 이력과 운영자 알림으로 전달됩니다.
> - 정상 종료(`masamong stop`, 콘솔·아이콘의 종료)는 감시 프로세스도 함께 끝냅니다. 재시작은 감시 프로세스가 같은 주소로 바로 다시 띄웁니다.
> - macOS도 같습니다. 이전에는 launchd가 메뉴 막대 앱만 다시 켜고 서비스 자체는 되살리지 않았습니다. Linux 서버의 systemd 유닛은 서비스를 직접 돌리므로(`Restart=on-failure`) 그대로입니다.
>
> 아래는 결정 전의 검토 내용입니다.

**현재**:

| 자동 시작 방식 | 비정상 종료 뒤 |
|---|---|
| Linux 서버 (systemd) | 5초 뒤 다시 시작 |
| macOS (launchd) | 다시 시작 (이번 점검에서 추가, 직접 끈 경우는 제외) |
| Windows (레지스트리 시작 항목) | **꺼진 채로 남음** |
| Linux 데스크톱 (XDG 자동 시작) | **꺼진 채로 남음** |

패닉은 이제 잡아서 기록하므로 흔하지 않지만, 메모리 부족·Go 런타임 치명 오류처럼 잡을 수 없는 종료는 남아 있습니다. 트레이 앱은 상태를 "꺼짐"으로 보여 줄 뿐 다시 켜지 않습니다.

**방법**:

- (가) 데몬 앞에 작은 감시 프로세스를 두고, 0이 아닌 코드로 끝나면 간격을 늘려 가며 다시 시작합니다. 모든 OS에서 같게 동작합니다.
- (나) 트레이 앱이 비정상 종료를 감지하면 다시 켭니다. 트레이를 띄우지 않고 쓰는 경우는 해결되지 않습니다.
- (다) Windows는 작업 스케줄러의 "실패 시 다시 시작"으로 등록합니다. OS마다 방식이 달라집니다.

**권장**: (가).

## 4. TiDB 장애 대비 임시 저장소

> **해당 없음 (2026-09-28)**: 운영자 결정으로 TiDB 백엔드를 껐습니다([저장소와 백업](https://github.com/kim0040/masamong2/wiki/저장소와-백업)). SQLite만 쓰는 동안에는 이 문제가 생기지 않습니다. TiDB를 다시 켤 때 아래 내용을 다시 봅니다.

**현재**: TiDB에 연결할 수 없는 동안 Discord에서 들어온 메시지는 저장에 실패하고 로그만 남습니다. 그 사이 대화는 기억에 남지 않습니다. 답변도 실패합니다(조용히 넘어감). SQLite에는 해당하지 않습니다.

**방법**: 저장에 실패한 메시지를 데이터 폴더의 로컬 파일(또는 작은 SQLite)에 모아 두고, 연결이 돌아오면 순서대로 옮깁니다. 가져오기는 중복을 건너뛰므로 두 번 들어가도 안전합니다.

**고려할 것**:

- 임시 저장소의 크기 상한(장애가 길 때).
- 옮기는 동안 들어오는 새 메시지와의 순서. 저장 순서가 아니라 메시지 시각으로 정렬하므로 문제는 작습니다.
- 콘솔에 "대기 중인 메시지 N개" 표시.

**권장**: TiDB로 옮기기로 하면 함께 구현합니다.

## 5. 백업 보관 개수와 압축

**현재**: 자동 백업은 주 1회, 4개를 보관합니다(`backup.keep: 4`). 디스크에는 DB 크기의 약 5배(DB와 백업 4개)가 필요합니다. 공간이 부족하면 백업을 건너뛰고 이유를 남깁니다(이번 점검에서 추가).

**방법**:

- 보관 개수를 2로 줄이면 DB의 약 3배가 됩니다. 설정만 바꾸면 됩니다.
- 백업을 압축합니다(gzip/zstd). 텍스트는 잘 줄지만 대부분을 차지하는 벡터는 압축이 잘 안 돼 **10–20% 정도**만 줄 것으로 예상합니다. 대신 백업과 복원 시간이 늘어납니다.
- 1번(int8 저장)을 하면 백업도 함께 약 37% 줄어듭니다.

**권장**: 필요하면 먼저 `backup.keep`을 조정합니다. 압축은 효과가 작아 우선순위가 낮습니다.

## 6. 아주 큰 단일 채널의 증분 조각 맞추기

> **구현함 (2026-10-12)**: 저사양 보강에서 체크포인트 기반 증분 경로를 넣었습니다. 자세한 동작은 [기억 운영 문서](https://github.com/kim0040/masamong2/blob/main/docs/memory-operations.md) 16절 "큰 방의 leaf 동기화"에 있습니다.

**지금 동작**: 마지막으로 끝난 조각 맞추기의 체크포인트를 저장해 두고, 그 뒤에 순서대로 들어온 새 메시지는 **꼬리만** 다시 자릅니다. 첫 동기화, 늦게 들어온 과거 시각 메시지(가져오기, 누락분 채우기), 수정·삭제, 조각 규칙·시간대 변경, 중단되거나 불확실한 체크포인트일 때만 방 전체를 다시 맞춥니다. 전체 재절단과 결과가 같은지는 테스트로 확인합니다.

## 7. 꺼져 있던 동안의 Discord 메시지 채우기

> **구현함 (2026-09-28)**: 운영자가 "자동, 최근 7일까지"로 정했습니다.
> - 연결이 준비되면 5초 뒤 수집(`capture`)을 켠 채널마다 마지막으로 저장한 메시지 이후를 읽습니다. 수집을 켠 뒤 아무것도 저장하지 않은 채널은 건너뜁니다(`never_captured`). 켜기 전의 과거를 퍼 오지 않기 위해서입니다.
> - 기간은 `memory.backfill_days`(0 = 7일, -1 = 끔, 최대 30), 방마다 한 번에 `memory.backfill_max_messages`(0 = 4000)개까지 읽습니다.
> - 채운 메시지에는 답하지 않고, 기억 동의를 철회한 사람의 메시지는 저장하지 않습니다(실시간 수집과 같은 규칙). 수정·삭제된 메시지는 실시간 이벤트로 기억에도 반영합니다.
> - 콘솔: 방 화면 **기억 → 놓친 메시지 채우기**에서 마지막 결과를 보고 지금 채울 수 있습니다. CLI: `memory backfill`.
>
> 아래는 결정 전의 검토 내용입니다.

**현재**: 실시간으로 받은 메시지만 저장합니다. 서비스가 꺼져 있었거나 Discord 연결이 새 세션으로 다시 맺어진 사이에 올라온 메시지는 가져오지 않아 기억에서 영구히 빠집니다. 과거 메시지를 가져오는 코드가 없습니다.

**방법**: 연결이 준비되면(ready) 수집을 켠 채널마다 마지막으로 저장한 메시지 ID 이후를 Discord API로 읽어 저장합니다. 가져오기는 메시지 ID로 중복을 건너뛰므로 겹쳐 읽어도 안전합니다. 늦게 들어온 과거 메시지이므로 해당 방의 조각을 다시 맞춥니다(6번과 관련).

**고려할 것**:

- 원문 수집 범위: 실시간 수집과 같은 채널 정책(`capture`)을 따를지, 채울 기간의 상한(예: 7일)을 둘지. Discord 원문 allowlist 정책과 맞아야 합니다.
- Discord 속도 제한: 채널이 많거나 공백이 길면 여러 번 나눠 읽어야 합니다.
- 채운 메시지에는 답하지 않습니다(수집만).

**권장**: 수집 범위와 기간 상한을 정하면 구현합니다.
