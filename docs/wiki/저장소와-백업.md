# 저장소 및 백업 가이드

**한국어** | [English](https://github.com/kim0040/masamong2/wiki/Storage-and-Backup)

## 데이터베이스 아키텍처: SQLite

Masamong 2는 데이터 디렉터리 내의 단일 파일 `masamong.db`에 시스템 설정, 과거 대화 기억, 턴별 추론 기록, 사용량 통계, 개인화 기능(동의 내역·운세·공지 구독)을 통합 저장합니다. 외부 데이터베이스 데몬을 별도로 설치하거나 유지보수할 필요가 없으며, 무중단 파일 복사(`VACUUM INTO`)를 통해 안전하게 백업할 수 있습니다.

단일 머신(개인 PC, 홈랩, 독립 서버)에서 구동되는 개인 봇 환경에서는 SQLite만으로도 압도적인 성능과 안정성을 제공합니다. 대화 10만 건 및 초당 6건의 지속 인입(응답 생성 초당 약 6건) 부하 테스트에서도 지연 없이 안정적으로 처리됨을 검증했습니다.

- **읽기/쓰기 커넥션 풀 분리**: SQLite의 쓰기 락 규칙에 맞추어 쓰기 작업은 단일 전용 트랜잭션 연결로 엄격히 직렬화 처리합니다. 대용량 색인 조회나 백업과 같은 무거운 읽기 작업은 **독립된 읽기 전용 커넥션 풀**에서 병렬로 수행되므로, 읽기 부하로 인해 실시간 메시지 저장이 지연되지 않습니다 (10만 건 기준 메시지 저장 p95 약 20ms).
- **WAL(Write-Ahead Logging) 모드**: WAL 모드를 기본 적용하여 읽기 트랜잭션과 쓰기 트랜잭션이 상호 블로킹 없이 동시 실행됩니다. WAL 로그 파일이 64MB를 초과하면 자동으로 체크포인트를 수행하여 파일 크기를 최적화합니다.
- **비정상 종료 및 정전 대비**: 설정 파일(`config.yaml`)은 임시 파일 기록 및 `fsync` 후 원자적 치환(Atomic Rename)으로 안전하게 교체됩니다. 데이터베이스는 SQLite 기본 동기화 메커니즘을 통해 커밋 시점마다 디스크 무결성을 보장합니다.
- **운영 시 주의사항**: SQLite는 단일 호스트 로컬 I/O에 최적화되어 있습니다. 데이터베이스 파일을 네트워크 파일 시스템(NFS, SMB/CIFS 등) 경로에 배치하면 파일 락 데드락이나 데이터 손상이 발생할 수 있으므로 반드시 로컬 SSD/HDD에 보관하세요.

## TiDB 지원 종료 및 단일 스토리지 정책 (2026-09-28)

초기에는 대규모 분산 환경을 위해 TiDB(MySQL 호환 프로토콜) 백엔드를 선택할 수 있었으나, 복수 데이터베이스 엔진을 동시에 유지보수하고 검증하는 데 따른 엔지니어링 오버헤드를 줄이고 안정성에 집중하기 위해 운영 결정에 따라 **SQLite 단일 백엔드 체제로 단일화**되었습니다.

- 레거시 코드는 보존되어 있으나 `internal/storage/settings.go`의 `TiDBEnabled = false` 가드에 의해 하드코딩 비활성화되었습니다. `storage.yaml`, 환경 변수 `MASAMONG_DB_BACKEND`, CLI 플래그 `--db-backend` 등 모든 진입점에서 TiDB 활성화가 거부됩니다.
- 구형 동적 스토리지 마이그레이션 도구(`storage migrate`) 역시 함께 비활성화되었습니다.
- **기존 TiDB 인스턴스 마이그레이션 절차**:
  1. 이전 버전에서 데이터 백업을 생성합니다 (TiDB 백업은 논리 JSON 덤프 포맷으로 생성됨).
  2. `storage.yaml` 파일에서 `backend: tidb` 설정을 제거합니다.
  3. 최신 버전으로 서비스를 시작한 뒤 콘솔의 **유지보수 → 백업** 메뉴에서 해당 덤프 백업을 복원합니다.

상세한 아키텍처 결정 배경과 재활성화 검토 가이드는 [저장소 설계 문서](https://github.com/kim0040/masamong2/blob/main/docs/STORAGE.md)에서 확인하실 수 있습니다.

## 이전 봇(V1) 개인 설정 마이그레이션

관리 콘솔의 **유지보수 → 이전 봇 개인 설정 가져오기** 메뉴에서 V1 봇의 SQLite 파일 경로를 지정하고, **미리보기** 버튼을 통해 마이그레이션 대상과 건너뜀 사유를 사전에 검토한 뒤 안전하게 가져올 수 있습니다 (`masamong migration apply --path V1.db [--confirm true]`).

- 개인정보 동의 이력, 운세 사주 등록 데이터, 대학/편입 공지 구독 정보만 선별적으로 가져오며, 대화 원문은 가져오지 않습니다.
- 최신 개인정보 정책 버전에 동의한 사용자의 데이터만 유효하게 가져오며, 현재 인스턴스에 이미 등록된 데이터는 임의로 덮어쓰지 않습니다.
- 구버전 데이터베이스 파일은 읽기 전용(Read-Only) 모드로 열어 원본 손상을 방지합니다.

## 백업 및 복원 관리

### 정기 자동 백업 스케줄링

```yaml
backup:
  schedule: weekly   # 비활성화(off) | 매일(daily) | 매주(weekly)
  hour: 4            # 실행 시각 (i18n.timezone 기준 24시간 표기)
  weekday: 0         # 요일 지정 (0 = 일요일, 매주 스케줄링 시 적용)
  keep: 4            # 자동 백업 최대 보관 개수 (수동 생성 백업 및 롤백 안전 백업은 자동 삭제 대상에서 제외)
```

### 수동 백업 생성 및 복원 절차

관리 콘솔의 **유지보수** 메뉴 또는 CLI 명령어를 통해 실행할 수 있습니다:

```bash
# 1. 즉시 백업 아카이브 생성
masamong backup create

# 2. 보관 중인 백업 목록 조회
masamong backup list

# 3. 특정 백업 아카이브의 무결성 검증
masamong backup verify --name <백업이름>

# 4. 백업 데이터 복원 (안전을 위해 백업 이름을 인자로 재확인)
masamong backup restore --name <백업이름> --confirm <백업이름>

# 5. 불필요한 백업 아카이브 삭제
masamong backup delete --name <백업이름>
```

- 백업 아카이브는 데이터 디렉터리 내 `backups/` 경로에 저장되며, SQLite DB 원본과 `config.yaml` 설정 파일을 함께 패키징합니다. (소유자 전용: macOS·Linux는 `0600`, Windows는 소유자 전용 ACL)
- **백업은 한 시점의 일관된 사본입니다.** DB 스냅샷을 먼저 뜨고, 설정 파일과 그 리비전 번호는 *그 스냅샷 안에서* 가장 최근에 커밋된 설정에서 가져옵니다. 백업이 도는 사이에 설정을 바꿔도 DB와 `config.yaml`이 서로 다른 시점의 것이 되지 않습니다. 같은 초에 시작한 백업 여러 개도 각자 폴더를 따로 받고, 실패한 백업은 자기가 만들던 폴더만 지울 뿐 성공한 백업은 건드리지 않습니다. 완성되어 검증을 통과하기 전까지는 숨김 폴더 `.backup-staging-*`에 있어 목록에 나오지 않습니다. 강제 종료로 남은 스테이징 폴더와 복원 때 남은 `.old-*`·`.new-*` 파일은 소유 작업이 없을 때 시작 시와 매시간 자동 정리하며, 남아 있는 동안 `doctor`에 표시됩니다.
- **검증**(`backup verify`, 그리고 복원 직전에 자동으로)은 파일 체크섬, SQLite 무결성 검사, 제품 스키마와의 일치, 설정 파싱과 매니페스트 리비전 일치를 확인합니다. 체크섬만 맞고 올바른 DB가 아닌 백업은 거절합니다. TiDB 시절 버전이 만든 옛 백업(논리 덤프)은 먼저 격리된 임시 DB에서 검사합니다.
- **자격증명 및 API 키 보안**: 보안을 위해 원문 API 키와 봇 토큰은 백업 아카이브에 포함되지 않으며 오직 안전한 식별 참조값만 포함됩니다. 따라서 다른 컴퓨터로 백업을 이전하여 복원한 경우 API 키는 콘솔에서 다시 입력해야 합니다.
- **자동 롤백 안전 백업(Safety Backup)**: 복원을 실행하기 직전에 현재 상태의 안전 롤백 스냅샷을 자동으로 생성한 뒤, 데몬 재기동 단계에서 새 데이터를 적용합니다. 복원 결과에 문제가 있다면 즉시 안전 백업으로 롤백할 수 있습니다.
- **복원은 진행 중이던 내용을 잃지 않습니다.** 살아 있는 것을 건드리기 *전에* 복원할 백업을 완전히 검사합니다(체크섬, 무결성, 스키마, 설정). 그다음 현재 DB와 쓰기 선행 로그(`-wal`. 아직 본 파일에 합쳐지지 않은 커밋이 들어 있을 수 있음), 설정을 이번 작업 전용 이름으로 옆에 치워 두고, 새 파일을 설치해 확인한 뒤에야 옛 파일을 지웁니다. 각 단계를 저널에 적어 두므로, 강제 종료·정전·Windows가 하필 그때 놓아 주지 않는 파일이 있어도 다음 시작에서 멈춘 자리부터 이어 가거나 옛 파일로 되돌립니다. 옛 상태조차 되돌릴 수 없으면 서비스는 DB를 열지 않고 현지화된 복구 화면을 띄웁니다([문제 해결](https://github.com/kim0040/masamong2/wiki/문제-해결#콘솔에-복구-필요가-뜰-때-유지보수-모드)).
- **복원 실패와 정리:** 실제 파일을 옮기기 전 준비 단계에서 실패하면 스테이징 사본을 지우고 실패를 기록한 뒤 현재 데이터를 그대로 두고 봇을 계속 실행합니다. 커밋된 복원은 옛 파일을 다른 프로그램이 열고 있어도 성공이며, 시작 때와 매시간 정리를 다시 시도합니다. 남은 파일과 `restore-result.json`의 경고는 `doctor`에서 확인할 수 있습니다.
- **업데이트 전후 자동 백업**: 콘솔에서 새 버전을 설치하기 직전(종류 *업데이트 전*)과, 어떤 방법으로 설치했든 새 버전이 처음 시작할 때(종류 *새 버전 첫 시작*) 자동으로 백업합니다. 종류마다 최근 3개를 남깁니다. DB는 새 형식으로만 바뀌므로, 이전 버전으로 돌아갈 때 이 백업으로 복원합니다.
- 백업 파일에는 과거 대화 원문이 포함되어 있으므로 외부에 공유하거나 공용 저장소에 업로드하지 마세요.

### 새로운 서버/컴퓨터로 마이그레이션

1. 기존 컴퓨터에서 백업을 생성합니다: `masamong backup create`
2. 생성된 `backups/<백업이름>` 디렉터리를 새 컴퓨터의 데이터 디렉터리 내 `backups/` 경로로 복사합니다.
3. 새 컴퓨터에 Masamong을 설치한 뒤 `masamong setup`을 실행하고, 복원 명령을 실행합니다: `masamong backup restore --name <백업이름> --confirm <백업이름>`
4. 콘솔의 **연결** 메뉴에서 모델 API 키 및 Discord 봇 토큰을 재등록합니다.

## 초기화

**유지보수 → 초기화**는 처음 설치한 상태로 되돌립니다. 경고를 보여 준 뒤 확인 단어를 입력해야 실행됩니다.

- **지워지는 것**: 기억과 가져온 대화, 대화 기록, 사람·동의·개인 설정, 서버·방 설정, 모든 설정과 변경 기록, 연습 모드 데이터. **실제로 쓰고 있는** DB가 대상이므로 `storage.yaml`의 `sqlite_file`로 고른 사용자 지정 파일(과 `storage.yaml` 자체)도 포함합니다. 인스턴스가 소유한 파일, 곧 올려 둔 가져오기 파일(`imports/`), 기억 준비 스테이징(`rag_staging/`)과 준비된 카탈로그(`memory/`), 채널 첨부 파일(`rag/`), 생성한 그림(`images/`), 공지 데이터(`notices/`), 복원 표식과 결과도 지웁니다. 문서 폴더에 둔 대화 내보내기처럼 인스턴스가 *가리키기만* 하는 파일은 건드리지 않습니다.
- **남는 것**: `backups/`, `logs/`, `admin/`, `sessions.json`(콘솔 로그인), 데몬과 잠금 상태 파일입니다. 저장한 키는 **API 키와 봇 토큰도 지우기**를 고르지 않으면 유지됩니다. **초기화 전에 백업 만들기**가 기본으로 켜져 있습니다(종류 *초기화 전*). 되돌리려면 처음 설정을 마친 뒤 유지보수에서 그 백업으로 복원합니다.
- **키**: **저장한 API 키와 봇 토큰도 지우기**를 고르지 않으면 남습니다. 골라도 콘솔에서 저장한 키(`secrets/`의 키 파일, 이 인스턴스의 키체인·자격 증명 관리자 항목)만 지우고, 환경변수나 다른 파일로 넣은 키는 건드리지 않습니다.
- 복원과 같이 재시작할 때 실행됩니다. 서비스가 DB를 열기 전에 파일을 지우고, 콘솔은 처음 설정 화면으로 넘어갑니다.
- **중간에 끊기면**(강제 종료, 또는 다른 프로그램이 열고 있어서 Windows가 지우지 못하는 파일): 무엇을 어디까지 지웠는지 정확한 목록을 저널에 남깁니다. 봇은 꺼지고 현지화된 복구 안내가 지금 쓸 수 있는 명령을 보여 줍니다. `masamong status`는 복구 주소에서 데몬이 실행 중이라고 표시하고(JSON에서는 `ready:false`), `maintenance:true`와 한 줄 `message`를 포함합니다. `masamong runtime status`도 같은 필드를 보여 줍니다. `masamong stop` 뒤 화면에 나온 `masamongd --maintenance retry`를 실행한 다음 `masamong start`를 쓰세요([CLI 명령어](https://github.com/kim0040/masamong2/wiki/CLI-명령어#복구-명령-masamongd)).
- **지우기를 시작한 뒤에는 되돌리거나 취소할 수 없고** 끝까지 마무리만 할 수 있습니다. 되돌릴 방법은 먼저 만든 백업입니다. 손상되었거나 옛 버전이 만든 초기화 표식은 무언가를 지워도 된다는 허락으로 절대 해석하지 않으며, 직접 볼 수 있게 따로 치워 둡니다.
- 데이터 폴더 자체는 링크 뒤에 있어도 됩니다(예: macOS의 `/var` → `/private/var`, 옮긴 홈 폴더). 그 *안쪽* 폴더만 진짜 폴더여야 합니다.

## 환경설정 스냅샷 관리

데이터베이스 본문은 그대로 유지한 채, `config.yaml` 설정 구성만 독립적으로 이름 붙여 스냅샷으로 저장하고 언제든 직전 상태로 복원할 수 있습니다:

```bash
# 현재 설정 스냅샷 저장
masamong config snapshot save --name before-experiment --note "대규모 프롬프트 실험 전 백업"

# 등록된 스냅샷 목록 및 고유 식별자 조회
masamong config snapshots

# 특정 스냅샷 구성으로 즉시 복원
masamong config snapshot restore --id <스냅샷ID>
```
