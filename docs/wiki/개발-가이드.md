# 개발 가이드

**한국어** | [English](https://github.com/kim0040/masamong2/wiki/Development-Guide)

## 개발 환경 요구사항

- Go 1.27 이상
- 웹 관리 콘솔(`ui/`)을 수정할 경우에만 Node.js 및 npm 필요 (일반 백엔드 빌드는 저장소에 커밋된 `ui/dist` 번들을 사용하므로 Node 환경 불필요)
- 선택 사항: Python 3 + NumPy (`experimental/` RAG 샌드박스 및 오프라인 평가 도구 실행 시). 콘솔 빌드도 문구 생성기 때문에 Python 3가 필요한데, `python3`, `python`, `py -3` 순으로 찾고 Microsoft Store 스텁은 건너뛰며, 하나도 안 되면 무엇을 설치해야 하는지 알려 줍니다
- Windows: PowerShell이면 충분합니다. `make`는 선택이며 아래 `make` 대상마다 그냥 쓰는 명령이 옆에 있습니다

```bash
git clone https://github.com/kim0040/masamong2.git
cd masamong2
make build          # build/masamong, build/masamongd 바이너리 빌드
make test           # 전체 단위 테스트 실행
```

```powershell
# make 없는 Windows
go build -o build\masamong.exe .\cmd\masamong
go build -o build\masamongd.exe .\cmd\masamongd
go test ./...
```

### 빠른 테스트 인스턴스 (원터치 실행)

macOS·Linux에서는 Finder에서 저장소 루트의 `start-test.command`를 더블클릭하거나 터미널에서 `./start-test.command` (또는 `make try`)를 실행합니다. Windows에서는 `powershell -ExecutionPolicy Bypass -File .\start-test.ps1`(또는 이것을 실행하는 `make try`)을 씁니다. 현재 소스코드를 즉시 빌드한 뒤, 실제 운영 환경과 완전히 분리된 전용 테스트 인스턴스를 띄우고 인증이 완료된 콘솔 브라우저를 열어 실시간 로그를 출력합니다. 터미널 창에서 `Ctrl+C`를 누르거나 창을 닫으면 테스트 프로세스가 안전하게 종료됩니다. 콘솔의 유지보수 → 서비스 종료나 다른 터미널의 `masamong stop`으로 멈춰도 이 창은 로그 표시를 끝내고 스스로 닫힙니다(재시작은 그대로 이어서 표시).

- 테스트 데이터는 `~/.masamong-try`(Windows는 `%USERPROFILE%\.masamong-try`, 환경변수 `MASAMONG_TRY_ROOT`로 변경 가능)에 격리 보관되며, API 키는 시스템 키체인·자격 증명 관리자 대신 해당 폴더 내 `secrets/` 파일에 저장되어(`MASAMONG_SECRET_STORE=file`) 실제 운영 인스턴스와 절대 혼합되지 않습니다. 기본 포트(8787)가 이미 사용 중인 경우 자동으로 빈 유휴 포트를 탐색하여 바인딩합니다.
- `--reset` 플래그는 기존 테스트 데이터를 초기화하고 온보딩 단계부터 다시 시작하며, `--check`는 기동 전 `go vet` 및 `go test` 검증을 수행하고, `--stop`은 실행 중인 테스트 서비스만 종료합니다. (예: `make try ARGS=--reset`). Windows 스크립트는 같은 기능을 PowerShell 스위치 `-Reset`, `-Check`, `-Stop`으로 받습니다(`make try ARGS=-Reset`). `build\try`에 빌드하고 창에서 `logs\daemon.log`를 따라 보여 주며 `Ctrl+C`로 테스트 서비스를 끕니다. `-Reset`은 `start-test.ps1`이 쓴 소유 표시 파일의 내용까지 정확히 맞는 폴더만 지웁니다. 이름이 `.masamong-try`여도 표시가 없으면 거절합니다.
- 별도의 API 키가 없더라도 콘솔 내 오프라인 연습 모드를 통해 UI 및 주요 대화 흐름을 테스트할 수 있습니다. Discord 연동을 테스트할 때는 운영 봇과의 간섭을 방지하기 위해 반드시 별도의 테스트용 봇 토큰을 사용하는 것을 권장합니다.

## 프로젝트 구조

| 디렉터리 경로 | 핵심 역할 |
|---|---|
| `cmd/masamong`, `cmd/masamongd` | CLI 런처 도구 및 백그라운드 서비스 데몬 엔트리포인트 |
| `internal/application` | **Action 비즈니스 계층.** CLI, 웹 콘솔, Discord 요청이 모두 `Service.Execute`를 거쳐 일관되게 처리됨 |
| `internal/catalog` | 지원되는 Action 카탈로그 (CLI 서브커맨드 매핑, 콘솔 라우트, 사이드 이펙트 정의) |
| `internal/transport/web` | 루프백 HTTP 서버, 세션 관리, RESTful API, 경량 `/lite` 페이지, Svelte 프론트엔드(`ui/`) |
| `internal/connectors/discord` | Discord Gateway 연결, 슬래시/접두사 명령어 파서, 임베드 메시지 렌더러 |
| `internal/chat` | 대화 추론 파이프라인 (플래너 의도 분석 → 도구 라우팅 → 기억 검색 → 최종 응답 생성) |
| `internal/memory/*` | 대화 원문 코퍼스(`corpus`), 청크 분할(`leaves`), 어휘 검색(`lexical`), 통합 검색(`search`), 영속성 저장(`store`), 인덱싱 엔진(`engine`) |
| `internal/tools` | 내장/외부 도구 카탈로그, 스키마 검증, 사용자/일일 호출 한도 제어 |
| `internal/providers/*` | LLM 모델, 기상청/Open-Meteo 날씨, 금융 시세, 웹 검색 등 외부 공급자 어댑터 |
| `internal/storage` | SQLite 기반 영속성 저장소 및 백업 엔진 (TiDB 관련 코드는 `TiDBEnabled=false`로 비활성화) |
| `internal/features/*` | 개인정보 동의 체계(`privacy`), 천문 운세 계산(`fortune`), 대학/편입 공지사항 스크래핑(`notices`, `catalog.json`) |
| `internal/lang/packs`, `locales/` | 봇 시스템 프롬프트/언어팩, 콘솔 및 백엔드 다국어 번역 리소스 |
| `internal/launcher`, `internal/tray` | 서비스 데몬 라이프사이클 관리, 부팅 시 자동 시작, 시스템 트레이 아이콘 |

### 동시성 프로그래밍 규칙

새로운 기능이나 Action을 추가할 때는 동시성 안전성을 위해 다음 규칙을 반드시 준수해야 합니다([동시 처리와 성능](https://github.com/kim0040/masamong2/wiki/동시-처리와-성능)).

- **설정 스냅샷 불변성**: 설정값은 `s.Doc()`, `s.Revision()`, `s.Registry()`를 통해 읽습니다. 반환된 객체는 읽기 전용 스냅샷이므로 **내부 맵이나 슬라이스를 직접 수정해서는 안 됩니다.** 여러 설정 필드 간의 정합성이 필요하다면 단일 시점에 읽어 로컬 변수에 보관합니다.
- **설정 변경 직렬화**: 설정을 수정할 때는 반드시 `mutateConfig`(또는 `applyCandidate`) 함수를 통해 안전하게 반영합니다. 모든 설정 쓰기 작업은 내부 뮤텍스를 통해 직렬화되어 처리됩니다.
- **DB 트랜잭션 격리**: "읽기 → 유효성 검증 → 쓰기"로 이어지는 일련의 데이터베이스 작업은 반드시 `Store.WithWriter` 트랜잭션 블록 **내부에서** 원자적으로 수행해야 합니다 (예: `updatePoll`). 단, 트랜잭션 블록 안에서 외부 API 호출이나 LLM 추론과 같은 지연 작업(I/O)을 절대 수행하지 마세요.
- **SQLite 단일 라이터 락 방지**: SQLite는 연결 풀이 단일 라이터로 동작합니다. `WithWriter` 콜백 블록 내부에서 상위 `s.Store.DB`를 다시 직접 호출하면 데드락(교착 상태)이 발생합니다. 반드시 콜백의 인자로 전달된 `tx` 트랜잭션 핸들러만 사용해야 합니다.
- **비동기 작업의 정상 종료 보장**: Discord 핸들러는 Gateway의 작업 수용 잠금 아래 등록합니다. 종료를 시작하면 새 작업을 받지 않고, 이미 수용한 READY·RESUMED 핸들러와 답변·명령을 함께 기다린 뒤 서비스가 DB를 닫습니다.

## 테스트 및 코드 검증

```bash
go test ./... -count=1            # 전체 단위 테스트 실행
go test -race ./... -count=1      # 경쟁 상태(Race Condition) 검출 테스트
go vet ./...                      # 정적 코드 분석
python3 scripts/license_audit.py  # 오픈소스 라이선스 검증 (Windows: python scripts\license_audit.py)

# 프론트엔드 UI 검증
cd internal/transport/web/ui
npm ci
npm run check -- --fail-on-warnings
npm run build
```

테스트 작성 시에는 격리된 합성 픽스처(Fixture)와 임시 디렉터리만 사용해야 합니다. 실제 사용자의 대화 원문, 개인 식별자, 실제 API 토큰을 테스트 픽스처에 포함해서는 안 됩니다.

## 지속적 통합 (CI)

`ci` 워크플로는 푸시에 빨리 답하고 무거운 검사는 매주 돌리도록 두 가지 크기로 돕니다.

**빠른 검사** — 푸시(모든 브랜치)와 풀 리퀘스트
- `go vet`, Go 테스트, 웹 UI를 뺀 최소 바이너리(`noweb`) 빌드
- 콘솔 검사(타입 검사, 번들 빌드와 용량 예산, 커밋된 `ui/dist`·`locales/ui` 일치)는 콘솔 코드나 문구가 바뀐 경우에만
- 라이선스 감사는 의존성(`go.mod`·`go.sum`·`package*.json`)이 바뀐 경우에만
- **Windows** 작업(`windows-latest`)이 모든 푸시와 풀 리퀘스트에서 `go vet`, Go 테스트, 콘솔 빌드(`npm ci`, `npm run build`), Python 검색 테스트를 돌려, Windows에서만 깨지는 변경이 병합 전에 잡힙니다
- **macOS** 작업(`macos-latest`)도 모든 푸시와 풀 리퀘스트에서 돕니다
- 문서만 바꾼 푸시(`docs/`, `*.md`)는 CI를 돌리지 않고, 새 푸시가 오면 이전 실행은 취소됩니다

**전체 검사** — 매주 월요일, 수동 실행(Run workflow), 릴리스 태그
- 빠른 검사 전부에 더해 Go Race Detector, 45초 부하 테스트, 모든 배포 타깃 크로스 컴파일(macOS, Linux amd64/arm64/armv7/riscv64, Windows amd64/arm64, FreeBSD amd64/arm64), 라이선스 감사

장시간 부하 테스트(`soak`)는 매달 1일에 한 번 돌고, 릴리스 전에는 수동으로 돌리는 것을 권합니다.

**CI가 돌지 않을 때**(fork에서 Actions를 꺼 두었거나, 푸시 전에 확인하고 싶을 때) — 같은 검사를 로컬에서 돌립니다. 바뀐 패키지만 `CI=true go test -count=1 -p 1 <패키지>`로, 경쟁 검사는 `go test -race -run <테스트>`로 좁혀서, 콘솔은 `make ui`와 `npm run check`, 문서는 `make docs`로 확인합니다.

## 릴리스 및 배포

태그 전에 거칠 순서(전체 검사, 장시간 부하, 테스트 봇으로 1주 시험, 백업·되돌리기)는 [릴리스 체크리스트](https://github.com/kim0040/masamong2/wiki/릴리스-체크리스트)에 있습니다.

### 버전 번호

버전은 `v주.부.수`(유의적 버전) 형식이고, 2026-11-02 첫 공개 릴리스가 `v1.0.0`입니다.

| 올리는 자리 | 언제 | 예 |
|---|---|---|
| 수(세 번째) | 버그 수정, 문구·문서 손질, 동작이 바뀌지 않는 작은 개선 | `v1.0.0` → `v1.0.1` |
| 부(두 번째) | 새 기능이나 눈에 띄는 동작 변경. 기존 설정과 데이터는 그대로 씁니다 | `v1.0.1` → `v1.1.0` |
| 주(첫 번째) | 큰 개편, 또는 설정·데이터를 손봐야 하는 변경. 릴리스 노트에 옮기는 방법을 적습니다 | `v1.4.2` → `v2.0.0` |

앞자리를 올리면 뒷자리는 0으로 돌아갑니다. 시험판은 `v1.1.0-rc1`처럼 붙이고, 앱의 업데이트 확인은 시험판보다 같은 번호의 정식판을 새 버전으로 봅니다.

버전 태그(`v*`)를 푸시하면 GitHub Actions의 `release` 워크플로가 macOS 러너에서 모든 아키텍처 배포 아카이브를 빌드하고(`scripts/release.sh`), 무결성 검증(`scripts/verify-release.sh`) 및 Linux/Windows 설치 시뮬레이션을 완료한 후 GitHub Release를 자동으로 생성합니다. Windows 스모크 작업은 Windows ZIP을 내려받아 `SHA256SUMS`와 대조한 뒤, Go와 호스트의 시간대 파일을 숨긴 상태로 임시 폴더에서 인스턴스를 설정·시작하고 `status`·`doctor`를 확인한 다음 멈춥니다. 내장 시간대 데이터베이스가 빠지면 릴리스가 실패합니다.

```bash
git tag v1.0.1 && git push origin v1.0.1
```

**Actions 없이 릴리스하기** — macOS에서 아카이브를 만들고 검사한 뒤 손으로 올립니다. Linux·Windows 설치 시뮬레이션은 돌지 않으므로 [릴리스 체크리스트](https://github.com/kim0040/masamong2/wiki/릴리스-체크리스트)의 Windows 항목은 Windows 컴퓨터에서 직접 확인합니다. 아카이브 이름과 `SHA256SUMS`는 앱 안 업데이트가 기대하는 형식이므로 바꾸지 않습니다.

```bash
scripts/release.sh v1.0.1 && scripts/verify-release.sh build/release
git tag v1.0.1 && git push origin v1.0.1
gh release create v1.0.1 build/release/* --title "Masamong v1.0.1" --generate-notes
```

앱 안 업데이트 확인과 설치 스크립트는 저장소의 공개 Release(첫 Release는 v1.0.0)에서 내려받습니다. 소스에서 만든 빌드(`git describe` 버전)는 콘솔로 업데이트하지 않습니다.

## 관리 콘솔 UI 수정 가이드

- 라우트 및 페이지: `internal/transport/web/ui/src/routes.ts`, 네비게이션: `src/lib/nav.ts`
- 다국어 UI 문구: `ui/scripts/strings.py`에서 코드로 관리 (생성된 `locales/ui/*.json` 파일을 직접 수정하지 않음. 생성기는 어느 시스템에서나 LF 줄바꿈으로 써서, Windows에서 다시 빌드해도 파일 전체가 바뀌지 않습니다)
- 카탈로그 JSON은 UTF-8로 저장합니다. PowerShell 5.1의 `Set-Content`는 시스템 코드 페이지로 저장하므로 `-Encoding utf8`을 지정해야 합니다. 가능한 경우 저장소의 Python 생성 스크립트를 우선 사용하세요. `go test ./locales`는 잘못된 코드 페이지로 깨진 카탈로그 문구를 확인합니다.
- UI 코드 수정 후에는 반드시 `make ui`(Windows: `cd internal\transport\web\ui; npm ci; npm run build`)를 실행하여 번들 산출물(`internal/transport/web/ui/dist`)을 다시 생성하고 **함께 커밋**해야 합니다. `npm run build`는 Windows에서도 동작하며, 두 번째 빌드는 `git status`를 깨끗하게 둡니다.
- 콘솔 로직 테스트는 `npm run test:i18n`(`node --test scripts/*.test.mjs`)으로 돌립니다. 빌드 스크립트, API 클라이언트(네트워크가 끊겨도 스피너가 끝없이 돌지 않음), 언어 목록과 글꼴, 시스템별 문구(`lib/platform.ts`)와 빈 검색 설명 같은 순수 로직을 검사합니다.
- 공통 패턴: 무언가를 불러오는 곳은 `components/LoadState.svelte`(스켈레톤 → "아직 불러오는 중" → 다시 시도 버튼이 있는 오류 카드), 시스템마다 다른 문구는 `lib/platform.ts`의 `tp()`(`key.windows` / `key.darwin`), 페이지 제목은 `lib/title.svelte.ts`([admin-gui-ia.md](https://github.com/kim0040/masamong2/blob/main/docs/admin-gui-ia.md))
- 데스크톱 화면뿐만 아니라 320px 최소 너비 모바일 화면, 라이트/다크 테마 전환, 키보드 접근성(A11y), 모션 감소 모드 동작을 확인하세요.

## 위키 문서 수정 안내

본 위키 문서는 저장소의 `docs/wiki/` 디렉터리가 원본(Single Source of Truth)입니다. `main` 브랜치에 변경 사항이 병합되면 `wiki` 워크플로가 GitHub 위키로 자동 동기화합니다. GitHub 위키 웹페이지에서 직접 수정한 내용은 다음 동기화 시 덮어쓰여 유실되므로, 반드시 `docs/wiki/` 폴더 내 마크다운 파일을 수정하여 Pull Request로 기여해 주세요. 위키 문서 간 링크는 `[표시 텍스트](https://github.com/kim0040/masamong2/wiki/문서-파일명)`처럼 위키 주소 전체를 씁니다. 위키 전용 겹대괄호 링크 문법은 표 안에서 `|` 때문에 칸이 갈라지고 저장소에서 볼 때 링크가 되지 않아 쓰지 않습니다.

### 링크와 번역 검사

`make docs`(`go run ./tools/doccheck`)는 두 가지를 확인합니다. `go test ./...`와 `wiki` 워크플로도 같은 검사를 돌리고, 실패하면 위키에 올리지 않습니다.

- **링크**: 상대 링크와 이 저장소 파일·위키 페이지로 가는 링크가 실제 파일을 가리키는지 확인합니다. `docs/archive/`는 Git에 없는 로컬 기록이라 제외합니다.
- **번역**: README 다섯 언어, 한국어 위키 페이지와 그 영문 페이지를 한 묶음으로 보고, `docs/translations.json`에 파일마다 해시를 기록해 둡니다. 한 언어만 고치면 검사가 실패합니다. 나머지 언어도 고친 뒤 `make docs-record`로 다시 기록합니다. 새 위키 페이지는 첫 줄 근처에 언어 전환 줄(`**한국어** | [English](…/wiki/영문-페이지)`)이 있어야 짝으로 잡힙니다.

영어 페이지는 영어 파일 이름(`Installation.md`, `Quick-Start.md` …, 영어 홈은 `English.md`)으로 따로 두고, 두 언어 페이지 맨 위에 서로를 가리키는 언어 전환 줄을 둡니다. 한쪽을 고치면 다른 쪽도 함께 고칩니다. 사이드바(`_Sidebar.md`)에는 두 언어 목록이 모두 있습니다.
