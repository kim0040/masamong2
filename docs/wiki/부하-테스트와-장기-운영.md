# 부하 테스트와 장기 운영

**한국어** | [English](https://github.com/kim0040/masamong2/wiki/Load-Testing-and-Long-Running)

마사몽은 몇 달씩 켜 두는 서비스입니다. 이 문서는 오래 켜 둬도 괜찮은지 **어떻게 확인하는지**, **확인한 결과**, 그리고 **규모별로 무엇을 준비해야 하는지**를 설명합니다.

## 부하 테스트 도구 (`tools/loadtest`)

실제 서비스 코드를 한 프로세스 안에서 돌리고, 모델 공급자 자리에는 가짜 OpenAI 호환 서버(지연·실패율 설정 가능)를 붙입니다. 외부로 나가는 호출이 없어(`MASAMONG_OFFLINE=1`) 비용이 들지 않습니다.

동시에 일어나는 일:

| 부하 | 실제 운영에서 |
|---|---|
| Discord 메시지 (Poisson 도착) → 기억 수집 → 일부에 답변 | 채널 대화 |
| 슬래시·`!` 명령, 투표 생성, 투표 버튼 | 명령과 버튼 |
| 대시보드·대화 기록·통계·로그 조회 | 열어 둔 관리 콘솔 |
| 채널 설정 변경 | 운영자의 설정 조정 |
| 1분마다 배경 색인, 예약 작업 | 데몬 배경 작업 |

측정하는 것:

- 작업 종류별 지연 p50/p95/p99/max와 결과(성공, 한도, 대기열 거절, 오류, 시간 초과)
- 모델 서버 호출 수, 동시 호출 최대치, 새로 연 연결 수
- 일정 간격의 goroutine 수, 힙, 열린 파일 수, DB·WAL·로그 크기, 표별 행 수, 색인 재구성 시간
- **1,000 대화당 증가량** (DB MB, 로그 MB, 표별 행 수), 저장 메시지당 힙
- 부하 종료 후 진행 중 작업이 끝나는지, goroutine·파일이 처음 수준으로 돌아오는지, DB `integrity_check`

`-strict`를 주면 다음 중 하나라도 해당할 때 종료 코드 1로 실패합니다: goroutine이 부하 전보다 10개 넘게 남음, 열린 파일이 10개 넘게 남음, 대화의 1% 넘게 오류·시간 초과, DB 무결성 오류, 진행 중 작업이 끝나지 않음. goroutine이 남으면 스택 요약을 보고서에 넣습니다.

### 실행

```bash
go run ./tools/loadtest -duration 2m                                  # 빠른 확인
go run ./tools/loadtest -duration 30m -rate 6 -dims 4096 -strict      # 장시간 soak
go run ./tools/loadtest -duration 5m -rate 30                         # 처리 한계 찾기
go run ./tools/loadtest -duration 5m -seed 100000 -dims 4096          # 기록이 많이 쌓인 인스턴스
go run ./tools/loadtest -duration 10m -report soak.md                 # 보고서 파일 (+ soak.json)
```

`-tidb-dsn`은 TiDB 백엔드를 끄면서(2026-09-28) 거부됩니다. 아래 TiDB 결과는 끄기 전의 기록입니다.

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `-duration` | `2m` | 부하 시간 |
| `-rate` | `10` | 초당 Discord 메시지 |
| `-reply` | `0.6` | 답하는 메시지 비율 |
| `-channels`, `-users` | `12`, `60` | 채널·사용자 수 |
| `-concurrency` | `8` | `limits.max_concurrent_turns` |
| `-llm-latency`, `-llm-jitter` | `400ms`, `400ms` | 모델 호출 지연 |
| `-llm-error-rate` | `0.01` | 모델 호출 실패율 (502) |
| `-dims` | `256` | 임베딩 차원 (운영 기본은 2026-10-13부터 1024, 그 전에는 4096) |
| `-seed` | `0` | 시작 전에 저장·색인할 과거 메시지 수 |
| `-config-every` | `30s` | 설정 변경 간격 |
| `-strict` | 끔 | 장기 운영 점검 실패 시 exit 1 |
| `-features` | 켬 | 개인 기능도 함께: 알림 부탁·확인·취소와 실제 발송(가짜 Discord), 홀수 채널의 먼저 말 걸기(shadow·conservative 번갈아), 동의·개인 설정, 콘솔 조회. 끝나면 알림이 두 번 나가거나 보내는 중에 멈춘 것이 없는지 검사 |
| `-feature-rate` | `1` | 초당 개인 기능 사용 |
| `-tidb-dsn`, `-db-latency` | — | TiDB 비활성으로 지금은 거부됨 |

## 측정 결과 (2026-09-25)

환경: 4코어 Linux 컨테이너, Go 1.27, SQLite. 가짜 모델 지연 0.4–0.8초, 모델 호출 1% 실패. 채널 12개, 사용자 60명.

### 20분 soak: 초당 메시지 6개(답변 60%), 임베딩 4096차원, 1분마다 설정 변경

| | 수정 전 | 수정 후 |
|---|---|---|
| 판정 (`-strict`) | **FAIL** | **PASS** |
| 답변 수 | 4,395 | 4,383 |
| 부하 후 goroutine (시작 전 9) | **43** (메모리 색인 DB 41개 누수) | 8 |
| 열린 파일 (시작 전 15) | 13 | 13 |
| DB 무결성 | ok | ok |
| 모델 연결 재사용 | 호스트당 유휴 연결 2개 (동시 호출 대부분 새 연결) | 16,072회 호출에 연결 26개 |

지연 (수정 후):

| 작업 | p50 | p95 | p99 |
|---|---|---|---|
| 답변 (대기 포함) | 4.4초 | 11.2초 | 13.7초 |
| 메시지 수집 | 1.1 ms | 1.6 ms | 4.5 ms |
| 투표 버튼 | 2.0 ms | 2.9 ms | 4.4 ms |
| 콘솔 대시보드 | 8.4 ms | 15.8 ms | 19.5 ms |
| 콘솔 대화 기록 | 2.9 ms | 4.9 ms | 5.8 ms |

이 부하(초당 답변 3.6개)는 동시 처리 8의 처리 한계(아래)를 조금 넘기 때문에 답변 지연의 대부분은 대기 시간입니다. 채널 대기열이 가득 차 조용히 건너뛴 메시지는 2.2%였습니다. 수집·버튼·콘솔은 답변이 몰려도 수 ms에 끝납니다.

### 1,000 답변당 증가량 (메시지 약 1,660개 포함)

| 항목 | 증가량 | 계속 쌓이나 |
|---|---|---|
| 질문 임베딩 캐시 | 7.4 MB | 아니오: 7일 뒤 삭제 (`retention.query_cache_days`) |
| 기억 조각·벡터·요약 | 3.3 MB | 예 (기억 자체. 블록 단위로 관리) |
| 대화 기록 | 1.9 MB | 상세는 30일 뒤 삭제, 요약 행은 400일 |
| 진단 trace | 0.8 MB | 아니오: 30일 뒤 삭제 |
| 백그라운드 작업(job) 기록 (기억 블록 준비) | 수 KB | 끝난 작업은 마지막 변경 30일 뒤 삭제. 끝나지 않은 작업과 방마다 최신 준비 작업은 항상 유지 |
| 로그 | 0.2 MB | 아니오: 10 MiB × 6개에서 순환 |

### 처리 한계 (3분, 초당 메시지 40개 = 답변 요청 초당 24개)

| 동시 처리 | 처리한 답변 | 대기열 거절 | 답변 p50 | 부하 후 메모리 |
|---|---|---|---|---|
| 8 (기본) | 초당 4.3개 | 3,292 | 14.5초 | 22 MB, goroutine 11 |
| 32 | 초당 6.3개 | 3,103 | 9.3초 | 23 MB, goroutine 11 |

- 답변 하나에 모델 호출 약 2.4초(플래너, 질문 임베딩, 재순위, 답변)가 들어 **처리 한계 ≈ 동시 처리 수 ÷ 답변당 모델 시간**입니다.
- 동시 처리 32에서는 채널 12개가 각각 한 번에 하나씩만 답하는 순서 보장이 한계를 정합니다(12 ÷ 1.9초 ≈ 6.3). 채널이 많을수록 더 올라갑니다.
- 한계를 넘는 요청은 채널 대기열에서 조용히 거절되고, 메모리·goroutine은 늘지 않았습니다. 과부하에서도 서비스가 무너지지 않습니다.

### 기록이 많이 쌓인 인스턴스: 메시지 10만 개 + 5분 부하 (`-seed 100000 -dims 4096`, 1분마다 설정 변경)

| | 수정 전 | 수정 후 |
|---|---|---|
| 판정 | PASS (누수 판정 기준 이전) | PASS |
| 색인 직후 힙 | 517 MB | 449 MB (행렬을 정확한 크기로 할당) |
| 부하 중 힙 추세 | **+309 MB/분** | **−28 MB/분** (안정) |
| 부하 후 힙 (GC 후) | 2,139 MB | 969 MB (현재 색인 + 교체 대기 중인 이전 색인 1개) |
| 전체 색인 재구성 | 11.8초 | 2.2–9.2초 |
| 답변 지연 p50 / p99 | 0.48 / 1.6초 | 0.47 / 1.4초 |
| 메시지 수집 p99 | 416 ms | 258 ms |

수정 전에는 설정을 바꿀 때마다(채널 규칙 같은 무관한 변경도) 색인 전체를 다시 만들었고, 교체된 색인이 1분씩 메모리에 남아 겹쳤습니다. 지금은 기억과 무관한 변경이면 색인을 그대로 씁니다.

### 용량 최적화 뒤: 메시지 10만 개 (색인 int8, 벡터 중복 저장 제거)

| | 최적화 전 (4096차원) | 최적화 후 4096차원 | 최적화 후 1024차원 |
|---|---|---|---|
| 색인 직후 힙 | 449 MB | **157 MB** | **85 MB** |
| 색인 직후 프로세스 RSS | (미측정) | 453 MB | 206 MB |
| 5분 부하 중 힙 | (미측정) | 355–570 MB (재구성 순간 900 MB 한 번) | 226–321 MB |
| 부하 후 힙 (GC 후) | 969 MB | 380 MB | 224 MB |
| 부하 후 RSS | (미측정) | 795 MB | 476 MB |
| DB (부하 전) | 약 470 MB (추정¹) | **274 MB** | **152 MB** |
| 전체 색인 재구성 | 2.2–9.2초 | 3.4초 | 1.9초 |
| 판정 | PASS | PASS | PASS |

¹ 메시지 3만 개에서 직접 비교: DB 117 MB → 84 MB, 색인 직후 힙 137 MB → 49 MB, 재구성 2.0초 → 1.0초. 10만 개 이전 DB는 같은 비율(조각 벡터·요약 벡터가 캐시에 한 번 더 저장됨)로 계산한 값입니다.

크기가 컸던 이유와 바꾼 점:

- **벡터가 텍스트보다 훨씬 큽니다.** 메시지 8개(약 300바이트)가 한 조각이 되고, 조각마다 조각 벡터와 요약 벡터가 하나씩 붙습니다. 4096차원이면 벡터 하나가 메모리에서 16 KB(float32), 디스크에서 8 KB(float16)라 조각 하나가 텍스트의 100배 이상을 차지했습니다.
- **메모리**: 색인 벡터를 int8(행마다 배율 하나)로 들고 있어 1/4이 됐습니다. 점수 차이는 약 0.001 이하이고, 비슷한 주제가 몰린 시험 데이터에서 상위 10개가 97.8% 같습니다(나머지는 점수가 거의 같은 동점권). 전문 검색 색인(FTS5)은 본문 사본을 따로 두지 않습니다(결과·점수·순서는 동일).
- **디스크**: 예전에는 조각·요약 벡터를 조각에 저장하고 임베딩 캐시에 한 번 더 저장했습니다. 이제 조각에만 저장합니다. 같은 본문의 조각은 기존 벡터를 그대로 쓰고, 모델을 바꿀 때 밀려나는 벡터만 캐시에 남겨 원래 모델로 돌아갈 때 비용이 들지 않습니다. 기존 DB의 중복은 첫 `usage_gc` 실행 때 한 번 지웁니다. SQLite 파일은 지운 자리를 다시 쓰므로 바로 작아지지는 않고, 백업(`VACUUM INTO`)은 줄어든 크기로 만들어집니다.
- **차원 줄이기**: `models.embed.dimensions`를 낮추면 저장된 벡터의 앞부분만 남겨(Matryoshka) 그 자리에서 옮기므로 재임베딩 비용이 없습니다. 1024차원이면 벡터가 다시 1/4입니다.

### 안정성 점검 뒤: SQLite 읽기 분리, 증분 재구성 (메시지 10만 개, 4096차원, 5분)

| | 이전 | 지금 |
|---|---|---|
| 메시지 저장 p95 / p99 / 최대 | 160 / 334 / 1,128 ms | **20 / 190 / 446 ms** |
| 답변 p99 | 3.2초 | 2.5초 |
| 색인 재구성 (부하 중) | 3.4초 | 1.2–1.8초 (바뀌지 않은 조각은 이전 색인에서 복사) |
| 부하 후 힙 / RSS | 380 / 795 MB | 223 / 654 MB |

긴 읽기(색인 불러오기)와 백업이 쓰기 연결을 붙잡지 않게 되어, 재구성 중에도 메시지 저장이 기다리지 않습니다.

### 개인 기능을 함께 켠 실행 (2026-09-28, SQLite, `-features`)

| 실행 | 결과 |
|---|---|
| 10분, 초당 메시지 6개, 1024차원, `-strict` | **PASS**. 채팅 턴 2,124개(p50 3.8초·p99 13.2초, 가짜 모델 지연 포함), 알림 180개 부탁 → 보냄 153·취소 20·대기 7. 중복 발송 0, 보내는 중에 멈춘 알림 0, 고루틴·파일 누수 없음, DB 무결성 ok |

알림 부탁 p99는 10분 실행에서 680 ms까지 올라갔습니다. 색인 저장과 SQLite 쓰기 연결이 겹친 순간이고, 버튼 응답 한도(3초) 안입니다. 먼저 말 걸기 판단은 대부분 "다른 사람이 먼저 답함"으로 취소됐습니다. 바쁜 채널에서 기대하는 동작입니다.

### TiDB (실제 TiDB 8.5, 초당 메시지 6개, 90초) — 비활성 전 기록

DB까지 한쪽 30 ms(왕복 60 ms)를 넣은 결과입니다. 다른 리전의 TiDB Cloud와 비슷합니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 판정 | **실패**: 답변 83건 시간 초과 | 통과 |
| 메시지 저장 p50 | 62초 (쓰기가 전부 한 줄로 대기) | 0.31초 |
| 답변 하나 (한가할 때) | 4.7초 | 3.2초 (같은 곳의 TiDB 2.0초, SQLite 1.8초) |
| 부하 중 답변 p50 | 시간 초과 | 11초 (대기 포함) |

같은 곳에 둔 TiDB에서 메시지 10만 개 + 5분 부하(`-seed 100000 -dims 4096`)도 통과했습니다: 답변 p50 0.88초·p99 3.2초, 메시지 저장 p50 5 ms, 부하 후 RSS 472 MB, goroutine·파일 누수 없음. 색인 재구성은 SQLite보다 느린 3–6초였습니다(모든 채널에 새 메시지가 계속 들어와 방마다 메시지를 다시 읽는 조건). 재구성은 배경에서 하고 그동안 이전 색인이 답변을 계속 처리합니다.

원인은 SQLite용 "한 번에 하나만 쓰기" 잠금이 TiDB에도 걸려 있던 것입니다. 트랜잭션 하나가 왕복 3–8번(0.2–0.5초)이라 초당 몇 건밖에 쓰지 못했습니다. 지금은 TiDB에서 쓰기가 동시에 진행되고, 같은 행을 읽고 고치는 곳(사용 한도, 투표)은 행 잠금으로 보호합니다(실제 TiDB로 확인: 24건이 동시에 한도 5를 노려도 정확히 5건만 통과, 잠금이 없으면 20건 통과). 쿼리마다 준비 단계 왕복을 없애고(`interpolateParams`), 답변마다 하던 작은 쓰기와 조회를 줄였습니다.

### 2026-10-01 재측정 (재난 알림·장소 검색·명령→대화 추가 뒤)

환경: 8코어 macOS(Apple Silicon), Go 1.27.1, SQLite. 가짜 모델 지연 0.4–0.8초, 1% 실패. 채널 12개, 사용자 60명, 개인 기능 함께(`-features`).

**평가**: 대기 상태 40 MB, 기억이 작을 때 부하 중에도 힙 20 MB 안팎이라 Go로 만든 목적(작은 자원)에 맞습니다. 메모리는 **저장된 메시지 수**(검색 색인이 메모리에 올라감)에 비례하고, 그 밖의 것(고루틴, 연결, 캐시)은 부하가 끝나면 처음 수준으로 돌아옵니다. 장시간 운영의 누수 위험은 9월 점검에서 고친 두 가지(색인 DB 연결 누수, 설정 변경마다 색인 재구성) 이후 재발하지 않았습니다. 15분 soak 후반부 힙 추세 +0.65 MB/분은 쌓이는 메시지(메시지당 약 3.5 KB)와 맞는 크기라 누수로 보지 않습니다.

## 용량 계획

### 메모리

검색 색인은 **메모리에 올라가며** 저장된 메시지 수에 비례합니다. 재구축 때 변경 없는 int8 행은 구·신 색인이 불변 메모리로 공유하고, 새로 생기거나 바뀐 행만 할당합니다. FTS는 여전히 다시 만들며 교체 뒤에도 이전 FTS가 잠시 남으므로, 권장 메모리는 부하 중 작업 집합에 여유를 더한 값입니다. MRL 메시지 벡터 기본 폭은 512이며 대상 메시지마다 516바이트의 벡터 payload(약 0.5 KiB)와 행 메타데이터가 듭니다. MRL 목록 밖 모델은 설치의 실제 leaf 폭을 써 더 커질 수 있습니다(명시 폭이 없으면 전체 폭). 공간 이름에는 실제 숫자 폭을 넣고 leaf 폭이 바뀌면 다시 임베딩하며, 폭을 아직 모르면 대기합니다. 아래 측정 수치는 1024 메시지 폭을 사용한 기록이므로 새 기본 적용 뒤의 실측값은 아닙니다.

| 저장된 메시지 | 4096차원 | 1024차원 (2026-10-13부터 기본) |
|---|---|---|
| 1만 | 512 MB | 512 MB |
| 10만 | 1.5 GB (측정: RSS 최대 약 0.8 GB) | 1 GB (측정: RSS 약 0.5 GB) |
| 50만 | 4 GB (추정) | 2 GB (추정) |
| 100만 | 8 GB (추정) | 4 GB (추정) |

기록이 많거나 Raspberry Pi처럼 메모리가 작은 기기라면:

- **임베딩 차원 줄이기**: `models.embed.dimensions: 1024`. 비용 없이 바로 적용되고 메모리·디스크 모두 크게 줄어듭니다. 다시 늘리려면 전부 재임베딩해야 하므로, 기본 모델처럼 차원 축소(MRL)를 지원하는 모델에서 쓰세요.
- **자동 Go 메모리 한도**: `GOMEMLIMIT`이 없으면 `masamongd`가 프로세스 메모리 한도를 감지해 60%를 GC 소프트 한도로 적용합니다(512 MiB에서 약 307 MiB, 1 GiB에서 약 614 MiB). Linux는 프로세스의 cgroup v2/v1 한도와 부모의 더 작은 한도, 물리 RAM 순으로 확인하고, Windows는 `GlobalMemoryStatusEx`, macOS·FreeBSD는 `sysctl`을 사용합니다. 감지할 수 없는 플랫폼은 기존 한도를 유지합니다. 시작 로그와 로그 → 진단에서 값과 출처(`go_memory_limit`)를 확인합니다. 명시적 `GOMEMLIMIT`이 우선합니다. SQLite·FTS의 Go 힙 밖 할당에는 남겨 둔 메모리가 필요합니다.
- **자동 성능 단계**: 같은 CPU 쿼터와 메모리 한도로 small·medium·large를 고릅니다. small(1코어, 또는 1.5 GiB 미만)은 읽기 연결 2개, 사진 디코드 1장, 운세 생성 1건, 대기 메시지 재집계 간격 2분입니다. medium은 지금까지의 고정 값입니다. SQLite 페이지 캐시 기본 2000 KiB, 재집계 간격 1분을 포함합니다. large(4코어 이상이고 6 GiB 이상)는 읽기 풀(최대 12), 페이지 캐시(연결당 32 MiB), 디코드 2장, 운세 생성 4건으로 올리고 재집계 간격을 20초로 줄입니다. 새 설정은 없고, `MASAMONG_PERF=small|medium|large`만 단계를 바꿉니다. 자세한 표는 [기억 운영 문서](https://github.com/kim0040/masamong2/blob/main/docs/memory-operations.md)에 있습니다.
- **요약 끄기**: `memory.summaries: false`면 요약 벡터가 없어집니다. 메시지 벡터는 남습니다(검색 품질은 조금 낮아질 수 있음).

### 디스크

기억은 **수집한 메시지 수**에 비례합니다: 메시지 1만 개당 약 27 MB(4096차원) / 15 MB(1024차원). 기간으로 지우지 않고 블록 단위로만 삭제합니다.

운영 기록은 **답변 수**에 비례하고 보관 기간이 지나면 지워집니다:

| 항목 | 1,000 답변당 | 보관 |
|---|---|---|
| 질문 임베딩 캐시 | 약 8 MB (4096차원) / 2 MB (1024차원) | 7일 |
| 대화 기록 | 약 1.9 MB | 상세 30일, 요약 400일 |
| 진단 trace | 약 0.8 MB | 30일 |
| 로그 | 약 0.2 MB | 최대 약 60 MB에서 순환 |

예: 하루 메시지 3,000개에 답변 1,000개면 운영 기록은 약 130 MB에서 더 늘지 않고, 기억은 하루 약 8 MB(1년 약 3 GB, 1024차원이면 1.6 GB)씩 늘어납니다. 백업은 DB 크기만큼 필요하며 자동 백업 보관 개수(`backup.keep`, 기본 4)만큼 곱합니다.

### 처리량

처리 한계 ≈ `limits.max_concurrent_turns` ÷ 답변당 모델 시간입니다. 실제 공급자에서 답변당 모델 시간이 3–8초라면 기본값 8로 초당 1–2.7개(시간당 3,600–9,600개)입니다. 대부분의 개인·커뮤니티 봇에는 충분하고, 더 필요하면 공급자의 분당 요청 한도를 확인한 뒤 값을 올립니다. [동시 처리와 성능](https://github.com/kim0040/masamong2/wiki/동시-처리와-성능)을 참고하세요.

## 알려진 한계와 다음 단계

비정상 종료는 감시 프로세스가 자동으로 다시 켜고 운영자에게 알립니다([보류 중인 결정](https://github.com/kim0040/masamong2/wiki/보류-중인-결정) 3번). 운영자가 정해야 하는 개선 항목(디스크 int8 저장, SQLite 동기화 수준, 백업 보관 등)은 [보류 중인 결정](https://github.com/kim0040/masamong2/wiki/보류-중인-결정)에 모아 두었습니다.

- **색인 재구축**: 새 조각이 들어오면 색인을 새로 만듭니다. 변경 없는 leaf·요약·메시지 int8 행은 이전 색인과 불변 메모리를 공유합니다. 메시지 메타데이터는 DB의 현재 메시지와 대조하고, 새로 생기거나 바뀐 벡터 BLOB만 500건씩 읽습니다. 삭제·수정·이름 변경 뒤의 메시지는 다음 재구축에서 제외합니다. 최초 leaf·요약 float16 BLOB도 최대 500 leaf씩 읽습니다. 점수 합산·메시지→leaf 순서·동점 처리는 그대로입니다. FTS와 leaf 메타데이터는 매번 다시 만들고, 새 메시지가 생긴 방의 이력도 다시 읽습니다. 콘솔 집계는 읽기 풀을 쓰며 대기 메시지 수에는 목록 정렬·그룹화를 생략합니다.
- **방 하나가 아주 클 때**: 새 메시지가 순서대로 들어오면 체크포인트 뒤 꼬리만 다시 자릅니다(2026-10-12). 가져오기·수정·삭제·조각 규칙 변경처럼 순서가 어긋나는 경우에만 그 방의 메시지를 전부 읽어 다시 맞춥니다. 한 채널에 수십만 개가 쌓였다면 그때 한 번 그만큼 읽습니다(SQLite에서 1초 안팎).
- **SQLite 쓰기는 하나씩**: 여러 작업이 동시에 써도 차례로 처리됩니다. 긴 읽기와 백업은 별도 연결이라 막히지 않습니다(10만 개에서 메시지 저장 p95 20 ms, 최대 0.45초).
- 테스트는 가짜 모델 서버로 합니다. 실제 공급자의 지연·한도·장애 패턴은 운영 로그와 콘솔 **대화 기록**의 단계별 시간으로 확인하세요.

## 2026-10-12 저사양 메모리 재측정

같은 i5-6400T에서 `GOMAXPROCS=1`, 1024차원, 메시지 벡터 기본 활성 상태로 측정했습니다. 100k는 완성된 합성 DB 사본(관측 100,171개, 벡터 100,016개)에서 `-seed 0`으로, 10k는 새 DB에 시드한 뒤 실행했습니다. 부하는 3분, drain 최대 60초이며 테스트와 겹치지 않았습니다. 별도 cold/hot Reload에서 5ms 간격으로 피크를 수집했습니다. 이 도구는 daemon main을 거치지 않아 자동 Go 메모리 한도 없이 인덱스 변경 자체를 측정합니다.

| 규모 | cold 뒤 heap | hot 재빌드 heap 피크 | hot 뒤 working set | hot 재빌드 |
|---|---:|---:|---:|---:|
| 10k | 23.6 MiB | 41.6 MiB | 80.0 MiB | 0.574초 |
| 100k | 208.3 MiB | 416.9 MiB | 494.2 MiB | 7.034초 |

100k의 변경 전 재빌드 heap 피크는 671–688 MiB, 색인 뒤 working set은 638 MiB였습니다. 변경 후 100k 부하 표본 피크는 heap 455.8 MiB/working set 563.4 MiB이고 drain 끝 working set은 619.4 MiB였습니다. 초기 로드는 16.925초, 마지막 재빌드는 6.400초였습니다. 별도 사본의 첫 cold 로드는 32.930초로, seed 직후의 따뜻한 DB와 캐시 조건이 달라 속도 개선을 주장하지 않습니다. hot 재빌드는 벡터 100,016개를 재사용하고 BLOB 읽기 0개를 확인했습니다.

10k는 seed 뒤 heap 30.4 MiB/working set 131.7 MiB, 부하 표본 피크 heap 60.0 MiB/working set 159.5 MiB였습니다. 두 부하 테스트 모두 오류 없이 끝나고 DB 무결성 검사를 통과했습니다. 30k/512MiB 및 실제 모델 지연은 별도 검증이 필요합니다. 콘솔 지연은 이후 방별 집계용 커버링 인덱스와 대기 메시지 수 공유 집계(콘솔·진단이 한 번에 하나, 끝난 뒤 1분 간격)로 줄였습니다. 같은 100k 사본·같은 부하에서(최종 측정 중 Windows Defender가 1–2코어를 써서 비관적인 수치) 작업 전 → 후: 블록 목록 p50 27.1초 → 2.1초, dashboard p50 26.1초 → 8.1초, 대화 응답 p50 7.9초 → 3.2초(p95 37.2초 → 9.7초), 메시지 수집 p95 7.6초 → 0.56초, 프로세스 RSS 최대 767 → 635 MB. 공간별 첫 블록 목록은 대기 수 집계(100k 약 5–7초)를 기다립니다. FTS·메타데이터 재생성이 다음 조사 대상입니다.
